### 先懂三層架構

前端

**lip-web-cln**

呼叫 `/api/…`，帶 LIP-C 電文 ID。例：`POST /api/case/inputInfo/query`（LIP-C-CLNCINPTC001）。

↓ nginx 轉發 /api/

組合層

**lip-svc-cln（composite layer）**

檢查上行後，用 `restTempHelper.postForEntity(normalReqFactory.genRequestTemplate(req, tranrq, "LIP-B-…"))` 依電文 ID 呼叫基礎層，再組合下行回給前端。部分功能也會直接查資料庫（專案內有 repo、entity、sql）。

↓ 依 LIP-B 電文 ID 呼叫

基礎層

**query（CQY）· transaction（CTN）· common（CCM）· todo（CTO）（base layer）**

真正查詢或寫入資料庫。基礎層之間也會互相呼叫，例如 CTNHRISKT001 → CTNHRISKT002。lip-svc-cln 呼叫次數：CQY 130、CTN 60、CCM 25、CTO 9。

報表（ZRWeb）與批次（lip-bch-cln）是另外的入口，不走這三層。依開發注意事項，寫新交易要更新 `LON_ENDPOINT`；組合層呼叫時只給電文 ID，電文與服務網址的對應應是由這張表管理（推論，細節請向團隊確認）。

### 電文 ID 怎麼拆

**LIP** 系統 \- **B** 層：B 基礎／C 組合 \- **CQY** 服務碼 **CINPT** 功能碼 **Q** 類型 **001** 序號

| 片段 | 代表 | 常見值 |
| --- | --- | --- |
| 層 | 電文屬於哪一層 | `C` 組合層（lip-svc-cln）、`B` 基礎層 |
| 服務碼 | 實作在哪個專案 | `CQY` 查詢（query）、`CTN` 異動（transaction）、`CLN` 組合層（lip-svc-cln）、`CCM` 共用（common）、`CTO` 待辦（todo）；另有 CLZ、COM、PZR、CLH、CEX 等其他服務 |
| 功能碼 | 業務功能，同一功能在各層相同 | `CINPT` 進件輸入、`HRISK` 高風險、`TODOV` 資深副總待辦、`INITC` 起案、`ITEMS` 項目設定、`REPOT` 報表、`CACNT` 科目 |
| 類型 | 做什麼 | `Q` 查詢、`T` 交易（異動）、`C` 組合層電文 |

同一個功能通常是一組：前端呼叫 `LIP-C-CLNCINPTC001` → 組合層呼叫 `LIP-B-CQYCINPTQ001`。例外以規格書的 TFS 路徑為準，例如 `LIP-C-CTNINITCT001` 雖以 C 開頭，實作在 transaction。批次用另一套編號（如 `CLNS0_B101`）。

### 怎麼讀規格書

#### API 規格書（LIP-C、LIP-B 電文）

| 規格書章節 | 看什麼 | 寫在哪裡 |
| --- | --- | --- |
| 壹、系統規格 | 程式名稱、TFS 專案路徑 | 決定寫在哪個 repo（lip-svc-cln、query、transaction…） |
| 貳、資料庫規格 | 用到的資料庫與 schema | 連線資訊以 Wiki 為準，不要寫進程式或文件 |
| 參、外圍服務資訊 | 是否呼叫行外或其他系統 | Service 的外部整合 |
| 肆、API 資訊 | URI、HTTP Method | Controller 的 `@PostMapping` |
| 肆、上行／下行電文 | 欄位、型別、長度、是否必要 | Tranrq／Tranrs DTO（型別一律 String）與欄位檢核 |
| 伍、處理邏輯 | 依序的處理步驟 | ServiceImpl：檢查必填（E001）→ 準備資料（查無資料拋 DataNotFoundException）→ 規則檢核（Check／Validator）→ 呼叫其他電文 → 寫入（DataProcessor）→ 寫歷程 → 回傳 0000 |

#### 前端頁面規格書（cln-xxx001）

| 規格書章節 | 看什麼 | 寫在哪裡 |
| --- | --- | --- |
| 程式功能概述 | 程式名稱、分頁方式（真分頁／假分頁） | 元件命名；分頁是否交給後端 |
| 相關電文（API） | 用到哪些 LIP-C 電文、查新修刪 | 頁面 Service 方法與 interfaces |
| 相關模組、初始畫面 | 畫面長相、有哪些子畫面或對話框 | 判斷頁面類型（見前端「頁面類型盤點」） |
| 接收參數 | 前頁傳入的值（以 @ 標示） | `@Input()` 或彈窗的 `DynamicDialogConfig.data` |
| 初始查詢 API | 進畫面時要查什麼 | `ngOnInit`／`ngOnChanges` |
| 畫面欄位 | 欄位類型、資料來源、下拉代碼、按鈕行為 | HTML 與 FormGroup；下拉用 `getComnCodeOptionsByCodetype`；按鈕對應的方法 |
| API 上下行資訊 | 欄位對應 | Req／Res interface |

### 怎麼練

### 讀規格書

API 功能先讀 LIP-C 再讀 LIP-B，弄清楚誰呼叫誰；前端功能先讀頁面規格書，再讀它用到的 LIP-C。

### 判斷寫在哪

看 TFS 路徑與電文 ID 的服務碼決定專案；前端用「頁面類型判斷流程圖」決定頁面寫法。

### 開練習分支自己寫

從 dev 切出自己的練習分支，照「拿到頁面怎麼寫」與後端共通規範實作；練習用的分支不要合回 dev。

### 對照解答

找同名的 SvcImpl、Controller、元件比較差異：自己漏了哪個檢核、哪個呼叫、哪個欄位。

### 用 AI CR 工具自查

`CLN_參考練習/md/` 已有 9 份轉好的 md 規格書，可直接搭配前端 CR 工具使用。

### 觀念題

**A三層架構與電文 ID 5 題**

#### Q1. 前端「進件輸入」頁按下查詢後，請求依序經過哪些服務？

-   A. lip-web-cln → lip-svc-cln-query
-   B. lip-web-cln → lip-svc-cln-query → lip-svc-cln
-   C. lip-web-cln → lip-svc-cln → lip-svc-cln-query
-   D. lip-web-cln → lip-svc-cln-transaction → lip-svc-cln

正確答案：C。前端打 `/api/…` 的組合層電文，nginx 轉給 lip-svc-cln；lip-svc-cln 再以基礎層電文呼叫 query 查資料。

#### Q2. 電文 ID LIP-B-CTNHRISKT001 應該實作在哪個專案？

-   A. lip-svc-cln-transaction
-   B. lip-svc-cln-query
-   C. lip-svc-cln
-   D. lip-svc-cln-common

正確答案：A。**B** 是基礎層，服務碼 **CTN** 代表異動（transaction）。

#### Q3. 電文 ID 裡的服務碼 CQY、CTN、CLN 分別代表什麼？

-   A. CQY 查詢（query）／CTN 異動（transaction）／CLN 組合層（lip-svc-cln）
-   B. CQY 查詢／CTN 待辦／CLN 報表
-   C. CQY 佇列／CTN 通知／CLN 清單
-   D. CQY 共用／CTN 待辦／CLN 批次

正確答案：A。服務碼決定程式寫在哪個專案：CQY → lip-svc-cln-query、CTN → lip-svc-cln-transaction、CLN → lip-svc-cln（組合層）。另外 CCM 是共用（common）、CTO 是待辦（todo）。

#### Q4. 寫前端頁面時，Service 應該呼叫哪一種電文？

-   A. LIP-B 基礎層電文，路徑如 `/case/inputInfo/query`
-   B. 兩種都可以，看哪個回應比較快
-   C. 直接查資料庫
-   D. LIP-C 組合層電文，路徑如 `/api/case/inputInfo/query`

正確答案：D。前端只打組合層 lip-svc-cln 的 `/api/…`，不會直接呼叫基礎層；基礎層的路徑沒有 `/api` 前綴。

#### Q5. 組合層 lip-svc-cln 是用什麼方式呼叫基礎層？

-   A. 直接 import 基礎層專案的 Service 類別
-   B. 共用同一個資料庫交易
-   C. `restTempHelper.postForEntity`，用 `normalReqFactory.genRequestTemplate(…, "LIP-B-…")` 帶入電文 ID
-   D. 請前端轉發

正確答案：C。組合層只給電文 ID 就能找到對應服務。依開發注意事項，新交易要更新 `LON_ENDPOINT`，電文與網址的對應應由這張表管理（推論，細節請向團隊確認）。

#### Q6. API 規格書的哪一章，決定程式要寫在哪個 repo？

-   A. 肆、上行／下行電文
-   B. 壹、系統規格（TFS 專案路徑）
-   C. 貳、資料庫規格
-   D. 伍、處理邏輯

正確答案：B。看 TFS 專案路徑。電文 ID 通常也看得出來，但以 TFS 路徑為準。

#### Q7. 處理邏輯寫「必填欄位為空，回傳 RETURNCODE=E001、資料格式錯誤」，這段應該寫在哪裡？

-   A. `LON_ENDPOINT` 設定
-   B. ServiceImpl 處理流程的第一步（檢查電文資料完整性）
-   C. Controller 的 `@PostMapping`
-   D. 前端的 ErrorInterceptor

正確答案：B。「伍、處理邏輯」依序對應 ServiceImpl：檢查必填 → 準備資料 → 規則檢核 → 呼叫其他電文 → 寫入 → 寫歷程 → 回傳 0000。

#### Q8. 上行電文欄位寫「資料型態 String、最大長度 16」，後端 Tranrq 的欄位型別應該是？

-   A. 一律 String
-   B. 看前端怎麼傳
-   C. 依內容改用 Integer 或 BigDecimal
-   D. Object

正確答案：A。後端共通規範：交易上下行參數型別一律為 String。

#### Q9. 前端頁面規格書的「接收參數」（以 @ 標示），在程式中對應什麼？

-   A. `ngOnDestroy`
-   B. `@Input()`，或彈窗的 `DynamicDialogConfig.data`
-   C. 一律從 sessionStorage 讀
-   D. `HttpParams`

正確答案：B。嵌入的子畫面用 `@Input()`，彈窗用 `DynamicDialogConfig.data`；「初始查詢 API」則對應 `ngOnInit`／`ngOnChanges`。

#### Q10. 規格書的下拉選單寫「CommonService.getComnCodeOptionsByCodetype(…)，label: codeName、value: codeOption」，正確寫法是？

-   A. 另外呼叫一支基礎層電文取代碼
-   B. 把回傳的 CommCode\[\] 直接綁到 p-dropdown
-   C. 呼叫後用 `mapToOptions` 轉成選單選項
-   D. 自己在 ts 寫死選項陣列

正確答案：C。CR 要點：代碼表選項用 shared 的 `mapToOptions` 轉換；多個代碼一起查用 `forkJoin`。

#### 進件輸入：查詢（組合層） LIP-C-CLNCINPTC001 · lip-svc-cln

#### Q11. 上行的案件編號 ApplyId 是空的，組合層應不應該呼叫基礎層？

-   A. 不應該，先做電文完整性檢查，直接回應錯誤
-   B. 應該，但把 ApplyId 補成空字串再送
-   C. 應該，讓基礎層去判斷
-   D. 應該，查不到資料再回錯誤

正確答案：A。每支電文第一步都是「檢查電文資料完整性」，必填缺漏就直接回錯誤，不往下呼叫。

#### Q12. 呼叫基礎層查詢後「查無資料」，組合層該怎麼回應？

-   A. 回 E001 資料格式錯誤
-   B. 自動重試三次
-   C. 拋 DataNotFoundException
-   D. 視為正常，回 0000

正確答案：D。規格書寫「若 API 查無資料視為正常」。查詢類電文常見這種設計，前端再依空資料顯示對應畫面。

#### Q13. 基礎層下行有些欄位組合層的規格書沒有列（例如郵遞區號、鑑價聯絡人），組合層下行該怎麼組？

-   A. 依組合層自己規格書的下行欄位組成
-   B. 回錯誤，請 SA 統一欄位
-   C. 多出來的欄位補成空字串
-   D. 把基礎層下行原封不動全部轉給前端

正確答案：A。組合層與基礎層各有自己的電文契約；組合層只回自己規格書定義的欄位。

#### Q14. 呼叫基礎層時發生非預期例外（例如連線逾時），下行 RETURNCODE 應該是？

-   A. E001 資料格式錯誤
-   B. 0000 交易成功
-   C. 9999 其他系統異常
-   D. 不包電文，直接回 HTTP 500

正確答案：C。規格書：流程無異常回 0000，否則回 9999「其他系統異常」。

#### Q15. 規格書的「處理結果代碼表」寫必填缺漏回 E903，但「處理邏輯」寫回 E001，該怎麼做？
