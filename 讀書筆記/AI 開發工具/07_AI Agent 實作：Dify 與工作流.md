# 07. AI Agent 實作：Dify 與工作流

> 來源：[筆記平台 · AI 開發工具](https://hhtim.github.io/notes-platform/ai-tools/#/lesson/ai-agent-dify)　第 7 課 / 共 8 課 · 約 14 分鐘

**把查課程、收報名資料、寫進試算表串成可檢查的流程，再補上記憶、日誌與防護。**

### 讀完這課你會

*   把助理拆成知識庫、工具與工作流
*   知道為什麼模型要靠外部工具才知道現在幾點
*   用日誌與防護規則看住會動手的助理

*【從需求到流程】*

## 讓助理同時具備知識與行動能力

使用者問「下週有哪些課？」時，助理要去查資料；說「幫我報名」時，它還得拿到姓名、信箱、課程與時間，再去呼叫外部系統。

```
使用者
  ↓
問題分類
  ├─→ 課程查詢 → 知識庫檢索 → 回答
  └─→ 課程報名 → 抽出欄位 → 跟使用者確認 → 寫入試算表
```

模型像聽得懂交辦事項的櫃檯人員，知識庫是資料櫃，工具是電話跟表單，工作流則是標準作業程序。四樣東西用途不同，不能只靠一段很長的提示全部取代。

*【先把知識裝進去】*

## 文件怎麼變成查得到的知識

先建知識庫、上傳課程表。系統通常會把文件切分，再用嵌入模型（Embedding Model，把文字轉成一組數字、讓意思相近的內容在數學上也靠得近）轉成向量；檢索拿到一批候選片段之後，還可以用重排序模型（Rerank Model）調整先後順序。

> 文件 → 切分 → 轉成向量 → 找候選片段 → 重排序 → 把相關內容交給模型回答

| 元件 | 白話比喻 | 用途 |
| --- | --- | --- |
| 嵌入 | 替內容標出語意座標 | 找出意思相近的片段 |
| 重排序 | 把候選答案重新排隊 | 讓最相關的內容排到前面 |
| 描述欄位（Metadata，Dify 的文件與介面用的就是這個名字）[出處](https://docs.dify.ai/en/cloud/use-dify/knowledge/metadata) | 貼在資料夾上的標籤 | 依日期、類別或來源先縮小範圍 |

1.  建課程知識庫並匯入文件。
2.  確認切分結果，不要只看「上傳成功」就算完。
3.  用已知答案的問題測它撈得回什麼。
4.  替文件加上課程類型、日期或版本這類描述欄位。
5.  建對話應用，指示模型只根據檢索到的內容回答，沒有依據就明說。

這條路也有代價：嵌入模型會更新，之前建好的流程可能要跟著調；描述欄位的量也會越積越多。介面、可選模型、切分方式與檢索參數會隨 Dify 版本改變，照做前先看目前的說明。

*【取得可靠的時間】*

## 會說話不等於知道現在幾點

模型可能從上下文猜日期，但不該把推測當成系統時間。需要「現在幾點」時，應該呼叫可信的時間工具，並且明確指定時區。這就像請櫃檯抬頭看牆上的標準時鐘，而不是憑感覺回答。

> 💡 例子：使用者說「幫我報名明天下午的課」，流程要先取得台北時區的目前時間，再把「明天」換算成確切日期。

做法是在 Dify 裝一個查目前時間的工具。外掛名稱與安裝方式會因版本與外掛生態而異，重點是「時間要從工具來，不要從模型猜」。

*【連上外部系統】*

## 工具負責動作，模型負責判斷何時用

報名表可以只設四個欄位：建立時間、姓名、信箱、課程名稱。寫入之前先檢查必填欄位，並讓使用者確認，免得模型把猜出來的內容送進正式資料。串接方式有三種：

| 串接方式 | 適合情境 | 注意事項 |
| --- | --- | --- |
| 人工操作介面 | 次數少、由人逐筆處理 | 容易重複輸入或漏填 |
| 直接串接對方的介面 | 需求固定、團隊有能力維護程式 | 要處理認證、錯誤與版本變動 |
| 透過 MCP | 希望用共通協定把工具交給助理 | 仍要審伺服器、權限與資料流向 |

這個實驗是用一個第三方平台建出一台連到試算表服務的 MCP 伺服器，完成授權之後把伺服器網址交給 Dify。供應商的介面、支援的工具、授權範圍與設定步驟都會變動，重點是別把試算表識別碼、授權權杖或憑證寫進提示或公開的日誌；只授權需要的那份試算表與必要操作，並先想好權杖要怎麼撤銷與輪替。

*【固定執行順序】*

## 用工作流取代「想到哪做到哪」

單一助理可能自己決定先後順序，沒辦法保證每次都走過同一輪檢查——可能發生的狀況是流程跑起來都對，精準度卻不穩。工作流把任務拆成節點與分支，每一步都有明確的輸入與輸出。

1.  **問題分類**：判斷使用者是要查課程、要報名，還是問別的事。
2.  **知識檢索**：查課程時間與內容。
3.  **抽出欄位**：把自然語句整理成姓名、信箱、課程這些欄位。
4.  **條件檢查**：必填欄位缺了就回頭追問，不直接寫入。
5.  **使用者確認**：把即將寫入的資料顯示出來，取得明確同意。
6.  **呼叫工具**：把資料寫進試算表。
7.  **處理結果**：依工具真正的回傳值告知成功或失敗，不用模型猜執行結果。

> 結構化流程提高可控性，但每一步都叫模型的話，延遲與成本會一路累積。能用確定規則完成的檢查，就不必交給模型。

這樣做有兩個代價：一是流程節點幾乎都在呼叫模型，處理耗時又要管成本；二是 MCP 的設定繁瑣，安全性也要顧。節點名稱與可用功能會隨 Dify 版本調整。

*【延伸實驗】*

## 語音與大量資料：先拆，再逐筆處理

語音流程可以拆成：上傳音檔、語音轉文字、抽出結構化欄位、人工確認、寫入紀錄。語音轉文字可以用雲端的語音服務，也可以用模型供應商提供的方案；外掛、取得金鑰的流程、支援格式與服務狀態都會改變。

```
音檔 → 語音轉文字 → 抽出可觀察的資訊
    → 標示不確定的地方 → 人工確認 → 只保存必要的紀錄
```

拿這套流程去對真實的人做事實認定（例如從一段錄音判斷某人做過什麼）要特別小心：模型的推測不該直接變成結論。凡是牽涉感情、健康、違法或其他敏感判斷的內容，都只能當成待人工確認的線索。

面對一大批資料（例如一堆標案）也一樣：不要一次全部塞給模型，它會處理不好。先用程式或規則切成可追蹤的項目，再一筆一筆處理，記錄成功、失敗與重試狀態。切小不代表可以忽略模型的輸入上限與成本。

*【記憶設計】*

## 對話紀錄跟變數記憶不是同一件事

每輪都把完整對話再附一次，像把整本逐字稿重印給新來的同事：內容越來越長，成本也跟著漲。而且長度一拉長就容易漏東西——例如聊了三輪之後，助理就忘了一開始講的名字。變數記憶則是把真正需要長期保留的資訊整理成欄位，例如偏好語言或會員等級。

| 記憶方式 | 適合保存 | 主要風險 |
| --- | --- | --- |
| 近期對話 | 這一輪問題的語境 | 內容變長、雜訊與成本增加 |
| 摘要 | 較長對話的重點 | 摘要可能遺漏或扭曲資訊 |
| 結構化變數 | 姓名、偏好、狀態 | 更新錯誤、資料過期、隱私問題 |

這些變數還可以往外存進快取或資料庫。各平台的記憶功能、保存位置與限制會持續更新。不論存在哪裡，儲存身分資料之前都要確認必要性、告知用途、限制保存期限，並提供修正與刪除的方式。

*【監控與防護】*

## 日誌告訴你發生了什麼，防護規則限制不該發生的

多個助理共用同一個模型服務時，需要記錄誰在什麼時候呼叫了哪個模型、延遲多久、有沒有失敗、大致用了多少量。做法是在 Bedrock 開啟模型呼叫紀錄，回 Dify 對話幾次，再到 S3 看產生的日誌。日誌可能包含提示、回應或個資，所以要搭配遮罩、權限與保存期限。

防護規則（Amazon Bedrock Guardrails）像入口與出口的安檢，可以針對禁止的主題、有害內容類別、特定字詞、敏感個資，以及回答有沒有依據來源，分別設定要擋下還是遮蔽。它不是靠一個關鍵字就能完美判斷的東西：規則太寬會誤擋正常問題，太窄則會漏掉換句話說的版本。

1.  先定義要降低的風險，例如詐騙式的投資招攬。
2.  準備三組測試案例：該擋的、該放行的、以及邊界模糊的。
3.  在 Bedrock 建立防護設定並測試。
4.  在 Dify 的工作流裡引用正確的防護設定與版本。
5.  記錄誤擋與漏擋，持續調整規則。

*【驗收】*

## 用案例證明流程真的可靠

*   查已存在的課程：答案要對得上知識庫的內容。
*   問不存在的課程：要說沒有足夠資料，而不是編一個出來。
*   報名資料缺信箱：流程要回頭追問，不能直接寫入。
*   相對日期：要用時間工具搭配指定時區換算。
*   寫入失敗：要回報失敗，並保留可以重試的資訊。
*   重複送出：不要產生重複的報名紀錄。
*   敏感或受限的問題：照防護政策處理，並留下適當的稽核資訊。

### 重點整理

*   知識庫讓助理找得到資料，工具讓它做得了事，工作流固定住關鍵順序。
*   模型不知道現在幾點，時間要從工具來並指定時區。
*   抽出欄位之後先檢查必填、再讓使用者確認，才降得下誤寫風險。
*   對話紀錄留語境、變數記憶留確認過的狀態，兩者解決的問題不同。
*   日誌管可觀測性、防護規則管安全邊界，兩者都要靠測試案例調整。

- (D) 判斷這個月的雲端帳單有沒有超支

**答案：(A)** 嵌入建立語意座標，系統才找得出跟問題意思相近的文件片段。

**Q2. 描述欄位（Metadata）在課程知識庫裡最適合拿來做什麼？**

- (A) 依課程類型、日期或來源先縮小檢索範圍
- (B) 取代文件內容並自動回答所有問題
- (C) 把自然語句換算成目前時間
- (D) 給予主機存取模型服務的權限

<details><summary>看答案</summary>

**答案：(A)** 描述欄位是描述資料的標籤，可以先縮小候選範圍，再做語意檢索。

</details>

**Q3. 使用者說「幫我報名明天的課」時，為什麼該呼叫時間工具？**

- (A) 相對日期必須依可靠的目前時間與時區換算
- (B) 模型完全看不懂「明天」這兩個字
- (C) 時間工具會順便取得使用者的姓名與信箱
- (D) 呼叫時間工具之後就不必再讓使用者確認

<details><summary>看答案</summary>

**答案：(A)** 模型讀得懂語意，但確切日期需要可信的時間來源與明確的時區。

</details>

- (A) 工作流能固定住分類、抽欄位、檢查、確認與寫入的順序

- (C) 工作流不需要任何外部工具或權限
- (D) 工作流會消除掉全部的模型費用

<details><summary>看答案</summary>

**答案：(A)** 工作流提高的是可控性與可測試性，消不掉模型、工具或權限本身的風險。

- (B) 不管欄位完不完整都先寫進去

- (B) 兩者完全相同，只是介面名稱不同
- (C) 變數記憶適合無限期保存所有原始對話
