*【先講清楚它是什麼】*

## 設計模式是經驗的名字，不是可以貼上去的答案

設計模式（design pattern）是針對常見軟體設計問題整理出來的**可重用解題思路**。它比較像建築裡「採光天井」這個概念：說明問題長什麼樣、結構怎麼擺、要付出什麼代價，但不會給你每一棟房子都通用的施工圖。

它最大的價值之一是**建立團隊的共同語言**：說一句「這裡用策略模式」，比逐句描述「把好幾種演算法各包成一個可替換的物件」省事得多。

> 先確認哪裡會變、有什麼限制，再選模式；不要先選模式，再回頭找地方套。

> 模式不是越多越好。問題很單純時，直接而清楚的程式碼，通常比先蓋一套複雜架構更好維護。

> GoF 那本書總共 23 種模式，分成三群——這個總表與「創建型五個是哪五個」在〈Java 基礎快答〉有整理過。

*【先看它在解哪一類關係】*

## 建立型、結構型與行為型

| 類別 | 核心問題 | 常見模式 |
|---|---|---|
| **建立型<br>Creational** | 物件該怎麼生出來、由誰決定生哪一種 | Singleton、Factory Method、Abstract Factory、Builder、Prototype |
| **結構型<br>Structural** | 類別與物件怎麼組合成更大的結構 | Adapter、Bridge、Composite、Decorator、Facade、Flyweight、Proxy |
| **行為型<br>Behavioral** | 物件之間怎麼分工、溝通、切換行為 | Strategy、Template Method、State、Observer、Command、Mediator、Chain of Responsibility |

分類的用處是縮小思考範圍，但同一個實際設計常常同時牽涉三類。重點永遠是**這個模式扛的是什麼責任**，不是把分類名稱背起來。

---

*【從需求裡的動詞認出來】*

## 常見模式怎麼認

- **Factory Method 工廠方法**：把「要建立哪一種具體物件」延後交給子類別或特定的建立者決定。
- **Builder 建構者**：把複雜物件的組裝步驟拆開，一步步設定完再產出成品。
- **Adapter 轉接器**：像轉接頭，把既有的介面轉成呼叫端要的樣子。
- **Decorator 裝飾者**：用包裝的方式疊加功能，不必改原本的類別。〈檔案與資料流〉的 I/O 鏈就是這個模式。
- **Facade 門面**：在複雜的子系統前面開一個簡單的統一入口。
- **Proxy 代理人**：用替身控制對真實物件的存取：延遲載入、權限檢查、遠端呼叫。
- **Strategy 策略**：把可替換的演算法各自包成物件，執行時再選。
- **Observer 觀察者**：主體狀態一變，就通知所有訂閱它的觀察者。
- **State 狀態**：把不同狀態下的行為拆成狀態物件，取代一長串條件分支。

「折扣算法有好幾種，之後還會再加」——這通常指向哪裡？

這是「演算法要能替換」的問題，先想 Strategy。如果需求換成「舊的付款服務介面跟新系統對不上」，那就比較接近 Adapter。認模式的訣竅就是先問**會變的是哪一塊**。

*【單例控制的是數量與入口】*

## Singleton 的核心結構

單例模式（Singleton）確保某個類別在指定範圍內只有一個實體（instance），並提供一致的取得方式。三個條件就講完它：**該類別只能有一個實體、它自己負責建立那個實體、它提供一個不必實體化就能呼叫的取得方法。**

最基本的結構：私有建構子 ＋ 保存實體的靜態欄位 ＋ 公開的取得入口。

```java
public final class AppRegistry {
    private static final AppRegistry INSTANCE = new AppRegistry();

    private AppRegistry() { }        // 外面 new 不出來

    public static AppRegistry getInstance() {
        return INSTANCE;
    }
}
```

這種「一開始就建好」的寫法（類別一載入就把實體建出來，不管之後用不用得到）結構單純，而且靠類別初始化機制就完成了安全發布。如果建立成本低、程式又一定會用到它，通常不需要為了「延遲」去增加同步的複雜度。

> 「只有一個」的範圍要講清楚：它是**一個類別載入器（class loader）底下只有一個**。同一支程式跑兩個行程，就有兩份實體；應用程式伺服器上不同的應用各有自己的載入器，也各有一份。所以單例不是分散式系統裡的「全域唯一」 [[出處]](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.3)。

*【延遲建立遇上並行】*

## Lazy Singleton 的競爭條件

最直觀的延遲建立（lazy initialization）寫法，在多執行緒下並不安全——兩條執行緒可能同時看到 `instance == null`，然後各建一個：

```java
public static Service getInstance() {
    if (instance == null) {        // 兩條執行緒可能同時走到這
        instance = new Service();
    }
    return instance;
}
```

常見的修法有兩種。第一種是**雙重檢查鎖定**：

```java
private static volatile Service instance;   // volatile 不能省

public static Service getInstance() {
    if (instance == null) {
        synchronized (Service.class) {
            if (instance == null) {
                instance = new Service();
            }
        }
    }
    return instance;
}
```

> 那個 `volatile` 是這段程式的命脈。沒有它，因為〈執行緒與並行〉講的指令重排序，別的執行緒可能拿到一個「參考已經指過去、但建構子還沒跑完」的半成品物件。

第二種是**靜態內部類別持有者**——寫起來最短，而且延遲建立與執行緒安全都由類別初始化機制保證，一個同步字都不必寫：

```java
public final class Service {
    private Service() { }

    private static class Holder {
        private static final Service INSTANCE = new Service();
    }

    public static Service getInstance() {
        return Holder.INSTANCE;    // 第一次碰到 Holder 才初始化
    }
}
```

還有一種是用列舉：

```java
public enum AppRegistry {
    INSTANCE;

    public void register(String name) { /* ... */ }
}
```

列舉寫法有兩個真正的優點：列舉實體的建立與序列化由語言本身保證，反射也破壞不了它 [[出處]](https://docs.oracle.com/javase/specs/jls/se21/html/jls-8.html#jls-8.9)。延遲建立這點它其實跟上面的持有者寫法一樣：列舉常數在類別初始化時建立，而類別初始化要等到第一次主動使用才發生。但說它是「最佳解」就過頭了——它一樣把相依藏起來，測試時很難換掉。**該問的是「全域唯一而且到處拿得到」真的是需求嗎**，而不是哪種寫法最方便。

*【唯一實體 ≠ 只有一條執行緒在用】*

## Singleton 的代價

單例物件往往被很多條執行緒同時存取，所以**「安全地只建立一次」只解決了初始化那一段**。物件裡如果還留著可變狀態，那些讀寫本身要另外設計執行緒安全（回頭看〈執行緒與並行〉）。

> 💡 **「單例」講的是實體數量與取得方式；「不可變」講的是建立後狀態能不能改——兩件事**

另一個代價是它會形成**藏起來的全域相依**：類別在自己內部直接 `getInstance()`，呼叫端從簽章上完全看不出它依賴了什麼，測試時也換不掉。依賴注入（dependency injection，把相依的物件從外面交給它，而不是自己去拿）就把這件事攤在陽光下：

```java
public class CheckoutService {
    private final PaymentGateway gateway;

    public CheckoutService(PaymentGateway gateway) {   // 依賴看得見
        this.gateway = gateway;
    }
}
```

測試時傳一個假的 `PaymentGateway` 進去就好，生命週期也交給框架決定。Spring 那套做的就是這件事。

*【用問題與代價檢查】*

## 選模式的實務流程

- 先找出**真正會變**的是哪一塊：建立流程、介面、演算法，還是物件狀態？
- 確認這個模式真的降低了耦合，而不是只把程式碼搬到更多類別去。
- 把代價列出來：多出來的抽象、多出來的物件、流程變難追、還有執行緒安全。
- 先用小範例驗證，再照實際的變化擴充。
- 留替換空間可以，但不要為了還沒出現的需求先蓋一座城堡。

### 重點整理

- 設計模式是可重用的解題思路與共同語言，不是可以複製貼上的程式碼範本。
- 建立型管物件怎麼生、結構型管怎麼組合、行為型管怎麼協作。
- Strategy 換演算法、Adapter 轉介面、Decorator 疊功能、Facade 開簡單入口。
- 延遲建立的單例一定要處理並行：雙重檢查鎖定的 `volatile` 不能省，靜態內部類別持有者更簡潔。
- 單例的「唯一」是一個類別載入器底下唯一，不是整個世界唯一。
- 安全地建立一次，不代表它內部的可變狀態自動就執行緒安全了。
- 單例會藏起相依關係；相依看得見、測試換得掉，通常比方便更值錢。

- (B) 靜態欄位會變得讀不到

- (D) 多條執行緒可能各建一個實體

<details><summary>看答案</summary>

**Q6. 雙重檢查鎖定的寫法裡，那個 volatile 可以省掉嗎？**

- (A) 可以，synchronized 已經夠了
- (B) 不行，但原因是 volatile 會加鎖

<details><summary>看答案</summary>

**答案：(D)** 指令重排序可能讓參考先指過去、建構子後跑完；volatile 建立的順序保證正是用來擋這件事。

</details>

**Q7. 某個 Singleton 已經能安全地只建立一次。關於它內部的可變欄位，哪一項正確？**

- (A) 所有欄位操作自動具有 CAS 語意
- (B) 單例物件不可能被多條執行緒同時存取
- (C) 欄位會自動變成 final
- (D) 那些欄位的並行讀寫仍要另外設計執行緒安全

<details><summary>看答案</summary>

**答案：(D)** 安全初始化只處理建立與發布這一段，不會保護之後對可變狀態的讀寫。

</details>

**Q8. 為什麼有些系統改用依賴注入，而不是讓類別自己呼叫 Singleton.getInstance()？**

- (B) 相依關係變得看得見，測試時也換得掉
- (C) 依賴注入會讓所有方法自動同步
- (D) 依賴注入保證整個 JVM 只有一個物件

<details><summary>看答案</summary>

**答案：(B)** 自己去拿單例會把相依藏起來；從建構子傳進來則讓依賴攤在簽章上，也方便換成測試用的假物件。

</details>
