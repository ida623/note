# 01. Claude Code 是什麼

> 🏠 **生活化版本**：每個段落開頭的「生活比喻」先用日常情境帶你抓到感覺，接著再看原本的技術說明與程式碼；篇末有「比喻對照表」可以快速複習。

### 讀完這課你會

*   說出會動手的 AI 助理跟純聊天的 AI 差在哪一步

*【先看問題】*

## 只會回話的模型，做不到「幫我讀檔案」

> 🏠 **生活比喻**
>
> 純聊天的模型像**電話那頭的顧問**：你說什麼他都能回，但他看不到你家，叫他「看看冰箱還剩什麼」他也無能為力。
> Claude Code 這類工具等於**把顧問請到你家**，還給他手和眼睛，能自己打開冰箱（讀檔案）、動手煮菜（改程式）。

大型語言模型（Large Language Model，簡稱 LLM，就是 ChatGPT、Claude 背後那種會接話的模型）只能根據送進去的文字產生回覆。舉個例子：你問「garden.jpg 裡有幾朵花？」，但送過去的只有這句話、沒有圖片內容，模型當然算不出來，只能回答它沒辦法讀那個檔案。

程式開發代理（Coding Agent，指的是夾在你和模型中間、會幫模型跑腿的那支程式）就是為了補上這一步。它在把你的話送給模型之前，先附上一份「你可以用這些工具」的清單，例如讀檔、搜尋程式碼、執行測試。模型挑了工具，代理程式負責真的去執行，再把結果送回模型。

```
你的要求
  ↓
代理程式附上任務內容與可用工具
  ↓
模型判斷下一步要做什麼
  ↓
代理程式執行工具，把結果送回
  ↓
模型根據新資訊繼續判斷，或給出答案
```

所以 Claude Code 的價值不只是「比較會寫程式」，而是能在你允許的權限與工具範圍內，反覆觀察、動手、再檢查。

*【引擎與底盤】*

## 同一顆模型，換一套框架就換一種表現

> 🏠 **生活比喻**
>
> 模型是**引擎**，代理程式是**整台車的底盤、方向盤和導航**。
> 同一顆引擎裝在跑車和貨車上，開起來完全不同；所以只比「用哪顆模型」不夠，還要看整台車怎麼設計。

可以這樣比喻：模型是引擎，代理程式是底盤、方向盤跟導航。就算裝同一顆引擎，操控方式、能走的路、安全限制不同，開起來就是不一樣。

> 實際表現 ≈ 模型能力 × 上下文品質 × 工具能力 × 流程安排

上下文（Context）指的是模型這一輪能看到的全部資訊——你打的字只是其中一小塊。框架決定模型看得到什麼、能用什麼，以及工具跑完之後怎麼接下去。差異可以拆成七層：

| 差異出在哪 | 影響什麼 |
| --- | --- |
| 系統提示（System Prompt，寫給模型的長期工作守則） | 角色、回覆風格、安全界線、什麼時候該問人 |
| 工具集合 | 模型能採取哪些行動；沒給的工具它根本看不到 |
| 工具規格（Schema，工具的名稱、參數與說明） | 模型判斷「這個情境該不該叫這個工具」的依據 |
| 自動塞進去的上下文 | 工作目錄、專案規則檔、開著的檔案、版本控制的差異、對話摘要 |
| 流程與迴圈控制 | 工具失敗要重試、換工具、問人，還是停下來 |
| 取樣參數 | 輸出的穩定度、多樣性與長度 |
| 模型版本與實驗功能 | 產品名稱一樣，實際對到的版本與啟用的功能可能不同 |

上面這張表是把模型固定住、只看框架層的差異；實務上各家工具不會剛好跑同一顆模型。所以拿兩個產品直接對比時，先分清楚差異是來自模型還是來自框架，也不要把某個模型名稱記死，版本更新得很快。

*【最容易忽略的一層】*

## 模型看到的，遠不只你打的那一句

> 🏠 **生活比喻**
>
> 像你請同事幫忙，他手上除了你這句話，還有**公司規章、交接筆記、之前的會議紀錄**。
> 這些你沒親口說的「背景資料」（上下文），往往比你那一句話更影響他怎麼做。

你輸入的提示只是上下文的一部分。代理程式還可能加上專案規則、工具說明、檔案片段和先前的執行結果。這些一起決定模型下一步做什麼。這一層因為看不到，常被忽略，影響卻可能比系統提示還大。

> 挑工具的時候不要只問「它用哪顆模型」，還要問「它怎麼取得上下文、給模型哪些工具、工具執行怎麼控管」。

工具也不是越多越好。太多或描述相近的工具會讓模型更難選；上下文塞太滿，真正重要的規則反而被淹沒。可靠的流程看重的是相關性，不是資訊總量。

*【資料邊界】*

## 跑在本機，不等於資料留在本機

> 🏠 **生活比喻**
>
> 像**請到府清潔的阿姨**：人在你家打掃，不代表她不會把東西帶回公司處理。
> - 先建索引上傳＝整間房子拍照寄回公司建檔
> - 用到才送檔案＝需要時才把某件衣服拿回去洗
> - 只送相關幾行＝只剪下一塊布料寄出去
>
> 所以要先問清楚：哪些東西會離開你家？

不同產品取得專案內容的方式不同：有的先整份建索引、有的用到才搜尋、有的只送出相關的幾行。例如這三種做法：

*   **先建索引再上傳**：把整份程式碼建立索引、送到雲端的機器上保存，之後靠這份索引回答問題。資料會離開本機。
*   **用到才送檔案**：以檔案為單位，需要時才把內容傳出去，範圍比整份程式碼小。
*   **用到才送幾行**：不預先建索引，等你送出要求的當下才搜尋，送到後端的是必要的那幾行程式碼。

這三種做法不必對應到特定產品：各家的實作隨版本變動，要判斷手上的工具屬於哪一種，得看它自己的文件。

不管介面開在哪裡，只要模型跑在遠端，送出去的提示、程式碼片段與工具結果就可能離開本機；實際情況要看部署方式、產品文件與公司的設定。

> 💡 動手前先確認四件事：它能讀哪些資料夾、哪些內容會送到遠端、哪些工具需要你核准、機密檔案有沒有被排除。

*【日常怎麼用】*

## 交代目標、看它改了什麼、跑測試

> 🏠 **生活比喻**
>
> 像**請裝潢師傅**：先說清楚要做什麼、哪些不能動，讓他看現場、提方案，動工後你驗收，敲牆之類的大動作要先問你。
> `CLAUDE.md`＝貼在門口的**施工須知**，每個進來的師傅都先看一遍。

一段可控的流程通常長這樣：先交代目標與限制，讓它去看相關檔案、提出做法、動手修改，最後執行測試並摘要結果；高風險的操作在執行前停下來讓你確認。幾個常用指令：

*   `/init`：初始化專案、建立 `CLAUDE.md`（放專案長期規則的檔案）。工作目錄與它上層的 `CLAUDE.md` 每次開新對話都會整份載入；放在子資料夾的那些則是等模型讀到該資料夾的檔案時才載入。
*   `/context`：看目前的上下文用量。
*   `/memory`：管理跨對話的記憶。它跟「每次都整份載入的 `CLAUDE.md`」不一樣：自動記憶的索引檔每次對話開頭只載入前 200 行或前 25KB（以先到的為準），超過的部分不在開頭載入，細節被拆到各自的主題檔，模型需要時才自己去讀。[出處](https://code.claude.com/docs/en/memory)
*   `/compact`：壓縮目前的對話上下文，把空間讓出來。
*   `ultrathink`：寫在提示裡的關鍵字，要求這一輪想得更深入。它的做法是在上下文裡加一段指示，送給模型的運算強度設定並不會改變；「think」「think hard」這類講法不算關鍵字，只會被當成普通文字。[出處](https://code.claude.com/docs/en/model-config)

指令名稱與行為會隨版本、方案與執行環境改變，用之前查一下當下版本的官方說明或內建的 `/help`。

| 技術名詞 | 生活比喻 |

| 代理程式 Agent | 把顧問請到家裡，給他手和眼 |

### 重點整理

*   模型負責判斷與生成，代理程式負責準備上下文、執行工具、控制流程；兩件事分開看。
*   同一顆模型放進不同框架，會因為系統提示、工具、自動塞入的上下文與流程安排而給出不同結果。
*   工具跟上下文不是越多越好，相關、清楚、可控才是重點。
*   介面跑在本機不代表資料不外傳，動手前先確認可讀範圍、外傳內容與核准方式。

- (A) 模型缺少判斷所需的上下文
- (B) 模型一定沒有看圖片的能力
- (C) 檔名不能包含句點
- (D) 問題必須先改寫成程式碼

**答案：(A)** 模型只能依照收到的內容判斷；代理程式可以用讀檔工具把缺的那塊補上。

**Q2. 模型說「我要用讀檔工具」之後，代理程式通常做什麼？**

- (A) 實際執行工具，再把結果送回模型
- (B) 永久改掉模型的參數
- (C) 跳過模型直接產生答案
- (D) 把整個專案公開到網路上

<details><summary>看答案</summary>

**答案：(A)** 代理程式負責真的去執行工具，模型再根據結果決定下一步。

</details>

**Q3. 「模型是引擎，代理程式是底盤」這個比喻要說明什麼？**

- (A) 模型相同時，上下文、工具與流程安排仍會讓表現不同
- (B) 只要模型相同，所有產品的輸出就會一致
- (C) 代理程式的功能只是換聊天介面的配色
- (D) 模型名稱比工具權限更值得看

<details><summary>看答案</summary>

**答案：(A)** 框架決定模型看到什麼、能用什麼、工具跑完之後怎麼接，這些都不是模型自己決定的。

</details>

**Q4. 下列哪一項是你沒有打、但代理程式可能自動加進上下文的？**

- (A) 目前的工作目錄與專案規則檔
- (B) 你從未授權的銀行密碼
- (C) 模型訓練資料的完整副本
- (D) 電腦上所有刪除過的檔案

<details><summary>看答案</summary>

**答案：(A)** 工作目錄、專案規則、開著的檔案狀態與對話摘要，都可能被自動附上。

</details>

**Q5. 兩套工具都提供讀檔功能，為什麼模型的使用方式還是可能不同？**

- (A) 工具的名稱、參數、說明與回傳格式可能不同
- (B) 只要用途相同就不可能有差別
- (C) 讀檔工具會自己訓練出新的模型
- (D) 工具規格只會影響畫面排版

<details><summary>看答案</summary>

**答案：(A)** 模型是靠工具的名稱與說明判斷該不該叫、參數怎麼填。

</details>

**Q6. 工具呼叫失敗後要重試、換工具還是問你，主要由哪一層決定？**

- (A) 代理程式的流程與迴圈控制
- (B) 模型的取樣參數
- (C) 工具回傳內容的字元編碼
- (D) 專案規則檔的檔名

<details><summary>看答案</summary>

**答案：(A)** 錯誤處理與停止條件屬於框架層的流程安排，不是模型自己決定的。

</details>

**Q7. 為什麼「代理程式跑在本機」不代表資料不會離開這台電腦？**

- (A) 提示、程式碼片段或工具結果仍可能送往遠端的模型
- (B) 本機程式一定會自動公開所有檔案
- (C) 只要開終端機就得連上公開網站
- (D) 所有模型都只能在瀏覽器裡運作

<details><summary>看答案</summary>

**答案：(A)** 資料會不會外傳取決於模型跑在哪裡、產品怎麼設計、公司怎麼設定，不能只看介面開在哪。

</details>

**Q8. 哪一種做法最能讓這類工具的流程變得可控？**

- (A) 交代目標與限制、檢查它改了什麼、用測試驗證結果
- (B) 一次把所有權限開好，結果也不看
- (C) 只指定模型名稱，不給任務背景
- (D) 工具失敗時讓它無限重試

<details><summary>看答案</summary>

**答案：(A)** 清楚的範圍、看得到的變更與可驗證的結果，能大幅降低誤解與誤操作。

</details>
