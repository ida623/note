## 平台、模型與文件各司其職

> 🏠 **生活比喻**
>
> 把 AWS 想成**出租的科技園區**：VPC 是園區、EC2 是辦公室、安全群組是門禁、IAM 角色是員工證、S3 是倉庫、Bedrock 是**外包的 AI 大腦**。
> Dify 則是辦公室裡的**客服中心系統**，把大腦、資料、流程串起來。

可以把 AWS 當成一座出租的科技園區：VPC 是園區、EC2 是辦公室、安全群組是門禁、角色是員工證、S3 是倉庫，Bedrock 則提供模型算力。這套架構不是把所有東西塞進同一台主機：

```
使用者
  ↓
EC2 上的 Dify
  ├─→ Amazon Bedrock：呼叫模型
  └─→ Amazon S3：讀取或保存文件
```

Dify 是一套開源的 AI 應用平台，可以接上不同家的模型、建知識庫、串工具、畫工作流，有雲端版也可以自己架。為什麼還要自己架一台？因為 Dify 要同時叫多家模型，就得管多把金鑰、多份帳單；改成在 EC2 上架 Dify、用機器的角色去呼叫 Bedrock，模型就跑在 AWS 自己的機房裡，認證走角色、帳單也統一在 AWS。

## 先設預算，再開資源

> 🏠 **生活比喻**
>
> 預算警示像**信用卡消費簡訊**：刷到某個金額就通知你，但**不會自動幫你停卡**。

AWS 多數服務按用量收費。預算警示像信用卡的消費通知：預估或實際支出碰到門檻時提醒你，但預設只會通知，不會自動把 EC2 關掉或停掉模型呼叫。

1.  進到帳務與成本管理介面。
2.  建立每月預算，設金額與收通知的人。
3.  依實驗規模設幾段門檻，例如到 50%、80%、100% 各通知一次。
4.  課程或實驗結束後，回頭檢查並停掉、刪掉不再用的資源。

初學者的預算可以抓每月 10 到 50 美元。實際費用受區域、開機時間、模型與流量影響，這個數字當參考就好。

> 預算警示是煙霧偵測器，不是自動灑水器。收到警示以後，還是要自己去看資源跟費用。

*【身分與授權】*

## 使用者身分給人，角色給服務

> 🏠 **生活比喻**
>
> - Root 使用者＝**公司保險箱的總鑰匙**，平常鎖起來不用。
> - IAM 使用者＝給**員工**的個人識別證。
> - IAM 角色＝給**機器**掛的臨時通行證，要用時才領。
> - MFA＝刷卡之外還要**按指紋**。

用信箱註冊出來的根使用者（Root user）像公司保險箱的總鑰匙，權限太大，不適合日常操作。日常操作要另外開一個權限受限的使用者身分、開啟多重要素驗證（MFA，登入時除了密碼再多驗一樣東西），並遵守最小權限原則（只給完成工作所需的權限）。IAM 的使用者、群組、角色與兩種政策，見〈AWS 全域架構與 IAM〉。

| 身分 | 主要用途 | 風險控制 |
| --- | --- | --- |
| 根使用者 | 少數只有它能做的帳號層級工作 | 避免日常使用，登入資訊要保護好 |
| 使用者身分（IAM User） | 人員登入與操作 | 只給工作需要的權限 |
| 角色（IAM Role） | 讓 EC2 這類服務取得暫時憑證 | 不必把長期金鑰寫進程式裡 |

做法是建一個信任 EC2 的角色，掛上存取 S3 與呼叫 Bedrock 的權限。這裡為了先跑通而掛了完整權限，正式環境應該縮到指定的資源與必要的動作——就像倉管只拿倉庫鑰匙，不該同時拿到財務室跟機房的鑰匙。

> EC2 能做什麼 ＝ 角色的信任關係允許 EC2 扮演它 ＋ 權限政策允許那些動作

## 用 S3 存客服資料

> 🏠 **生活比喻**
>
> S3 像**倉庫**，Bucket 是一間間**倉庫房**，每個檔案連同標籤（描述資訊）是一件**貨物**；整件存、整件取，不能只拿半件。

Amazon S3 是物件儲存服務（Object Storage，以整個檔案為單位存取，不像硬碟那樣切成區塊）。Bucket（儲存貯體）像倉庫，放進去的每個檔案連同它的描述資訊就是一個物件。適合放客服手冊、常見問答、表格資料或流程的暫存檔。S3 的物件、前綴、版本控制與儲存類別，見〈S3 儲存資源〉。

1.  建一個不會跟別人撞名的 Bucket。
2.  選一個跟主要工作負載相容的區域。
3.  維持「封鎖公開存取」，除非需求與風險都評估過了。
4.  上傳測試文件，記下 Bucket 名稱與物件路徑。

Bucket 名稱要在同一個分區（partition）內唯一，而不是真的全球唯一[出處](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html)——AWS 分成四個分區（一般區域、中國區域、美國政府雲、歐洲主權雲），名稱只在自己那一區共用命名空間。實務上你還是得挑個夠特別的名字。

> 📝 查證更正：原筆記寫「Bucket 名稱：必須全球唯一」，查證後更正

`us-east-2` 是美國東部（俄亥俄），不是美國西部[出處](https://docs.aws.amazon.com/general/latest/gr/rande.html)。挑區域時以主控台顯示的名稱，以及你要用的模型在哪些區域可用為準。

> 📝 查證更正：原筆記寫「區域：選擇 us-east-2（美國西部，Bedrock 支援較好）」，查證後更正

區域代號還有另一個容易出錯的地方，跟上面記錯地理位置是兩回事：同一套系統裡，不同服務各自要填一次區域，很容易填成不同的。例如文件上傳到 `us-east-2`，後面設定 Dify 連 Bedrock 時卻填了 `us-east-1`，資料跟模型就不在同一區了。實作時先決定要用哪一區，再逐項確認每個服務填的都是它。

*【網路與門禁】*

## VPC 決定道路，安全群組決定誰能進門

> 🏠 **生活比喻**
>
> - VPC＝**有圍牆的社區**；子網路＝社區裡的**分區**。
> - 路由表＝**路標**，網際網路閘道＝**社區大門**。
> - 安全群組＝每棟房子的**門禁**，決定誰能進門。

虛擬私有雲（Virtual Private Cloud，VPC）是一塊隔離出來的網路範圍；子網路切分資源的位置、路由表決定封包往哪走、網際網路閘道讓符合條件的資源跟外網往來。這個實驗建了兩個公有子網路、讓 EC2 拿得到公有 IP，這是為了示範方便，不等於正式環境的好架構——正式環境通常還要評估私有子網路、負載平衡器、受管憑證與維運入口。下面這張連接埠表就是安全群組（Security Group）的規則：它是跟著網卡（ENI）走的虛擬防火牆規則，不是裝在主機作業系統裡的防火牆。VPC、子網路、路由表與安全群組的完整說明見〈VPC 網路架構〉。

| 連接埠 | 用途 | 實驗時的安全重點 |
| --- | --- | --- |
| 22 | SSH 管理 | 限制可信來源，不用時關掉 |
| 80 | HTTP | 內容沒加密，測完就可以移除 |
| 443 | HTTPS | 仍要把憑證與應用程式設定正確 |

把來源設成 `0.0.0.0/0` 代表所有 IPv4 位址都可以嘗試連線。這不代表誰都能登入，但攻擊面確實變大了，正式環境應該限制來源。

*【租一台電腦】*

## 軟體決定硬體

> 🏠 **生活比喻**
>
> EC2 是**租來的電腦**。先想好要做什麼（Dify 要多少記憶體），再挑房子大小，就像先知道家裡幾個人再決定租幾房。
> t 系列像**平常省電、需要時能衝刺的車**，但衝刺額度用完就會變慢。

EC2 執行個體就是租來的雲端電腦。順序是先確認 Dify、容器與預估流量需要多少運算、記憶體跟磁碟，再挑規格。下面是一般說法跟 AWS 術語的對照：

| 一般用語 | AWS 術語 | 作用 |
| --- | --- | --- |
| 虛擬電腦 | EC2 Instance | 執行作業系統與 Dify |
| 系統映像 | AMI | 建立主機用的作業系統範本 |
| 網路卡 | ENI | 接上 VPC 網路 |
| 防火牆 | Security Group | 控制允許進出的流量 |
| 硬碟 | EBS | 保存主機的區塊資料 |
| 標籤 | Tag | 分類、查找與成本管理 |

這個實驗用 Amazon Linux 2023 這個系統映像、選 t3.large 這個規格（t 系列是突發效能型：平常效能普通，有流量時衝上去），並在開機腳本裡裝好容器環境、抓 Dify 的 1.8.1 版啟動。規格需求、安裝指令與軟體版本都會持續變，照做之前先看官方文件確認目前的版本。

```
# 概念流程，執行前依官方文件確認目前版本與指令
安裝容器執行環境
取得指定且經審核過的 Dify 版本
設定環境變數與持久化儲存
啟動服務
檢查容器狀態與應用程式日誌
```

*【權限實驗】*

## 用一次失敗跟一次成功證明角色有效

> 🏠 **生活比喻**
>
> 像**員工證測試**：沒掛證刷門 → 被擋；掛上證再刷 → 開門。同一個人同一扇門，差別只有證件，證明權限來自證件而不是偷藏的鑰匙。

這個對照很值得自己跑一次：先在還沒掛角色的 EC2 上執行列出 Bucket 的指令，看它授權失敗；再把允許存取 S3 的角色掛上去，重跑同一條指令。

```
aws s3 ls
```

同一台機器、同一條指令，只因為角色變了就有不同結果——這就證明權限來自角色，不是偷偷寫在主機裡的金鑰。如果還是失敗，依序檢查角色有沒有掛到正確的執行個體、信任關係、權限政策、Bucket 本身的政策、區域，以及組織層級的限制。另外，看得到所有 Bucket 不是理想終點；正式環境通常只該看得到指定的那一個。

*【接上模型】*

## Bedrock 出算力，EC2 出平台

> 🏠 **生活比喻**
>
> EC2 上裝好 Dify，就像**蓋好客服中心但還沒請專家**。Bedrock 是**按件計酬的外包專家**，客服中心用員工證（角色）打電話過去請他回答。

EC2 上架好 Dify 不會因此就有模型算力：EC2 只建好了平台，沒有 AI 算力。Amazon Bedrock 是 AWS 的受管模型服務，模型託管在 AWS 機房裡，按用量計費、不用自己管顯示卡或部署模型；Dify 則利用 EC2 的角色取得授權，把推論請求送過去。

1.  確認目標區域有你要的模型與推論方式。
2.  在模型存取頁面完成申請或必要的使用資格設定。
3.  先在測試介面驗證模型會不會回話。
4.  在 Dify 新增 Bedrock 這個模型供應商，區域填成同一個。
5.  用簡單的提示測連線，再開始建客服應用。

這個實驗申請的是 Claude 3、Llama 3 與 Mistral 三個系列。可用的模型清單、存取流程與計費方式會隨時間改變，以主控台顯示的為準。

提示可以用固定結構寫，把角色、任務、輸入、限制與輸出格式交代清楚：

```
角色：你是專業的客服人員。
任務：根據提供的知識內容回答問題。
限制：找不到依據時明說不確定，不要自己補。
輸出：先給結論，再列出使用者可以採取的下一步。
```

提示寫法還有幾種：不給範例直接下任務、給幾個範例示範格式、引導模型一步一步推理、把任務拆成固定欄位的範本、以及指定角色再交辦。都是常見做法，可以照任務性質混用。

*【自動化與收尾】*

## 範本能重建環境，但取代不了審查

> 🏠 **生活比喻**
>
> CloudFormation 範本像**建築藍圖**：照著藍圖可以一次把整個園區蓋好，拆掉也能照圖重蓋；但開工前還是要先審圖。
> 實驗完記得**退租**，不然房租會一直扣。

CloudFormation 範本像建築藍圖（也就是把基礎設施寫成程式碼）：一份檔案描述 VPC、EC2、S3 與相關設定，一次建起來，環境要重來也容易。匯入之前還是要看區域、權限、映像、規格，以及會不會產生費用。

實驗做完，先確認哪些資料要留，再停掉或移除 EC2、沒在用的儲存、網路元件與其他會計費的資源。刪除整組範本之前，也要確認範本的刪除政策會不會把資料一起帶走。

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| VPC / 子網路 | 有圍牆的社區 / 分區 |
| EC2 | 租來的辦公室電腦 |
| 安全群組 | 每棟房子的門禁 |
| IAM 使用者 / 角色 | 員工識別證 / 機器的臨時通行證 |
| S3 Bucket | 倉庫房 |
| Bedrock | 按件計酬的外包 AI 專家 |
| CloudFormation | 建築藍圖 |
| 預算警示 | 信用卡消費簡訊 |

### 重點整理

*   先用預算警示顧成本，但它只負責通知，不會自動停機。
*   人用使用者身分、服務用角色；角色讓機器拿到暫時憑證，不必把金鑰寫死在程式裡。
*   VPC 決定網路範圍，安全群組決定誰能連進來；來源開成全部等於把攻擊面放到最大。
*   EC2 跑平台、S3 存文件、Bedrock 出模型算力，三者分工不要混。
*   同一條指令在掛角色前後結果不同，就是權限設定有效的證據。

**Q6. S3 Bucket 名稱的唯一性要求是什麼？**

- (A) 在同一個分區內唯一，分區是一群 AWS 區域的集合
- (B) 在自己的帳號內唯一就好
- (C) 在同一個區域內唯一就好
