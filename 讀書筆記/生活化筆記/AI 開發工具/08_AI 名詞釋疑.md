## 使用者提示與系統提示

> 🏠 **生活比喻**
>
> 像**演員拍戲**：
> - 系統提示＝導演事先給的**角色設定**（「你是溫柔的女朋友」）
> - 使用者提示＝對手演員這一場**說的台詞**（「我肚子痛」）
>
> 設定和台詞分開放，演員才不會把兩者搞混。

舉個例子：你跟 AI 說「我肚子疼」，它通常回一些沒營養的話；你想要它有個人設，最直接的辦法是把「你是我的女朋友」塞進你的提示裡。這招有效，但那句話其實不是你這次真正想說的內容，所以人們把人設抽出來，放進另一個地方。

*   **使用者提示（User Prompt）**：你這一次真正要問的問題或要交辦的任務。
*   **系統提示（System Prompt）**：工作守則：角色、個性、背景知識、語氣、行為限制與輸出要求。每次你送出訊息時，它會被一起送給模型。

```
系統提示：你是課程助教，用繁體中文回答，先說結論。
使用者提示：請比較代理人跟聊天機器人的差別。
```

不過提示寫得再完美，模型說到底還是在產生內容。你問問題，它最多給你答案、告訴你怎麼做，真正動手的還是你。要讀檔、查服務或改東西，就得靠代理人跟工具把文字上的意圖變成實際動作。

*【從回答到行動】*

## 代理人與它的工具

> 🏠 **生活比喻**
>
> 代理人像**秘書**：在老闆（使用者）、顧問（模型）和各種辦公設備（工具）之間跑腿傳話。
> `read_file`、`list_files` 就是秘書會用的**影印機、檔案櫃**。

AI 代理人（AI Agent）是負責在使用者、模型跟工具之間協調的那支程式，講白話一點，就是在模型、工具跟使用者之間傳話的那支程式。

它的工具（Agent Tool）則是一個個具體的能力，例如：

*   `list_files`：列出目錄內容。
*   `read_file`：讀取指定檔案。
*   `web_browse`：取得網頁資訊。

> 工作迴圈：理解任務 → 選工具 → 執行 → 看結果 → 決定下一步

這個迴圈會重複很多次，直到任務完成、碰到停止條件，或需要你補資訊、給授權為止。

這種讓模型自己跑迴圈的做法，早期常被拿來當例子的是 AutoGPT：2023 年 3 月 30 日由 Toran Bruce Richards 發布，是最早讓一般人用得到、能展示 GPT-4 自主能力的應用之一。[出處](https://en.wikipedia.org/wiki/AutoGPT)

*【把工具呼叫變結構化】*

## 函式呼叫解決了什麼

> 🏠 **生活比喻**
>
> 以前像叫顧問**手寫申請單**，常常漏欄位、寫錯字，秘書看不懂只好退件重寫。
> 函式呼叫＝改成**電子表單**，欄位、格式都固定，填錯系統直接擋下。

早期的做法是在系統提示裡用自然語言描述工具，並要求模型照某個文字格式回答。問題在於模型本質上是機率模型，還是可能少個括號、拼錯工具名稱，讓代理人解析不了。很多代理人只好在發現格式不對時自動重試——既耗費用，又讓人覺得不可靠。

函式呼叫（Function Calling）就是為了這件事出現的：把工具的名稱、用途與參數整理成機器比較好驗證的結構，模型要用工具時，也產生結構化的呼叫要求。

```
{
  "name": "read_file",
  "description": "讀取指定的文字檔",
  "parameters": { "path": "string" }
}
```

它改善的是介面與格式，不代表模型挑的工具一定對，也不會自動給出工具權限。代理人仍然要驗參數、處理錯誤、控制可執行的範圍。

早年各家大廠的介面定義都不一樣，很多開源模型也還不支援，要寫一個跨模型通用的代理人相當麻煩。主流模型多數已支援函式呼叫，MCP 出現後生態也在收斂，但各家的細節仍有差異，實作前還是要看你要用的那家怎麼定義。

*【兩個常被混在一起的名詞】*

## 一個管模型怎麼挑工具，一個管代理人怎麼接服務

> 🏠 **生活比喻**
>
> - 函式呼叫＝**顧問和秘書之間**的溝通格式（要用哪個工具）。
> - MCP＝**秘書和外面廠商之間**的溝通格式（怎麼請廠商執行）。
>
> 一個管對內、一個管對外，可以搭配但不是同一件事。

| 概念 | 溝通的是哪兩邊 | 解決什麼問題 |
| --- | --- | --- |
| 系統提示 | 應用程式 ↔ 模型 | 用自然語言設定角色、規則與行為 |
| 函式呼叫 | 模型 ↔ 代理人 | 結構化描述工具，以及模型提出呼叫的格式 |
| MCP | 主機／用戶端 ↔ 外部伺服器 | 找得到並用得到外部的工具、資源與提示範本 |

代理人可以先透過 MCP 跟伺服器拿到工具說明，再轉成模型支援的函式呼叫格式；模型提出呼叫之後，代理人再透過 MCP 請伺服器去執行。兩者可以合作，但不是同一件事。

```
MCP 伺服器提供工具資訊
        ↓
代理人轉成模型看得懂的工具定義
        ↓
模型產生一個函式呼叫
        ↓
代理人透過 MCP 請伺服器執行
        ↓
工具結果回到模型
```

*【MCP 在做什麼】*

## 把工具變成共用的服務

> 🏠 **生活比喻**
>
> 像**社區共用的洗衣間**：不用每戶都買一台洗衣機，大家都去同一間用；MCP 就是洗衣間的使用規則。

MCP 出現的動機是這樣：有些工具其實是通用的，例如「瀏覽網頁」，很多代理人都要。總不能在每個代理人裡都複製一份相同的程式碼。於是大家把工具變成一種服務、統一託管，讓所有代理人都來呼叫。

MCP 規定了伺服器跟用戶端怎麼溝通、伺服器要提供哪些共通介面（例如查詢有哪些工具、每個工具的說明、需要什麼參數與格式）。除了可執行的工具，伺服器也能直接提供資料（Resource）或提示範本（Prompt）。

伺服器可以跟代理人跑在同一台機器上、用標準輸入輸出溝通，也可以部署到網路上、透過 HTTP 溝通；現行規格定義的兩種標準傳輸就是這兩條——標準輸入輸出與 Streamable HTTP。

上面講的是伺服器提供給用戶端的三種能力，現行規格另有反方向的：取樣（伺服器請主機用模型生成內容）、Roots（伺服器問清楚可以在哪些路徑或網址範圍內作業）、Elicitation（伺服器中途向使用者要一項補充資訊）。其中取樣與 Roots 已在 2026-07-28 版標為棄用（deprecated），新的實作不該再採用，最快會在 2027-07-28 之後的版本移除。詳見 [MCP 規格](https://modelcontextprotocol.io/specification/2026-07-28)與[棄用功能清單](https://modelcontextprotocol.io/specification/2026-07-28/deprecated)。

還有一件很容易誤解的事：MCP 雖然是為了模型而訂的標準，本身卻跟模型沒有關係。它不管代理人用哪一顆模型，只負責幫代理人管理工具、資源跟提示範本。

*【需要時再翻資料】*

## 檢索增強生成怎麼運作

> 🏠 **生活比喻**
>
> RAG 像**開卷考試**：先把課本切成小段做好索引，考試時翻到相關頁，再根據那幾頁作答。
> 常見問題是書切得太碎、翻錯頁。

檢索增強生成（Retrieval-Augmented Generation，簡稱 RAG）像開卷考試：先把文件切成片段，轉成可以比較語意的向量，使用者提問時再找出相關片段交給模型回答。

```
文件 → 切割 → 轉成向量 → 存進向量資料庫
問題 → 語意檢索 → 相關片段 → 模型 → 回答
```

它的優點是能很快用上大量既有文件，也比較容易附上是從哪裡查到的；常見問題則是切得不好、找錯片段、該找到的沒找到，以及片段缺少前後文。

*【另一條路】*

## 先把資料整理成知識地圖

> 🏠 **生活比喻**
>
> RAG 是考試時才翻書；這種做法是**考前先整理好一本重點筆記**，有章節、有目錄、有互相連結，人和 AI 都能直接讀。

另一種對照的做法是：不要等提問時才去撈片段，而是先請模型把散落的資料整理成有章節、有連結、有索引的百科頁面，之後人可以直接讀，問答系統也可以拿來用。這種做法可以用 Obsidian（一套以 Markdown 檔案與雙向連結為主的筆記軟體）承載頁面，模型則協助分類、摘要與產草稿；內容仍要人工核對與維護。

| 比較項目 | 檢索增強生成 | 先整理成百科 |
| --- | --- | --- |
| 核心做法 | 提問時才檢索相關片段 | 預先整理成主題頁面與概念連結 |
| 使用方式 | 適合直接問答與文件搜尋 | 適合瀏覽、教學與建立知識全貌 |
| 上下文 | 可能只撈回局部片段，缺前後文 | 同一主題已整合，比較留得住脈絡 |
| 知識關聯 | 片段之間通常沒有明確關係 | 可用連結、標籤或圖譜呈現概念關係 |
| 維護 | 文件更新後重新切割並重建索引 | 同步更新頁面、摘要、連結與版本 |
| 主要風險 | 檢索錯誤、該找到的沒找到 | 摘要失真、內容過時、來源遺失 |

兩者不互斥。整理好的頁面提供適合閱讀的結構，再用檢索從頁面與原始文件裡撈出相關內容。不論用哪一種，都要留下來源連結、更新日期與人工審核紀錄。

*【放回同一張地圖】*

## 一個完整任務怎麼串起來

> 🏠 **生活比喻**
>
> 整件事像**秘書幫老闆訂餐廳**：老闆說需求（使用者提示）→ 秘書照公司規定（系統提示）問顧問（模型）→ 顧問填好電子表單要查訂位系統（函式呼叫）→ 秘書透過共用服務去查（MCP）→ 結果回報老闆。

```
系統提示：規定代理人的角色與界線
使用者提示：提出這次的任務
代理人：安排步驟，協調模型與工具
函式呼叫：讓模型用結構化的方式挑工具
MCP：連接外部的工具、資源或提示範本
檢索或整理好的知識：提供任務需要的內容
工具結果：回到模型，形成下一步或最終答案
```

> 💡 判斷技巧：先問「這個名詞在解決哪兩個元件之間的問題？」比背定義好用得多，也比較不會把代理人、函式呼叫跟 MCP 混在一起。

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| 系統提示 / 使用者提示 | 導演的角色設定 / 這場台詞 |
| AI Agent | 跑腿傳話的秘書 |
| Function Calling | 固定欄位的電子表單 |
| MCP | 秘書對外找廠商的規則 |
| RAG | 開卷考試 |
| 知識地圖 | 考前整理好的重點筆記 |

### 重點整理

*   系統提示管長期的角色與規則，使用者提示表達這一次的任務。
*   代理人負責協調，工具負責執行；模型不等於代理人。
*   函式呼叫處理的是模型與工具呼叫的格式，MCP 處理的是主機與外部服務的連接。
*   檢索增強生成偏向即時撈片段，先整理成百科偏向預先建結構，兩者可以搭配。
*   模型產生的摘要、詞條與連結都要留來源，並定期回頭核對。
