## 準備工具與版本

> 🏠 **生活比喻**
>
> 像**開始做菜前先備好廚具**：Node.js 是**爐子**、npm 是**採購員**、Git 是**食譜的版本紀錄本**、VS Code 是**砧板和刀**。
> 版本相容就像**新款鍋子要配特定規格的爐子**，太舊的爐子（Node 16）帶不動新鍋（Angular 17+）。

需要 Node.js、隨附的套件管理工具 npm、Git，以及支援 TypeScript 的編輯器（VS Code 加 Angular Language Service 擴充是常見組合）。Node.js 的版本要看目標 Angular 版本的相容性表，每個大版本的門檻都不同：例如 Angular 17 要求 `^18.13.0 || ^20.9.0`，Angular 22 要求 `^22.22.3 || ^24.15.0 || ^26.0.0`，「16+」已經低於任何現行版本的門檻[出處](https://angular.dev/reference/versions)。

> 📝 查證更正：原筆記寫「檢查 Node.js 版本（建議 16+ 版本）」，查證後更正：Angular 17 就要求 Node 18.13 以上，16 帶不動

```
node -v
npm -v
git --version
```

*【建立與執行】*

## 用 CLI 建立 standalone 專案

> 🏠 **生活比喻**
>
> - `npx`＝**現場租最新款的工具機**，而不是用家裡放很久的舊款（全域安裝的版本）。
> - `npm run start -- --open`＝**透過總機轉話**時要先說「請轉告他：」（`--`），不然總機會把話吞掉。
> - `--host 0.0.0.0`＝**把家門打開讓整條街的人都能進來**，只在信得過鄰居時這樣做。

```
npx @angular/cli new notes-app
cd notes-app
npm start
```

`npx` 會直接執行指定版本的 CLI，避免「全域裝的版本」和「專案要的版本」不一致。已全域安裝 Angular CLI 的話，`ng new`、`ng serve` 也一樣能用。開發伺服器常用參數：

寫成 `npm run start --open` 是常見的踩雷：那樣參數不會傳進 ng serve。透過 npm script 轉手時要多一個雙連字號：`npm run start -- --open`，或像下面直接用 ng 指令。

```
ng serve --open        # 啟動後自動開瀏覽器
ng serve --port 8888   # 換連接埠
ng serve --host 0.0.0.0  # 讓同網路的其他裝置連入
```

綁 `0.0.0.0` 等於向整個區域網路開放開發伺服器，只在確有需要（例如給後端同事連）且網路可信時使用。

*【接手既有專案】*

## 先照 lockfile 安裝相依套件

> 🏠 **生活比喻**
>
> `package-lock.json` 像一份**精確到克數和品牌的食譜**。
> - `npm ci`＝**一字不差照食譜做**，保證跟大家做出同樣的菜（接手專案時用）。
> - `npm install`＝可以加料、換牌子，順便**更新食譜**（日常開發時用）。

```
git clone <repository-url>
cd <project-directory>
npm ci
npm start
```

lockfile（`package-lock.json`，記錄每個套件確切版本的鎖定檔）同步且可信時，乾淨安裝優先用 `npm ci`——照鎖定檔一字不差地重現；日常新增或調整套件才用 `npm install`。

## 從需求找到 Angular 工具

> 🏠 **生活比喻**
>
> 這張表像**工具箱的索引**：要切菜拿刀、要煮湯拿鍋。
> - **樣板驅動表單**＝**便條紙點餐**，簡單快速。
> - **響應式表單**＝**正式的點餐系統**，欄位多、規則嚴時更好管理和檢查。

| 需求 | 常用工具 |
| --- | --- |
| 拆分畫面 | standalone 元件、Input、Output |
| 切換頁面 | Router、routerLink、router-outlet |
| 呼叫 API | `provideHttpClient()`、HttpClient、Observable（RxJS 的資料流物件，值會陸續送來、要訂閱才拿得到） |
| 簡單表單 | FormsModule、ngModel（樣板驅動表單） |
| 複雜表單 | 響應式表單（Reactive Forms）＋驗證器 |
| 共用邏輯 | Service、依賴注入 |
| 顯示轉換 | Pipe |

```
bootstrapApplication(AppComponent, {
  providers: [
    provideRouter(routes),
    provideHttpClient()
  ]
});
```

樣板驅動表單直接在 HTML 上用 `ngModel` 疊，欄位少最快；響應式表單在 TypeScript 裡明確建立結構與驗證器，欄位多、驗證嚴的表單好測試也好維護。

## 完成不等於畫面能動

> 🏠 **生活比喻**
>
> 像**交屋前的驗屋**，房子看起來能住不代表合格：
> - `ng build`＝**結構安檢**；`ng test`＝**水電測試**。
> - 延遲載入（`loadComponent`）＝**家具分批送**，不用第一天就把所有東西塞進門。
> - 前端驗證只是**前門保全**，有人會從後門（直接打 API）進來，所以後端也要鎖。
> - `ng build --prod`＝**過期的通行證**，現在拿出來會被擋。
> - `ng lint` 要先**請驗屋師**（`ng add` 安裝 lint 工具）才驗得了。

*   用 `ng build` 驗證正式建置能過。
*   跑專案設定的測試指令（預設 `ng test`）。
*   大型功能用路由層級的延遲載入（`loadComponent`），第一次載入的程式檔不必包含整個應用程式。
*   清單用穩定的 `track` 值。
*   驗證輸入並使用 HTTPS；前端驗證擋不住直接打 API 的人，後端驗證不能省。

舊版 CLI 的 `ng build --prod` 已經不能用：這個參數在 CLI v12 棄用、v14 移除，現代 CLI 的 `ng build` 預設就是正式組態，要指定時用 `ng build --configuration production`[v12 棄用](https://github.com/angular/angular-cli/releases/tag/v12.0.0)[v14 移除](https://github.com/angular/angular-cli/releases/tag/14.0.0)。

> 📝 查證更正：原筆記的常用指令表寫「ng build --prod」，查證後更正：--prod 於 CLI v12 棄用、v14 移除，現在會報 Unknown argument

`ng lint` 有個前提：新專案預設沒有安裝 lint（程式碼風格與常見錯誤的靜態檢查）工具，要先用 `ng add` 加上 angular-eslint 這類套件才有得跑[出處](https://angular.dev/cli/lint)。

### 重點整理

*   Node.js 沒有一個「Angular 通用」的最低版本：各版本的下限不同，以官方相容性表為準，例如 17.x 是 18.13、22.x 是 22.22。
*   新專案用 `npx @angular/cli new`；接手專案乾淨安裝用 `npm ci`。
*   API 用 `provideHttpClient()`、路由用 `provideRouter(routes)` 在應用程式層明確提供。
*   簡單表單用 ngModel、複雜表單用響應式表單。
*   `ng build --prod` 已移除；交付前至少過正式建置與測試。

- (B) 記住「18.13 以上」就好，Angular 17 之後都適用
- (C) 裝最新版 Node.js 一定相容
- (D) Node 版本只影響編輯器提示，不影響建置

<details><summary>看答案</summary>

**答案：(A)** Node 版本是硬性相容性要求，門檻逐版本上調（17.x 要 18.13、22.x 要 22.22），記一個數字遲早過期；最新版 Node 也可能還沒被支援。

**Q2. 用 npx @angular/cli new 建專案的好處是什麼？**

- (A) 執行指定版本的 CLI，避免全域版本與專案需求不一致
- (B) 跳過 npm 相依安裝，加快建立速度
- (C) 自動附帶後端 API 範本
- (D) 讓專案不需要 package.json

<details><summary>看答案</summary>

**答案：(A)** npx 臨時抓對版本來執行；相依安裝照常，也不會生出後端。

</details>

**Q3. 接手既有專案、lockfile 同步可信時，乾淨安裝優先用什麼？**

- (A) npm ci
- (B) npm install --force
- (C) npm update 全部升到最新
- (D) 手動逐一安裝 package.json 列的套件

<details><summary>看答案</summary>

**答案：(A)** npm ci 照 lockfile 一字不差重現；update 與 --force 反而會改變版本。

</details>

**Q4. standalone 應用程式要讓 HttpClient 可注入，常用什麼設定？**

- (B) 把 HttpClient 加進元件的 declarations

<details><summary>看答案</summary>

</details>

**Q5. 欄位多、驗證嚴的表單，通常適合哪種做法？**

- (A) 響應式表單：在 TypeScript 明確建立結構與驗證器
- (B) 樣板驅動表單：全部疊在 HTML 的 ngModel 上
- (C) 不用表單模組，手動監聽每個 input 事件
- (D) 把驗證全部留給後端就好

<details><summary>看答案</summary>

**答案：(A)** 響應式表單好測試好維護；後端驗證必要但不該是唯一防線。

</details>

**Q6. 關於 ng build --prod，哪個敘述正確？**

- (A) 已於 CLI v12 棄用、v14 移除，現在 ng build 預設就是正式組態
- (B) 它仍是唯一能產生正式建置的指令
- (C) 它只在 NgModule 專案可用
- (D) 它等同於 ng serve --open

<details><summary>看答案</summary>

**答案：(A)** 現代 CLI 用 ng build（預設 production）或 --configuration 指定組態，--prod 會報 Unknown argument。

</details>

**Q7. 「前端驗證不能取代後端驗證」的原因是什麼？**

- (A) 使用者可以繞過前端直接對 API 發請求
- (B) 前端驗證會拖慢頁面載入
- (C) 後端驗證的錯誤訊息比較好看
- (D) HTTPS 已經取代了前端驗證

<details><summary>看答案</summary>

**答案：(A)** 前端驗證是體驗優化；任何人都能用工具直接打 API，把關必須在伺服器端。

</details>

**Q8. 路由層級的延遲載入（loadComponent）解決什麼問題？**

- (A) 首次載入不必揹整個應用程式的程式碼，進到該路由才下載
- (B) 讓路由比對從先到先得改成最長路徑優先
- (C) 把元件樣式延後到互動時才套用
- (D) 避免使用者直接輸入網址進入頁面

<details><summary>看答案</summary>

**答案：(A)** 延遲載入讓第一次載入的程式檔變小、加快初次載入；比對規則與樣式都不因此改變。

</details>
