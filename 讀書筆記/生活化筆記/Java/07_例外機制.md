## 例外把失敗路徑從正常流程裡拉出來

> 🏠 **生活比喻**
>
> 例外像**緊急逃生路線**：平常照正常動線走，出事時直接走逃生梯，不用在每個房間都寫「如果失火怎麼辦」。

程式遇到照原計畫走不下去的狀況——檔案不存在、資料格式錯、索引越界、資料庫連不上——就產生並拋出一個例外物件。這個機制像建築物的緊急動線：平常走正常通道，出事才轉到處理失敗的那條路。這樣分的好處很實在：**正常流程跟錯誤處理分開寫，程式好讀多了**，不用到處塞 `if...else` 自己檢查。

所有能被拋出的東西都繼承 `Throwable`，底下分兩支：

| 類別 | 意思 | 一般怎麼處理 |
|---|---|---|
| **`Error`** | JVM 或執行環境層級的嚴重問題，例如記憶體爆了 | 不寫程式去救，救了也沒用 |
| **受檢例外<br>（checked）** | `Exception` 裡不屬於 `RuntimeException` 的那些 | **編譯器強迫**你捕捉或宣告拋出 |
| **非受檢例外<br>（unchecked）** | `RuntimeException` 及其子類別 | 不強迫處理，靠修邏輯或先驗證輸入來預防 |

受檢例外的代表是 `IOException`、`SQLException`；非受檢的常客是 `NullPointerException`、`IllegalArgumentException`、`NumberFormatException`、`ClassCastException`、`IndexOutOfBoundsException`。後者為什麼不強迫處理？因為**這些狀況本來就該由程式設計者在寫的時候避開**。

*【捕捉失敗】*

## try 放有風險的操作，catch 接你懂的例外

> 🏠 **生活比喻**
>
> - `try`＝**做有風險的事**（像煮油炸）
> - `catch`＝**旁邊準備好的滅火器**，只接你知道怎麼處理的那種火

```java
try {
    int port = Integer.parseInt(input);
    connect(port);
} catch (NumberFormatException e) {
    System.err.println("連接埠必須是整數：" + e.getMessage());
} catch (ConnectionException e) {
    System.err.println("連線失敗：" + e.getMessage());
}
```

變數 `e` 指向被接住的那個例外物件，可以用 `getMessage()` 取訊息，或 `printStackTrace()` 看呼叫堆疊。

> 💡 **多個 `catch` 要「先具體、後一般」——出事了兒子先擋**

如果先寫 `catch (Exception e)`，後面那些特定例外的區塊永遠到不了，編譯器會直接拒絕。

> 不要為了讓程式看起來沒壞就寫一個空的 `catch`。當下沒辦法合理復原時，該做的是保留原因、補上情境後重新拋出，或交給上層統一處理。

## finally 與 try-with-resources

> 🏠 **生活比喻**
>
> - `finally`＝**不管成功失敗，最後都要關瓦斯**
> - try-with-resources＝**自動關瓦斯的爐子**，用完自動關，不怕忘記

`finally` 放在所有 `catch` 後面，不管成功失敗都會跑，所以拿來釋放資源——關資料庫連線、關檔案。

**「無論發生什麼情況」要加一個但書：例外有沒有被處理，`finally` 都會跑沒錯；但如果在 `try` 裡呼叫了 `System.exit()`，或整個 JVM 被強制砍掉，`finally` 就不會執行。準確的範圍是：try 或 catch 還在執行時 JVM 就結束了，finally 區塊可能不會執行** [[出處]](https://docs.oracle.com/javase/tutorial/essential/exceptions/finally.html)。

> 📝 原筆記更正：原筆記寫「finally { } 是無論發生什麼情況皆會執行的程式區塊」，查證後補上界線：呼叫 System.exit() 或 JVM 被強制結束時，finally 不會執行

關資源除了 `try-catch-finally`，還有更省事的 **try-with-resources**。這是 Java 7 就有的語法：只要資源實作了 `AutoCloseable`，區塊結束時會自動關閉，而且會妥善保留「主要例外」與關閉時產生的受抑制例外 [[出處]](https://docs.oracle.com/javase/tutorial/essential/exceptions/tryResourceClose.html)。

```java
// 舊寫法：自己在 finally 裡關
Connection connection = null;
try {
    connection = openConnection();
    runQuery(connection);
} catch (DatabaseException e) {
    System.err.println(e.getMessage());
} finally {
    if (connection != null) {
        connection.close();
    }
}

// 現在的寫法：括號裡宣告資源，區塊結束自動關
try (BufferedReader reader = Files.newBufferedReader(path)) {
    System.out.println(reader.readLine());
} catch (IOException e) {
    System.err.println("讀取失敗：" + e.getMessage());
}
```

> **把參考變數設成 `null` **不等於**關閉資源，而且 `null` 只能指定給參考型別——`int` 這種基本型別設成 `null` 會直接編譯失敗。真要自己收尾，順序是先 `close()` 再把變數設成 `null`** [[出處]](https://docs.oracle.com/javase/specs/jls/se21/html/jls-4.html#jls-4.1)；不過改用 try-with-resources 之後，這件事根本不必自己做。
>
> 📝 原筆記更正：原筆記（Java 2 札記「釋放資源」）建議「先呼叫close()，再將該物件設為空值(null)」，附的程式碼是 int a = scanner(System.in); ... a = null;——這段用 JDK 21 編譯會報 incompatible types: <null> cannot be converted to int，因為 int 是基本型別，null 只能給參考型別；查證後更正

## throw 是真的丟，throws 是先聲明可能會丟

> 🏠 **生活比喻**
>
> - `throw`＝**真的大喊「失火了！」**
> - `throws`＝**門口貼告示「本房間可能失火」**，提醒呼叫的人要準備滅火器

| 關鍵字 | 寫在哪 | 作用 |
|---|---|---|
| **`throw`** | 方法主體內 | 丟出一個 `Throwable` 物件 |
| **`throws`** | 方法宣告後面 | 聲明這個方法可能把哪些例外交給呼叫端 |

```java
static void withdraw(int amount) throws InsufficientFundsException {
    if (amount < 0) {
        throw new IllegalArgumentException("金額不可小於 0");
    }
    if (amount > balance) {
        throw new InsufficientFundsException("餘額不足");
    }
}
```

`throws` 不代表例外一定會發生，也不代表已經處理好了——它只是把責任交給呼叫端。呼叫一個會丟受檢例外的方法時，呼叫端只有兩條路：用 `try-catch` 接（又叫「明確處理」），或在自己的宣告上繼續 `throws`（又叫「消極處理」）。一路推到最後沒人接，就是 JVM 幫你印錯誤然後結束。

## 多重捕捉

> 🏠 **生活比喻**
>
> 多重捕捉像**一支滅火器同時能滅油火和電火**：`catch (A | B e)`，同樣處理就不用寫兩次。

```java
try {
    loadConfiguration();
} catch (IOException | ParseException e) {
    System.err.println("設定載入失敗：" + e.getMessage());
}
```

用直線 `|` 分隔多個型別，Java 7 起可用。兩個限制：列出來的例外**不能有父子繼承關係**（廣的那個已經涵蓋窄的了），而且只有處理方式一模一樣時才值得合併。

## 自訂例外

> 🏠 **生活比喻**
>
> 自訂例外像**自己設計的警報類型**：「餘額不足」比籠統的「出錯了」清楚得多。
> - 受檢例外＝**一定要處理的警報**
> - 非受檢例外＝**程式寫錯造成的，應該修程式而不是一直接**

自訂例外繼承 `Exception` 就是受檢的，適合表達「呼叫端可以預期、也有機會補救」的業務失敗；繼承 `RuntimeException` 就是非受檢的，適合表達「違反方法的使用約定」或「程式狀態不合理」。

```java
class InsufficientFundsException extends Exception {
    InsufficientFundsException(String message) {
        super(message);
    }

    InsufficientFundsException(String message, Throwable cause) {
        super(message, cause);   // 保留真正的原因與堆疊
    }
}
```

包裝底層例外時記得把 `cause` 傳進去，不然原始的錯誤現場就不見了。另外，例外的名稱與訊息要描述「失敗了什麼」，不要把正常的流程分支也改用例外來寫。

*【繼承規則】*

## 覆寫方法不能加上更廣的受檢例外

> 🏠 **生活比喻**
>
> 子類別覆寫方法像**繼承店面時不能比原本承諾更危險**：爸爸說「只可能停水」，兒子不能改成「可能停水、停電、失火」，不然依賴爸爸承諾的客人會措手不及。

```java
class Base {
    void load() throws IOException { }
}

class Child extends Base {
    @Override
    void load() throws FileNotFoundException { }   // 可以：更具體
    // void load() throws Exception { }            // 不行：範圍變大了
}
```

子類別覆寫時可以不宣告例外，也可以宣告相同型別或更具體的子型別，就是不能換成更廣的受檢例外。道理跟〈封裝、繼承、多型〉的存取權限規則一樣：**呼叫端只照父類別的約定做準備，不該突然被迫面對更大的風險範圍。**這條限制只管受檢例外，非受檢例外不受宣告限制。

*【開發期的自我檢查】*

## assert 驗證內部假設，不能拿來驗證輸入

> 🏠 **生活比喻**
>
> `assert` 像**自己心裡的檢查**：「這時候門應該是鎖的吧？」，用來抓自己的 bug；不能拿來檢查**客人給的資料**，因為正式環境預設不會開啟。

```java
assert total >= 0 : "總額不應為負數";
```

斷言（assertion）失敗時會丟 `AssertionError`。它適合檢查「照設計來說一定成立」的內部條件。執行時要加 `java -ea` 才會啟用，這正是它的限制所在：**斷言預設是關閉的**，所以絕對不能拿來驗證使用者輸入、權限或公開方法的參數——那些要用 `if` 加丟例外。

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| 例外 | 緊急逃生路線 |
| try / catch | 煮油炸 / 旁邊的滅火器 |
| finally | 最後一定關瓦斯 |
| try-with-resources | 自動關瓦斯的爐子 |
| throw / throws | 喊失火 / 貼「可能失火」告示 |
| assert | 心裡的自我檢查 |

### 重點整理

- 受檢例外編譯器逼你處理，非受檢例外不逼；`Error` 不寫程式去救。
- 多個 `catch` 要先具體、後一般，不然後面的永遠到不了。
- `throw` 是丟出物件，`throws` 是在宣告上聲明責任要交給呼叫端。
- 關資源優先用 try-with-resources，必要時才自己寫 `finally`；設成 `null` 不等於關閉。
- `finally` 幾乎一定會跑，但 `System.exit()` 或 JVM 被砍掉時不會。
- 覆寫方法不能加上比父方法更廣的受檢例外；`assert` 預設關閉，不能拿來驗證輸入。

**Q1. 哪一類例外會被編譯器要求「捕捉或宣告拋出」？**

- (A) 受檢例外，例如 IOException
- (B) 所有 AssertionError
- (C) 所有 RuntimeException
- (D) 所有 Error

<details><summary>看答案</summary>

**答案：(A)** 受檢例外必須用 try-catch 處理，或用 throws 把責任交給上層，否則編譯不過。

</details>

**Q2. 同時寫好幾個 catch 時，排列原則是什麼？**

- (A) 依例外名稱的字母順序
- (B) 受檢例外一律放在非受檢例外後面
- (C) Exception 一律放最前面
- (D) 較具體的子類別放前面，較廣的父類別放後面

<details><summary>看答案</summary>

**答案：(D)** 父類別先接的話，後面那些子類別的 catch 永遠到不了，編譯器會直接拒絕。

</details>

**Q3. throw 與 throws 的差別是什麼？**

- (A) throw 在方法內丟出例外物件；throws 在方法宣告上聲明可能外拋的例外
- (B) throw 只能用於受檢例外，throws 只能用於 Error
- (C) throw 用來關閉資源，throws 用來開啟資源
- (D) throw 是類別，throws 是介面

<details><summary>看答案</summary>

**答案：(A)** throw 是方法內的動作，throws 是方法對外約定的一部分，不代表例外一定會發生。

</details>

**Q4. 要讀寫一個實作了 AutoCloseable 的資源，現在建議怎麼寫？**

- (A) 把資源變數設成 null
- (B) 用 try-with-resources，區塊結束自動關閉

- (D) 寫一個空的 catch 區塊

<details><summary>看答案</summary>

**答案：(B)** try-with-resources 是 Java 7 的語法，會可靠地呼叫 close()，還會保留主要例外與受抑制例外。

**Q5. 關於 finally，下列哪一項最精確？**

- (A) 只有沒發生例外時才執行

- (C) 只有發生例外時才執行

**Q7. 父方法宣告 throws IOException，子類別覆寫時哪個宣告符合規則？**
