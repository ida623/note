## 程式、行程與執行緒

> 🏠 **生活比喻**
>
> 用**工廠**記：
> - 程式＝**工廠的設計藍圖**
> - 行程＝**真的蓋好開工的工廠**，有自己的廠房和資源
> - 執行緒＝**工廠裡的工人**，共用同一個廠房，各自做事

這三個詞用工廠來記最快：**程式**（program）是工廠藍圖，還沒執行的程式碼；**行程**（process）是照藍圖開起來、已經拿到資源的工廠；**執行緒**（thread）是工廠裡真正在做事的員工。

> 行程、執行緒也有人寫作「進程」「線程」，指的是同一件事。容器裡的程式在主機上看就是一個行程，見〈Docker 上手〉。

```text
程式（Program）
└── 啟動後成為行程（Process）
    ├── 主執行緒（Main Thread）
    ├── 工作執行緒 A
    └── 工作執行緒 B
```

| 概念 | 角色 | 跟資源的關係 |
|---|---|---|
| **程式** | 還沒執行的程式碼 | 同一份程式可以啟動成多個行程 |
| **行程** | 執行中的程式實體（instance） | 有自己的記憶體空間，彼此看不到對方；至少含一個執行緒 |
| **執行緒** | 行程內的執行單位 | 共用行程的物件與記憶體，但各自有呼叫堆疊 |

「共用記憶體、各有自己的堆疊」這句是關鍵：執行緒之間透過參考碰得到同一個物件，但各自方法裡的區域變數是獨立的。

> 「一個 CPU 一次只能執行一個行程」這句話在單核心年代成立，放到今天要改成**一個處理核心**——八核心的 CPU 在同一瞬間真的跑得動八件事。下面「並行」跟「平行」的差別講的正是這件事 [[出處]](https://docs.oracle.com/javase/tutorial/essential/concurrency/procthread.html)。

- **並行 concurrency**：多件事在一段時間內交錯推進。單核心靠快速切換也做得到。
- **平行 parallelism**：多件事在同一瞬間真的同時執行。要有多個核心才可能。

> 多行程隔離性好，但行程之間要交換資料得靠行程間通訊，而且每個行程都要一份資源，比較吃記憶體（Chrome 就是這種設計）。多執行緒交換資料直接，代價就是共享狀態容易打架——接下來整課都在講這件事。

## 在 Java 建立與管理工作

> 🏠 **生活比喻**
>
> - 繼承 `Thread`＝**自己就是工人**
> - 實作 `Runnable`＝**寫一張工作單交給工人**，比較有彈性
>
> `start()` 是**叫工人開工**；直接呼叫 `run()` 是**你自己做完**，沒有開新工人。

兩種做法：繼承 `Thread`，或把工作寫成 `Runnable`。`Runnable` 這個寫法比較通用，因為寫工作的那個類別還能去繼承別的類別；繼承 `Thread` 的寫法在簡單的程式裡比較好寫，代價是它必須是 `Thread` 的子類別——Java 類別只能單一繼承，繼承的名額就這麼一個 [[出處]](https://docs.oracle.com/javase/tutorial/essential/concurrency/runthread.html)。

```java
Runnable task = () -> {
    System.out.println(Thread.currentThread().getName());
};

Thread worker = new Thread(task);
worker.start();
```

****一定要呼叫 `start()`。**直接呼叫 `run()` 只是在目前這條執行緒裡執行一個普通方法，根本不會有新執行緒** [[出處]](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html#start())。

> 📝 原筆記更正：原筆記在實作 Runnable 介面的步驟清單最後一步寫「5. 呼叫`run()`方法」，跟同一份筆記前面「3. `start()` 打開執行緒」互相矛盾，查證後更正：要開新執行緒一定是呼叫 start()

`join()` 讓目前這條執行緒等另一條結束再繼續，控制的是**等待關係**，不是整個系統的執行順序。

```java
worker.start();
worker.join();   // 等 worker 跑完再往下
```

**`join(毫秒)` 的意思是「**最多**等這麼久」——對方提早結束就提早往下走，時間到了對方還沒完就不等了。它不會去強制中斷或介入對方執行緒** [[出處]](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html#join(long))。

> 📝 原筆記更正：原筆記寫「join(long milliseconds) -> 等到時間倒數完，其他執行緒就會強制加入」，查證後更正：join(毫秒) 是最多等這麼久，時間到就不等了，不是強制介入對方

`yield()` 只是給排程器的提示，表示目前這條執行緒願意讓出處理器：

- **排程器可以忽略這個提示**
- 很少有適合用這個方法的場合 [[出處]](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Thread.html#yield())

> 優先權（1 到 10，預設 5）的通說是「優先權較高者先執行，優先權相等時 CPU 任選其一」。但實際排到誰跑，取決於作業系統的排程器，不同平台差很多——**不要拿優先權來保證程式的正確性**。一句話總結：**多執行緒難以預測、順序無法完全保證、切換可能發生在任何時刻**。

> 大量工作不要一個配一條新執行緒。執行緒池（thread pool）會重複利用固定數量的執行緒，並集中管理工作佇列與生命週期——例如 Spring Boot 內建的 Tomcat 預設最多 200 條（設定鍵是 `server.tomcat.threads.max`），每個進來的請求分一條 [[出處]](https://docs.spring.io/spring-boot/appendix/application-properties/index.html#application-properties.server.server.tomcat.threads.max)。Servlet 容器怎麼把請求分配到執行緒、為什麼同步問題仍是應用程式自己的事，見〈Servlet 與 JavaWeb 基礎〉。

## 競爭條件與原子性

> 🏠 **生活比喻**
>
> 競爭條件像**兩個人同時看到庫存剩 1，都說「我買了」**，結果賣出兩個。
> `count++` 其實是**讀、加、寫三步驟**，中間可能被插隊。

多條執行緒同時讀寫同一份狀態，結果又取決於誰先誰後，就是**競爭條件**（race condition）。

```text
stock--;   // 看起來一個動作，其實是三個：
           // 1. 讀取 stock 的值
           // 2. 算出 stock - 1
           // 3. 把結果寫回 stock
```

拿購物來看最清楚：庫存 100，兩個人同時買——

```text
時間        T1        T2        T3
執行緒 1    讀到 100   （處理中） 寫回 99
執行緒 2              讀到 100   寫回 99

預期：98　　實際：99
```

兩個人都買到了，庫存只少 1。這叫**遺失更新**（lost update）。

**原子性**（atomicity）指的是：這個操作對其他執行緒而言不可分割——要嘛完整做完，要嘛還沒發生，不會被看到做到一半。

**原子性跟可見性是**兩件不同的事**。原子性講的是「不會被拆開觀察」，可見性講的是「我寫的值別人什麼時候看得到」。原子動作不會被交錯執行，**但這並不代表就不必同步，因為記憶體一致性的問題還在**。`AtomicInteger` 這類原子類別確實兩者都給，但那是它額外提供的保證，不是原子性的定義** [[出處]](https://docs.oracle.com/javase/tutorial/essential/concurrency/atomic.html)。

> 📝 原筆記更正：原筆記把原子性定義成三點：「不可分割性」「即時可見性：操作結果立即對所有線程可見」「硬體層級」，查證後更正：原子性與可見性是兩個不同的性質，不可分割不等於別人馬上看得到

## synchronized 與顯式鎖

> 🏠 **生活比喻**
>
> - `synchronized`＝**廁所門鎖**，一次只能一人進臨界區
> - `ReentrantLock`＝**功能更多的智慧門鎖**：可以設定等多久、可以中斷、可以排隊公平

臨界區（critical section，也有教材叫「危險區域」）是會碰到共享可變資料、需要協調的那段程式。`synchronized` 會先取得指定物件的監視器鎖（monitor lock），同一時間只有拿到同一把鎖的執行緒進得去，其他人就在門外等。

```java
private int stock = 100;

public synchronized boolean buy() {
    if (stock <= 0) {
        return false;
    }
    stock--;
    return true;
}
```

> 💡 **鎖住的範圍必須**涵蓋完整的判斷條件**——「先檢查庫存，再扣庫存」是一組，只保護扣的那一行照樣會超賣**

`ReentrantLock` 提供 `synchronized` 沒有的彈性：可中斷的等待、限時嘗試（`tryLock()`）、多個條件佇列。代價是你得自己記得解鎖，而且一定要寫在 `finally` 裡：

```java
lock.lock();
try {
    // 存取受保護的共享狀態
} finally {
    lock.unlock();   // 例外了也要放開，不然這把鎖永遠鎖著
}
```

## 可見性、volatile 與指令重排序

> 🏠 **生活比喻**
>
> 每個工人有**自己的筆記本**（CPU 快取），改了數字不一定馬上抄回**公告欄**（主記憶體），別人看到的還是舊的。
> `volatile` 是**規定這個數字只能寫在公告欄上**，大家都看最新的；也禁止**偷偷調換做事順序**。

可見性（visibility）講的是：一條執行緒寫進去的值，其他執行緒什麼時候看得到。編譯器、處理器跟快取都會做最佳化，所以不能用單執行緒的直覺去推測結果。

`volatile` 提供可見性與順序保證，最適合「一個人寫狀態、其他人讀狀態」的旗標：

```java
private volatile boolean shutdownRequested;

public void requestShutdown() {
    shutdownRequested = true;
}

public void runLoop() {
    while (!shutdownRequested) {
        // 執行工作
    }
}
```

**`volatile int count` 的 `count++` **仍然**是讀取、計算、寫回三步，照樣會遺失更新——`c++` 這樣的遞增運算式不是一個原子動作** [[出處]](https://docs.oracle.com/javase/tutorial/essential/concurrency/atomic.html)。要原子遞增請用同步區段或 `AtomicInteger`。

> 📝 原筆記更正：原筆記在「加上 `volatile` 後的效果」那段的程式碼註解寫「count++; // 立即刷新到主記憶體」「System.out.println(count); // 強制從主記憶體讀取最新值」，這跟同一份筆記小結裡「不能解決 ❌ 原子性問題」自相矛盾，查證後更正：volatile 不會讓 count++ 變成不可分割的動作

> 常見的解釋是「volatile 會立即寫入主記憶體、讓其他 CPU 的快取失效」。當直覺可以，但嚴格講，Java 記憶體模型是用**先行發生關係**（happens-before）來定義的，並沒有規定實作一定要去刷快取；同步、volatile 與各種並行工具的作用，是建立這種關係，讓跨執行緒的可見性與順序有明確保證。

**指令重排序**（instruction reordering）是編譯器與處理器在不破壞單執行緒語意的前提下調整執行順序。舉個例子：`a` 跟 `b` 沒有依賴關係，順序換一下結果一樣，但可能跑得比較快。問題是這種「單執行緒看起來沒差」的最佳化，在多執行緒下就看得出來了。

## AtomicInteger 與 CAS

> 🏠 **生活比喻**
>
> CAS 像**改共用白板前先確認**：「白板上還是 5 嗎？是的話我改成 6」，不是的話就重新讀再試，**不用鎖門**。

原子類別用在單一變數的原子更新，底層靠的是**比較並交換**（compare-and-swap，CAS）：帶著「我以為現在是多少」去改，只有真的還是那個值才寫進去，否則回報失敗、由演算法決定要不要重試。

```java
AtomicInteger count = new AtomicInteger(0);
int result = count.incrementAndGet();
```

```text
目前值 = 5
執行緒 A：compareAndSet(5, 6) → 成功
執行緒 B：compareAndSet(5, 6) → 失敗（已經是 6 了）
執行緒 B：重新讀到 6，再試 compareAndSet(6, 7) → 成功
```

跟鎖比起來，CAS 不阻塞——失敗的人立刻重試，不會被掛起來等。競爭不激烈的時候，這通常比鎖便宜；競爭一激烈，反覆失敗重試反而在燒 CPU。它有兩個代價：

- **ABA 問題**：值從 A 變成 B 又變回 A，單看值看不出中間發生過事，CAS 會誤以為沒人動過。
- **CPU 開銷**：競爭很激烈時，大量的失敗重試也是在燒 CPU。

**`AtomicInteger` 只保護得了一個變數。**跨多個欄位的業務規則它管不到——那種情況要用鎖、不可變資料，或更高階的並行設計。

> 有一種常見的庫存寫法是「先扣，發現扣成負的再用 `incrementAndGet()` 加回來」。推一遍會發現**賣出的總數其實是對的**，不算 bug；問題只在於補回來之前庫存會短暫變成負數，這段期間別的執行緒讀 `get()` 會看到負值。想避開這個暫態，可以用 `getAndUpdate` 一次完成「檢查＋扣減」，它回傳的是更新前的值，剛好拿來判斷這次有沒有扣到：

```java
int before = stock.getAndUpdate(current -> current > 0 ? current - 1 : current);
// getAndUpdate 回傳的是「更新前」的值
if (before > 0) {
    // 扣成功，剩餘庫存是 before - 1
} else {
    // before 是 0，本來就沒貨了
}
```

## 死結與怎麼避免

> 🏠 **生活比喻**
>
> 死結像**兩個人吃飯各拿一支筷子**，都在等對方放下另一支。
> 避免方法：**大家約好拿筷子的順序**（先拿左再拿右），或**等太久就先放下**。

死結（deadlock）要四個條件同時成立才會發生：

- **互斥**：這份資源同一時間只能給一個人用。
- **持有並等待**：手上抓著一個，又在等另一個。
- **不可搶占**：占著很久也不能把他趕走。
- **循環等待**：A 等 B、B 等 C、C 又等 A，繞成一圈。

```java
// 兩個方法拿鎖的順序相反，就湊齊了循環等待
public void transferAtoB() {
    synchronized (lock1) { synchronized (lock2) { /* ... */ } }
}

public void transferBtoA() {
    synchronized (lock2) { synchronized (lock1) { /* ... */ } }
}
```

最常用的預防法是**破壞循環等待：讓所有程式一律照同一個順序拿鎖**。其他做法還有縮小鎖定範圍、減少巢狀鎖，或用 `tryLock()` 加逾時，拿不到就放棄重來。

> 同步的重點不是「加一把鎖」，而是講清楚哪些狀態必須一起保持一致，以及由哪一把鎖負責保護它們。

## 補充：虛擬執行緒

> 🏠 **生活比喻**
>
> - 平台執行緒＝**正職員工**，人數有限、請一個很貴
> - 虛擬執行緒＝**臨時工**，可以請幾百萬個，等待時（I/O）就讓出座位給別人

長年的建議是「不要啟動 1000 條執行緒，那會把 JVM 弄死」，前提是每一條執行緒都對應一條作業系統執行緒，很貴。Java 21 起定案的**虛擬執行緒**（virtual thread）改變了這個前提：它由 JVM 自己排程，非常輕，開幾十萬條都不成問題 [[出處]](https://openjdk.org/jeps/444)。

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> handleRequest());
    }
}
```

它最適合的是「大部分時間在等」的工作——等資料庫、等外部 API。但要講清楚：**虛擬執行緒完全沒有解決這一課講的任何一個問題。**競爭條件、可見性、死結，一條都沒少，該加的鎖還是要加。

## 一張表收尾

> 🏠 **生活比喻**
>
> 這張表是**多執行緒的工具箱索引**：遇到什麼問題拿哪件工具。

| 工具 | 適合 | 要注意 |
|---|---|---|
| **`synchronized`** | 保護一段複合邏輯或多個相關狀態 | 鎖太大就是大家一起排隊 |
| **`ReentrantLock`** | 需要限時取得、可中斷等待 | 一定要在 `finally` 裡解鎖 |
| **`AtomicInteger`** | 單一計數器或簡單的原子更新 | 跨欄位的規則它管不到 |
| **`volatile`** | 狀態旗標、發布最新的參考 | 不保證複合操作的原子性 |
| **`ExecutorService`** | 提交大量工作、管理執行緒池 | 記得關閉，也要處理工作失敗 |

| 虛擬執行緒 | 可以請幾百萬個的臨時工 |

### 重點整理

- 程式是靜態的碼，行程是執行中的實體，執行緒是行程裡的執行單位。
- 同一行程的執行緒共用物件與記憶體，各有自己的呼叫堆疊——所以共享狀態要協調。
- `start()` 才會開新執行緒，直接呼叫 `run()` 只是普通方法呼叫；優先權與 `yield()` 都只是提示，不能拿來保證正確性。
- `synchronized` 與鎖保護的是完整的臨界區；`AtomicInteger` 只管單一變數。
- `volatile` 給可見性與順序，但 `count++` 照樣不是原子的。
- 死結靠一致的鎖定順序、縮小鎖定範圍或限時取鎖來避免。
- 虛擬執行緒讓「開很多條」變便宜了，但競爭條件、可見性、死結一個都沒消失。

## 隨堂測驗

**Q1. 同一份 Java 應用程式啟動兩次，作業系統會把它們看成什麼？**

- (A) 共用一份呼叫堆疊的兩段程式
- (B) 同一行程內的兩個區域變數
- (C) 同一執行緒的兩次方法呼叫
- (D) 兩個彼此獨立的行程

<details><summary>看答案</summary>

**答案：(D)** 程式是靜態的程式碼，每次啟動都會形成各自擁有記憶體空間與執行環境的行程。

</details>

**Q2. 關於同一行程內的多條執行緒，哪一項正確？**

- (A) 各自擁有完全獨立的行程記憶體空間
- (B) 共用行程裡的物件，但各自有呼叫堆疊
- (C) 不能讀取同一個物件
- (D) 一定照建立的順序執行

<details><summary>看答案</summary>

**答案：(B)** 共用記憶體讓資料交換很直接，各有堆疊讓區域變數彼此獨立；也正因為共用，共享狀態才需要協調。

</details>

**Q3. 建立 Thread 物件後直接呼叫 run()，會發生什麼？**

- (A) run() 會等其他執行緒都結束才跑
- (B) 該方法自動取得所有物件的鎖
- (C) run() 在目前這條執行緒裡像普通方法一樣執行
- (D) JVM 會另外建立一個作業系統行程

<details><summary>看答案</summary>

**答案：(C)** 只有 start() 會要求開新執行緒；直接呼叫 run() 完全沒有並行可言。

</details>

**Q4. 兩條執行緒同時執行 stock--，結果只少扣了一次，這是什麼問題？**

- (A) 泛型型別擦除
- (B) 行程間通訊逾時
- (C) 類別載入失敗
- (D) 競爭條件造成的遺失更新

<details><summary>看答案</summary>

**答案：(D)** stock-- 其實是讀取、計算、寫回三步，交錯執行時後寫的那筆會蓋掉前一筆。

</details>

**Q5. 把 count 宣告成 volatile，為什麼還是保證不了 count++ 正確？**

- (A) volatile 只能用在區域變數
- (B) volatile 禁止其他執行緒讀取該變數
- (C) volatile 不會把讀取、加一、寫回合成不可分割的一個動作
- (D) volatile 會讓所有寫入自動回復

<details><summary>看答案</summary>

**答案：(C)** volatile 給的是可見性與順序保證；複合操作的原子性要靠同步區段或 AtomicInteger。

</details>

**Q6. 執行緒優先權（1 到 10）能拿來做什麼？**

- (A) 保證高優先權的一定先跑完
- (B) 決定執行緒能用多少記憶體
- (C) 保證同優先權的輪流平均執行
- (D) 只是給排程器的提示，不能用來保證執行順序

<details><summary>看答案</summary>

**答案：(D)** 不同作業系統對優先權的處理方式不一樣，靠它保證正確性是很典型的錯誤。

</details>

**Q7. worker.join(1000) 的意思是什麼？**

- (A) 把 worker 的優先權調高一秒
- (B) 一秒後強制把自己插進 worker 裡執行
- (C) 最多等 worker 一秒，時間到就不等了
- (D) 強制讓 worker 在一秒內結束

<details><summary>看答案</summary>

**答案：(C)** join(毫秒) 是上限等待；對方提早結束就提早往下，時間到還沒完也不會去中斷對方。

</details>

**Q8. 要安全地替單一整數計數器累加，而且不必保護其他欄位，用哪個最直接？**

- (A) Thread.yield() 搭配普通 int
- (B) volatile int 搭配 count++
- (C) 提高執行緒優先權後用普通 int
- (D) AtomicInteger.incrementAndGet()

<details><summary>看答案</summary>

**答案：(D)** AtomicInteger 底層用 CAS 提供單一變數的原子更新；volatile、yield 與優先權都做不到這件事。

</details>

**Q9. 兩個方法都要拿 lockA 與 lockB，哪個做法最能降低死結風險？**

- (A) 持有第一把鎖時無限期等第二把
- (B) 把兩條執行緒的優先權都調高
- (C) 一個先拿 lockA，另一個先拿 lockB
- (D) 所有方法一律先拿 lockA，再拿 lockB

<details><summary>看答案</summary>

**答案：(D)** 一致的鎖定順序會破壞死結四條件裡的「循環等待」，是最常用的預防方式。

</details>

**Q10. Java 21 的虛擬執行緒解決了什麼、沒解決什麼？**

- (A) 自動幫所有共享變數加鎖
- (B) 讓「開很多條執行緒」變便宜，但競爭條件與死結完全沒消失
- (C) 讓 count++ 變成原子操作
- (D) 讓程式不再需要 synchronized

<details><summary>看答案</summary>

**答案：(B)** 虛擬執行緒是排程與成本層面的改進；資料競爭、可見性與死結這些問題一條都沒少。

</details>
