## EC2 由哪些零件組成

> 🏠 **生活比喻**
>
> EC2 像**租一台車**：車款（Instance Type）、引擎和配備（AMI）、行李廂（EBS）、停車證（Security Group）、駕駛許可（IAM Role，要透過「通行證夾」Instance Profile 掛上去）。

| 元件 | 角色 | 白話比喻 |
| --- | --- | --- |
| AMI | 決定作業系統、開機磁碟配置等啟動內容 | 裝機範本 |
| Instance Type | 決定 vCPU、記憶體、網路與儲存能力 | 硬體規格單 |
| Instance Metadata | 提供執行個體 ID、主機名稱等執行環境資訊 | 機器的身分證 |
| ENI | 提供 IP、所屬 Subnet 與 Security Group 等網路身分 | 虛擬網卡 |
| Instance Profile | 把 IAM Role 交給這台 EC2 使用 | 權限識別證的套子 |
| EBS Volume | 透過網路連接的區塊儲存 | 外接硬碟 |

IAM Role 不是「寫在主機設定裡」就會自動生效。EC2 是透過 Instance Profile（執行個體設定檔）取得角色憑證，應用程式才能在權限範圍內呼叫 AWS 服務，不必把長期金鑰塞進程式。

*【快，但不一定留得住】*

## Instance Store 與 EBS

> 🏠 **生活比喻**
>
> - Instance Store＝**車上的置物箱**：很快，但換車就沒了
> - EBS＝**可以拆下來帶走的行李箱**：車子停了東西還在，還能裝到另一台車

Instance Store（執行個體儲存）就在承載這台 EC2 的實體主機旁邊，適合暫存資料、快取，或是弄丟了可以重新產生的高速工作資料。它是短暫性儲存（Ephemeral Storage），不該拿來放唯一一份重要資料。

EBS（Elastic Block Store）是獨立於 EC2 生命週期的區塊儲存。EBS Volume 和掛它的 EC2 必須在同一個 AZ；執行個體停掉或換了底層主機，EBS 裡的資料還在。

最容易失手的動作是「把機器停下來，隔天再開起來」。把執行個體「停止」，Instance Store 的資料一樣會被抹除——不是只有砍掉機器或硬碟故障才會不見[出處](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Stop_Start.html)。停止執行個體時，所有 Instance Store 磁碟上的資料都會被抹除。

> 📝 查證更正：原筆記把 Instance Store 的壞處列成兩點：「Ephemeral 短暫存在：當我們把 EC2 Instance 砍掉之後，在 Instance Storage 的資料會跟著全部消失」與「No Backup：就算沒有手動刪除 EC2 Instance，只要所在的 Host 儲存硬碟故障，資料也會跟著不見」。查證後更正：這份清單漏掉最常遇到的那一項——「停止」。第二點用「就算沒有手動刪除」起頭，讀起來像是把沒砍掉機器的情況都涵蓋了，照它判斷會以為只要不砍機器、硬碟沒壞就安全；實際上把執行個體停止，Instance Store 的資料一樣會被抹除

會這樣是因為：啟動執行個體時，它通常會被移到新的底層主機，並取得新的公有 IPv4 位址。這跟資料被抹除是同一件事的兩面——Instance Store 之所以快，正是因為那些磁碟實體插在「現在承載你這台 EC2 的那台實體主機」上；機器一旦被搬到另一台實體主機，插在舊主機上的磁碟當然跟不過去。

所以重點不是「有沒有關機」，而是「是哪一種關機」：

*   重新開機：Instance Store 的資料還在
*   停止、休眠、終止：資料不保留[出處](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html)（休眠＝hibernate，把記憶體裡的內容先存下來再關機，下次開機接著跑。）

> 重新開機（reboot）：Instance Store 的資料留著。停止、休眠或終止：資料沒了。

「停止」不是唯一會清掉資料的情況：

*   資料不保留的還有：變更執行個體類型、AWS 排定的執行個體停止與退役、自動復原
*   資料保留的：重新開機、系統重新開機、電源中斷後重開

判斷方式其實一致——只要這台機器有可能被換到另一台實體主機上，Instance Store 就留不住[出處](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html)。

| 比較項目 | Instance Store | EBS |
| --- | --- | --- |
| 位置 | 與實體主機緊密相連 | 經 AWS 內部網路連接 |
| 生命週期 | 執行個體一停止、休眠或終止就消失 | 可以獨立於執行個體保留 |
| 適合放什麼 | 快取、暫存、可重建的資料 | 系統磁碟、資料檔與要長期保存的資料 |
| 備份方式 | 要由應用程式自己另外複製 | 可以建立 EBS Snapshot |

EBS 會不會在 EC2 終止時一起被刪掉，還要看那個裝置的 Delete on termination 設定；不能因為它是 EBS 就假設一定留得下來。

*【效能不是只看一個數字】*

## IOPS、I/O 大小與 Throughput

> 🏠 **生活比喻**
>
> 像**搬家**：IOPS 是**每秒搬幾趟**，I/O 大小是**每趟搬多少**，Throughput 是**每秒總共搬了多少東西**。

IOPS 是每秒能處理幾次輸入輸出操作；I/O 大小是每次操作搬多少資料；Throughput（吞吐量）則是每秒搬運的資料總量。

> 概念上的吞吐量 ≈ IOPS × 每次 I/O 大小

大量小型、隨機存取的工作通常重視 IOPS；次數少但每次搬很多資料的循序工作，則比較看吞吐量。實際效能還會同時受到 EBS 類型、磁碟設定、工作負載，以及這台 EC2 本身的 EBS 頻寬上限限制。

建立 EC2 選磁碟時，IOPS 的上限有一條算得出來的規則。以現行的 gp3 來說，可以額外加購 IOPS，比例是每 GiB 最多 500 IOPS、整顆最多 80,000，所以一顆 8 GiB 的 gp3，上限正好是 500 × 8 = 4,000[出處](https://docs.aws.amazon.com/ebs/latest/userguide/general-purpose.html)。這裡有兩件事容易搞混。第一，那 4,000 是「最多可以買到」的數字，不是預設就有；gp3 不論容量大小，基準都先給你 3,000 IOPS，多出來的才要另外付錢。第二，這條算式只適用 gp3；老一代的 gp2 是另一套，效能隨容量走，每 GiB 3 IOPS、最低 100、最高 16,000，所以同樣 8 GiB 的 gp2 基準只有 100 IOPS。

> 磁碟規格像水管的一端，EC2 的 EBS 能力像另一端；水流速度會被比較窄的那一端卡住。

*【新硬碟不能直接當資料夾】*

## 建立檔案系統並掛載 EBS

> 🏠 **生活比喻**
>
> 新的 EBS 像**剛買的空白書櫃**：要先**裝隔板**（建立檔案系統），再**擺到房間某個位置**（掛載），才能放書。

把新的 EBS Volume 掛到 EC2，只代表作業系統看得到這個區塊裝置。如果它還沒有檔案系統，得先格式化，再掛載到某個目錄。

```
# 列出區塊裝置與完整路徑
lsblk -p

# 檢查裝置上是否已經有檔案系統
sudo file -s <device-path>

# 只對確認是空白的新磁碟建立 XFS 檔案系統；這個動作會清掉既有資料
sudo mkfs -t xfs <device-path>

# 建立掛載點並掛載
sudo mkdir -p /my_data
sudo mount <device-path> /my_data

# 檢查容量使用狀況
df -h
```

上面用的 XFS 是 Linux 常見的檔案系統格式之一，決定磁碟上的資料怎麼編排。重新開機後要自動掛載，還得依裝置的 UUID（Universally Unique Identifier，一組幾乎不可能重複的識別碼；用它認磁碟比用裝置名稱可靠，因為名稱會變）正確設定作業系統的掛載表。裝置名稱會因環境而異，不要把畫面上看到的名稱當成永遠不變。

*【備份不必每次整顆複製】*

## EBS Snapshot 與復原

> 🏠 **生活比喻**
>
> Snapshot 像**幫書櫃拍照備份**：第一次拍全部，之後只拍有變動的格子；需要時照照片重建一個書櫃。

EBS Snapshot 是 EBS Volume 的區塊層級備份。後續的快照是漸進式備份（Incremental Backup）：概念上只加上前次快照之後變動的區塊，但每一個快照仍然都能單獨當成復原點使用。

快照是 Region 層級的資源，可以拿它在目標 AZ 建立新的 EBS Volume，再掛到那個 AZ 的 EC2。這也說明了「Volume 屬於 AZ、Snapshot 屬於 Region」的差別。

```
EBS Volume
→ 建立 Snapshot
→ 從 Snapshot 建立新的 Volume
→ 把新 Volume 掛到同一 AZ 的 EC2
→ 檢查檔案系統與原有資料
```

想拿到應用程式層級一致的備份，建立快照前通常還要考慮停止寫入、把檔案系統快取刷回磁碟，或改用資料庫本身的備份機制來協調。

*【把配置做成可重複使用的範本】*

## AMI 裝了什麼

> 🏠 **生活比喻**
>
> AMI 像**手機的出廠設定範本**：系統、預裝 App 都在裡面，拿它可以一次開出很多台一模一樣的手機。

AMI（Amazon Machine Image）是啟動 EC2 的範本。它描述作業系統、根裝置與區塊裝置對應（Block Device Mapping），也能設定哪些帳號可以使用這個 AMI（Launch Permissions）。

如果你先在一台用 EBS 開機的 EC2 上裝好套件、建好檔案，再由這台執行個體建立 AMI，AWS 會用相關的磁碟快照把映像內容留下來。之後從這個 AMI 開的新機器，就會帶著同一套基礎環境。

```
基礎 AMI
→ 啟動 EC2
→ 安裝套件與建立檔案
→ 建立新 AMI 與相關 Snapshot
→ 由新 AMI 啟動多台一致的 EC2
```

建立映像時如果允許重新開機，通常比較容易拿到一致的磁碟狀態；選擇不重新開機的話，就要自己評估當下正在寫入的資料完不完整。

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| EC2 | 租來的車 |
| Instance Store / EBS | 車上置物箱 / 可拆的行李箱 |
| IOPS / Throughput | 每秒搬幾趟 / 每秒搬多少 |
| Snapshot | 書櫃拍照備份 |
| AMI | 出廠設定範本 |

### 重點整理

*   AMI 管啟動範本，Instance Type 管運算規格，ENI 管網路身分。
*   EC2 透過 Instance Profile 使用 IAM Role，不該把長期憑證寫進主機或程式。
*   Instance Store 適合可重建的暫存資料；EBS 適合要留住的資料。
*   停止再開機通常會把執行個體搬到另一台實體主機，Instance Store 的資料會被抹除；單純重新開機則留得住。
*   EBS Volume 屬於某個 AZ，EBS Snapshot 是 Region 層級的備份資源。
*   最終的 EBS 效能同時受磁碟規格與 EC2 本身能力限制。
