## S3 與 EBS 的根本差異

> 🏠 **生活比喻**
>
> - EBS＝**電腦的硬碟**，可以改檔案裡的某一行
> - S3＝**倉儲寄物服務**，一次存一整箱、取一整箱，要改就整箱換

S3 是物件儲存（Object Storage）：每個物件由資料、Key 與中繼資料組成。一般操作是上傳、讀取、複製或刪除一整個物件；要改內容，通常是產生新內容後把整個物件重新上傳。

EBS 是區塊儲存（Block Storage），像交給作業系統用的虛擬硬碟。作業系統先建立檔案系統，再透過檔案系統讀寫底層區塊，所以能像一般磁碟那樣改檔案。

| 比較項目 | S3 | EBS |
| --- | --- | --- |
| 模型 | 物件儲存 | 區塊儲存 |
| 識別方式 | Bucket 與 Object Key | 區塊裝置與檔案系統 |
| 典型操作 | 上傳、取得、替換、刪除整個物件 | 由作業系統讀寫與修改檔案 |
| 常見用途 | 圖片、備份、日誌、靜態內容 | EC2 開機磁碟、資料庫磁碟 |

*【看起來像資料夾，其實是一串 Key】*

## Bucket、Object 與 Prefix

> 🏠 **生活比喻**
>
> Bucket 是**倉庫**，Object 是**貼了標籤的箱子**，Prefix 像標籤上的**分類前綴**（「2026/發票/」），看起來像資料夾，其實只是名字的一部分。

Bucket（儲存貯體）是物件的容器。Bucket 名稱除了要符合命名規則，還必須跟別人取的名字不重複——別人先取走的名字你就不能用。

「不能重複」的範圍更精確地說：名稱要在同一個分區（partition）內的所有 AWS 帳號、所有 Region 之間唯一[出處](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html)。分區指的是一群 Region 的集合。平常只用一般商用 Region 的話，記成「全球唯一」不會出錯。

分區這個詞常被記成只有三個，實際上：AWS 在 2026 年 9 月有四個分區，不是三個；而且美國政府雲的代號是 `aws-us-gov`，不是 `us`[出處](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucketnamingrules.html)。四個分別是一般商用 Region（`aws`）、中國 Region（`aws-cn`）、美國政府雲（`aws-us-gov`）與歐洲主權雲（`aws-eusc`）。

> 📝 查證更正：原筆記寫「partition: 分區，目前為止，僅有 Global 分區(aws) & 中國分區(aws-cn) & 美國政府(us)」，查證後更正兩處：一是現在有四個分區，多了歐洲主權雲 aws-eusc；二是美國政府雲的分區代號是 aws-us-gov，不是 us

Object Key 是物件在 Bucket 內的完整識別名稱。例如：

```
s3://my-example-bucket/config/app.json

Bucket：my-example-bucket
Object Key：config/app.json
Prefix：config/
```

S3 底層不是傳統磁碟的目錄樹。主控台顯示的「資料夾」多半是依 Key 裡的斜線與共同前綴（Prefix）整理出來的視覺效果。

S3 以分散式架構處理資料，並提供強一致性（Strong Consistency）：成功寫入或刪除物件之後，後續的讀取與列出操作會反映最新狀態。

*【讓覆寫與刪除有回頭路】*

## Versioning 版本控制

> 🏠 **生活比喻**
>
> 開了 Versioning 像**Google 文件的版本紀錄**：同名檔案重新上傳，舊版還留著，誤刪也能救回來。

開啟 Versioning 之後，同一個 Key 被重新上傳時，S3 會保留不同版本，而不是只留最後一次的內容。這像文件櫃保留每一次修訂稿，能降低手誤覆寫的風險。

在已開啟版本控制的 Bucket 中，對物件做一般刪除時，S3 通常會加上一個 Delete Marker（刪除標記），讓這個 Key 看起來消失了，舊版本其實還在。把那個 Delete Marker 移除，先前的版本就會重新變成目前可見的版本。

Versioning 不是免費的復原魔法：舊版本仍然佔儲存空間，也會產生費用。如果是永久刪除某個特定版本，那個版本就不是靠移除 Delete Marker 找得回來的。

```
同一個 Object Key
├─ Version A：原始內容
├─ Version B：後來覆寫的內容
└─ Delete Marker：目前看起來已刪除
```

*【公開網址不代表公開權限】*

## S3 的存取控制

> 🏠 **生活比喻**
>
> 知道箱子的地址（URL）不代表能打開：像**知道銀行保險箱的編號**，沒有權限還是開不了。

知道 Object URL，不代表任何人都有權讀它。能不能存取，取決於 Block Public Access、Bucket Policy、IAM Policy，以及這個環境有沒有啟用 ACL 等設定。

ACL（存取控制清單）是比較舊、比較細碎的管理方式。一般設計應該優先集中使用 IAM Policy 與 Bucket Policy，並保留 Block Public Access，除非業務上真的需要公開內容。

> 「網址打得開」是結果；真正的安全設計，是先說清楚誰能對哪些 Key 執行哪些動作。

內容要給外部使用者時，也不必馬上把整個 Bucket 公開。可以評估限定範圍的 Bucket Policy、有時效的預先簽署 URL，或乾脆由應用程式控制下載。

*【資料不消失，和現在讀得到，是兩件事】*

## Durability 與 Availability

> 🏠 **生活比喻**
>
> - Durability＝**東西會不會不見**（保險箱被燒掉的機率）
> - Availability＝**想拿的時候拿不拿得到**（銀行今天有沒有營業）

Durability（耐久性）關心資料長期存放後還在不在；Availability（可用性）關心你要用的時候，服務能不能即時回應。

> 耐久性：資料會不會不見；可用性：現在能不能順利讀到。

S3 的耐久性常被記成「11 個 9」：S3 Standard、Standard-IA、One Zone-IA 與 Glacier 系列的設計耐久性都是 99.999999999%[出處](https://aws.amazon.com/s3/storage-classes/)。要注意的是耐久性高不等於永遠讀得到，也不表示可以不做版本控制、權限保護和備份。

*【讓資料自動搬到合適的倉庫】*

## 儲存類別與 Lifecycle

> 🏠 **生活比喻**
>
> 儲存類別像**家裡的收納分區**：常用的放客廳（Standard）、偶爾用的放儲藏室（IA）、幾年用一次的放老家倉庫（Glacier，便宜但取出要等）。
> Lifecycle 是**自動整理規則**：「放超過 90 天就搬去儲藏室」。

選儲存類別不要只看每 GB 的單價，要一起看存取頻率、可接受的取回時間、取回費用，以及資料放在幾個可用區。

| 儲存類別 | 適合情境 | 主要取捨 |
| --- | --- | --- |
| S3 Standard | 經常讀取、要立刻用的資料 | 即時存取，儲存成本較高 |
| S3 Standard-IA | 比較少存取，但需要立刻取回 | 通常有取回費用與最低計費條件 |
| S3 One Zone-IA | 可重建、較少存取的資料 | 只放在單一 AZ，不適合當唯一的重要副本 |
| S3 Glacier 系列 | 封存與長期備份 | 取回時間與費用依方案而異 |
| S3 Glacier Deep Archive | 極少取用的長期封存 | 用較長的取回時間換較低的儲存成本 |

表格最後一欄的「放在幾個可用區」：Standard、Standard-IA 與 Glacier 系列是 3 個以上，One Zone-IA 是 1 個[出處](https://aws.amazon.com/s3/storage-classes/)。One Zone-IA 的設計耐久性數字雖然一樣，但整個可用區出事時仍可能遺失資料。

Lifecycle（生命週期規則）可以依物件年齡或版本狀態，自動把物件轉到別的儲存類別或到期刪除。例如近期日誌放 Standard，變舊了轉進封存類別，超過保存期限再刪掉。

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| S3 vs EBS | 整箱寄物 vs 硬碟 |
| Bucket / Object / Prefix | 倉庫 / 箱子 / 標籤前綴 |
| Versioning | 文件版本紀錄 |
| Durability / Availability | 會不會不見 / 拿不拿得到 |
| 儲存類別 | 客廳 / 儲藏室 / 老家倉庫 |

### 重點整理

*   S3 操作的是完整物件；EBS 提供可以建立檔案系統的區塊裝置。
*   S3 的「資料夾」多半是 Object Key 前綴造成的視覺效果。
*   Versioning 保留覆寫前的版本，Delete Marker 只是把目前版本藏起來。
*   知道 Object URL 不等於有讀取權限。
*   Lifecycle 可以自動轉換儲存類別或清掉過期物件。

## 隨堂測驗

**Q1. 應用程式只想修改大型檔案中的一小段內容，並把儲存空間當一般磁碟用，哪種模型比較合適？**

- (A) 像 EBS 這類區塊儲存
- (B) S3 的物件儲存
- (C) S3 Glacier Deep Archive
- (D) S3 的 Lifecycle 規則

<details><summary>看答案</summary>

**答案：(A)** 物件儲存的一般做法是整個物件重新上傳；要原地改一小段，區塊儲存才適合。

</details>

**Q2. 在 S3 中看到 config/app.json 時，config/ 最精確的解釋是什麼？**

- (A) 它是 Object Key 的共同前綴，主控台把它呈現成資料夾
- (B) 它是一個獨立配置容量的磁碟分割
- (C) 它是一個獨立計費的 Bucket
- (D) 它是掛載在 EC2 上的檔案系統目錄

<details><summary>看答案</summary>

**答案：(A)** S3 底層沒有目錄樹，所謂資料夾是依 Key 裡的斜線整理出來的視覺效果。

</details>

**Q3. 開啟 Versioning 之後，用相同的 Key 上傳新內容，通常會發生什麼事？**

- (A) 建立一個新版本，舊版本仍然保留
- (B) 舊版本立即被永久刪除
- (C) Bucket 會自動變成公開
- (D) 物件會自動轉到 Glacier 類別

<details><summary>看答案</summary>

**答案：(A)** 版本控制的重點就是不覆蓋舊內容，而是多留一個版本。

</details>

**Q4. 在已開啟版本控制的 Bucket 中，一般刪除物件後想復原，首先應該檢查什麼？**

- (A) 是不是有 Delete Marker，以及先前的版本還在不在
- (B) 能不能把 EBS Snapshot 掛到這個 Bucket
- (C) 能不能替 Object URL 配置一組公有 IP
- (D) 能不能把 Bucket 搬到公開子網路

<details><summary>看答案</summary>

**答案：(A)** 一般刪除通常只是加上 Delete Marker，把它移除舊版本就會重新變成目前版本。

</details>

**Q5. 使用者拿到某個 S3 Object URL 卻看到 Access Denied，最合理的原因是什麼？**

- (A) URL 存在不代表這個使用者已經被授權讀取該物件
- (B) S3 物件根本不能透過任何 URL 存取

- (D) 該 Bucket 尚未建立 Lifecycle 規則

<details><summary>看答案</summary>

**答案：(A)** 能不能讀取由 Block Public Access、Bucket Policy 與 IAM Policy 決定，跟知不知道網址無關。

</details>

**Q6. 哪一句最能分辨耐久性與可用性？**

- (A) 耐久性關心資料會不會不見；可用性關心需要時讀不讀得到
- (B) 耐久性是下載速度；可用性是物件大小
- (C) 耐久性只適用 EBS；可用性只適用 S3
- (D) 兩者都是在描述 Bucket 名稱不會重複

<details><summary>看答案</summary>

**答案：(A)** 一個講長期保存，一個講當下能不能服務，兩件事要分開看。

</details>

**Q7. 一份可以從別的來源重建、很少讀取但需要時要能立刻取回的資料，而且能接受單一可用區的風險，哪個類別最符合？**

- (A) S3 One Zone-IA
- (B) S3 Standard
- (C) S3 Glacier Deep Archive
- (D) S3 Standard-IA

<details><summary>看答案</summary>

**答案：(A)** One Zone-IA 就是用單一可用區換較低成本；Deep Archive 雖然更便宜，但取回要等很久。

</details>

**Q8. Lifecycle 規則最適合解決哪個需求？**

- (A) 依資料年齡自動轉換儲存類別或刪除過期物件
- (B) 替 S3 物件自動加上版本控制
- (C) 把 Bucket 名稱改成全球唯一
- (D) 在物件內部直接修改其中一段區塊

<details><summary>看答案</summary>

**答案：(A)** Lifecycle 管的是物件隨時間該搬去哪或該不該留，不負責改內容或改名稱。

</details>
