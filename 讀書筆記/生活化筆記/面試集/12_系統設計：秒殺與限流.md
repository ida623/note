## 先問五個問題，再估流量

> 🏠 **生活比喻**
>
> 秒殺像**限量球鞋開賣**：先問有幾雙、會來多少人、一人限購幾雙、多久賣完、能不能超賣。

答題順序：先釐清需求、再估容量、再畫架構。秒殺是「寫多且要搶」：幾十萬人同一秒搶幾千份限量優惠，難的是同一筆庫存被同時扣。以下以 Redis 8.x、MySQL 8.4 的 InnoDB、Spring Cloud Gateway 現行版為準。

> 💡 面試官：銀行 App 要辦「整點發紅包，限量一萬份」，你怎麼開始？

**一句話定義**：秒殺（限量商品在同一時刻被大量使用者搶購）的核心矛盾是「請求數遠大於庫存數」，目標不是讓每個請求成功，而是讓多餘的請求便宜地失敗、有限的庫存正確地發出去。

| 先問 | 為什麼會改變設計 |
| --- | --- |
| 商品幾種、各幾份？ | 一種一萬份是「一把熱點鍵」；一千種各十份是「一千把小鍵」，拆法不同 |
| 預估峰值？ | 決定要擋掉幾成流量、Redis 與資料庫各要撐多少 |
| 能不能超賣？ | 紅包多發是真金白銀，通常絕不超賣，扣庫存就必須是原子操作 |
| 能不能少賣？ | 要保證一萬份發完，搶到沒付款的份就得退回 |
| 公平性？ | 先到先得還是抽籤？抽籤把「搶」變成「登記」，問題就變成離線批次 |

> 💡 面試官：QPS、頻寬、連線數怎麼估？

QPS（queries per second，每秒請求數）從人數推：一百萬人參加、九成在開搶後前十秒按下，峰值 ＝ 90 萬 ÷ 10 ＝ 每秒 9 萬。每個回應約 1 KB，頻寬約 90 MB/s，即 720 Mbit/s。同時在線的連線數用 Little 定律（Little's law，排隊理論的基本公式）：系統裡同時存在的請求數 ＝ 到達速率 × 平均停留時間。[出處](https://en.wikipedia.org/wiki/Little%27s_law) 每秒 9 萬、停留 50 毫秒是 4,500 條；停留拉長到 2 秒就是 18 萬條，連線池立刻爆掉。所以秒殺每一層都要「快速失敗」而不是「慢慢等」。

**追問時要補的**：每秒查詢數當容量指標常常不準，比較好的做法是直接用可用資源衡量容量，例如 CPU 核數與記憶體。[出處](https://sre.google/sre-book/handling-overload/) 答完 QPS 補一句「最後靠壓測換算成每台機器扛多少」。

*【分層擋流量】*

## 越前面擋越便宜

> 🏠 **生活比喻**
>
> 擋人潮像**演唱會分層管制**：在捷運站就限流（前端、CDN）比擠到會場門口才擋（資料庫）便宜得多。

> 💡 面試官：每秒 9 萬個請求，總不能都打到資料庫吧？

**一句話定義**：把請求當成漏斗，每一層只放行下一層扛得住的量。原則是拒絕一個請求的成本要比它省下的工作低，所以越早拒絕越好。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

```
瀏覽器／App    按一次就變灰、開搶前不給按、驗證碼
   ↓ 擋掉「一個人狂點」
CDN／靜態化     活動頁、商品圖、倒數全是靜態檔
   ↓ 擋掉「看頁面」的流量
Gateway 限流    按使用者、活動、IP 限速，超額回 429
   ↓ 擋掉「超過容量」的流量
應用層          參數與活動時間檢查、黑名單、限購一人一份
   ↓ 擋掉「不合法」的請求
Redis 預扣庫存  一支 Lua 腳本扣庫存，扣不到就結束
   ↓ 擋掉「沒庫存」的請求
訊息佇列 → 資料庫   只剩搶到的一萬筆慢慢寫
```

多層快取與 Bloom Filter 見〈系統設計：短網址的高併發〉，令牌桶、漏桶、滑動視窗的白話定義也在那課。

> 💡 面試官：固定視窗、滑動視窗、漏桶、令牌桶各適合什麼？

**一句話定義**：四種都是「一段時間內最多放行幾個」，差在怎麼算時間、爆量放不放。限流也叫 throttling（節流）。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

| 演算法 | 怎麼算 | 秒殺裡用在哪 | 實作例 |
| --- | --- | --- | --- |
| 固定視窗 | 每分鐘一個計數器，滿了拒絕；12:00:59 與 12:01:00 各放滿一次，邊界瞬間放進兩倍 | 粗略的每人每分鐘上限 | Redis INCR 頁的限流範例[出處](https://redis.io/docs/latest/commands/incr/) |
| 滑動視窗 | 算「最近 60 秒」不是「這一分鐘」，沒有邊界問題，但要記每筆時間 | 敏感操作的精確限制 | Redis 限流詞條（該頁的範例程式其實是固定視窗）[出處](https://redis.io/glossary/rate-limiting/) |
| 漏桶 | 請求先進桶，出口固定速率滴出，桶滿才拒絕；輸出最平滑 | 保護處理能力固定的下游，例如核心帳務 | Nginx `limit_req`，用的就是漏桶[出處](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html) |
| 令牌桶 | 桶裡定速補代幣，有代幣才放行；閒置時代幣會累積，允許短暫爆量到桶的容量 | Gateway 這種要吸收開搶尖峰的入口 | Spring Cloud Gateway 的 Redis 限流器，用的就是令牌桶[出處](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/gatewayfilter-factories/requestratelimiter-factory.html) |

**參數要會講：**

*   Spring Cloud Gateway：`replenishRate` 是令牌桶每秒補幾個代幣，`burstCapacity` 是桶最多裝幾個代幣；超額預設回 HTTP 429；限誰由 `KeyResolver` 決定，預設取登入身分。[出處](https://docs.spring.io/spring-cloud-gateway/reference/spring-cloud-gateway-server-webflux/gatewayfilter-factories/requestratelimiter-factory.html)
*   Nginx：`burst` 是允許排隊的超額數；拒絕預設回 503，可改 429。[出處](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)

```
http {
    # 後端應用伺服器群，proxy_pass 會用到
    upstream app_backend {
        server 10.0.0.11:8080;
        server 10.0.0.12:8080;
    }

    # 以來源 IP 當 key；狀態放 10MB 共用記憶體區 "sale"；平均每秒放 10 個請求
    limit_req_zone $binary_remote_addr zone=sale:10m rate=10r/s;

    server {
        location /api/grab {
            # 超出平均速率的請求最多排 20 個；nodelay 讓排進來的立刻處理、超過的直接拒絕
            limit_req zone=sale burst=20 nodelay;
            limit_req_status 429;
            proxy_pass http://app_backend;
        }
    }
}
```

**429 怎麼答**：429 表示使用者在一段時間內送出太多請求，也就是被限流了；回應可帶 `Retry-After` 標頭指出要等多久。怎麼識別使用者、怎麼計數，HTTP 規格（RFC 6585 第 4 節）沒有規定。[出處](https://www.rfc-editor.org/rfc/rfc6585#section-4)

> 💡 面試官：Gateway 有十台各算各的，限流不就變十倍？分散式限流怎麼做？

**一句話定義**：計數器放大家共用的 Redis，「加一、設過期、判斷」在一次往返裡原子完成，所以用 Lua 腳本。

**為什麼要 Lua：**

*   「先 INCR、第一次才 EXPIRE」分兩個指令送，有競態條件：INCR 做了、EXPIRE 沒做到，這把 key 永遠留著。修法是把兩步寫成一支 Lua 腳本，用 EVAL 送出。[出處](https://redis.io/docs/latest/commands/incr/)
*   Redis 保證腳本原子執行：腳本跑的整段期間，伺服器其他活動全部擋住。[出處](https://redis.io/docs/latest/develop/programmability/eval-intro/)

```
-- KEYS[1] 計數鍵（例如 rl:user:42:1727580000），ARGV[1] 視窗秒數，ARGV[2] 上限
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
  return 0             -- 超過上限，拒絕
end
return 1               -- 放行
```

在 Redis 8.10 實跑：上限 3、視窗 10 秒，前三次回 1、第四次回 0。集中計數的代價是每次決策多一趟 Redis 往返；折衷做法是把上限除以副本數分給每台，定期校正。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling) 「限流元件掛了是放行還是拒絕」見〈後端與雲端面試題庫〉。

## 一萬份紅包，怎麼保證一份都不多發

> 🏠 **生活比喻**
>
> 一份都不能多發：用 **Redis 原子扣庫存**像**一個人顧發號機，按一次出一張**，不會兩人同時拿到最後一張。

> 💡 面試官：庫存放哪裡？Redis 預扣怎麼保證不超賣？

**一句話定義**：活動前把庫存數預熱進 Redis，開搶時用一支 Lua 腳本做「查、判斷、扣一、記名單」；腳本原子執行，兩個人不可能同時看到「還剩 1」然後各扣一次。

**為什麼不能拆成 GET 再 DECR**：GET 回來剩 1，兩個請求都看到 1、都去 DECR，庫存變 -1。DECR 本身是原子的（INCR、DECR 都是 Redis 的原子遞增／遞減操作）[出處](https://redis.io/docs/latest/commands/incr/)，但「先判斷再扣」是兩個指令，中間可以被插隊。

```
-- KEYS[1] 庫存鍵，KEYS[2] 已搶到名單，ARGV[1] 使用者 ID
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -2            -- 這個人已經搶過
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
  return -1            -- 活動不存在或還沒預熱
end
if stock <= 0 then
  return 0             -- 賣完
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1               -- 搶到

-- 呼叫：EVAL "<腳本>" 2 {sale:1001}:stock {sale:1001}:buyers u1
```

在 Redis 8.10 實跑：庫存 2，u1 回 1、u1 再搶回 -2、u2 回 1、u3 回 0；庫存 100、一千個不同使用者一口氣送進去，最後庫存剛好 0、名單剛好 100 人。key 名裡的大括號是雜湊標籤（hash tag），讓多個 key 分到同一個雜湊槽（hash slot，Redis Cluster 把 key 空間切成 16384 格，每格就是一個槽），在叢集上才能做多 key 操作[出處](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)；腳本動兩把 key，不加標籤在叢集上跑不了。

**上線要補三件事：**

*   用腳本的應用程式應該一律呼叫 EVALSHA：先 SCRIPT LOAD 拿 SHA1，之後用 SHA1 呼叫。[出處](https://redis.io/docs/latest/develop/programmability/eval-intro/)
*   腳本必須短，腳本一慢、整台 Redis 都在等。
*   Redis 主從是非同步複製，切換主機的瞬間剛扣掉的庫存可能「還沒扣」，會多發幾份；原因見〈分散式鎖與 Redis〉，補法是資料庫端再擋一道。

> 💡 面試官：直接在資料庫 UPDATE stock = stock - 1 WHERE stock > 0 不行嗎？

**一句話定義**：正確性沒問題、不會超賣；問題是慢，因為同一列的更新在 InnoDB 裡排隊執行。

**為什麼：**

*   MySQL 8.4 的 `UPDATE ... WHERE ...` 對搜尋碰到的每一筆紀錄設排他的 next-key 鎖；用唯一索引找唯一一列時，只需要索引紀錄鎖。[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)
*   交易 T1 持有列 r 的排他鎖時，另一個交易 T2 對 r 的鎖請求必須等 T1 釋放。[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)
*   所以一萬個請求更新同一列，就是一萬個交易輪流拿鎖、各自等 commit 才放手。

在 MySQL 8.4.11 實跑：庫存 1，第一次 UPDATE 影響 1 列、第二次影響 0 列，stock 停在 0。

```
UPDATE coupon_stock SET stock = stock - 1 WHERE id = 1001 AND stock > 0;
-- 影響列數 1 ＝ 搶到；0 ＝ 賣完
```

**取捨怎麼答**：幾百人搶幾十份，這一行就夠。流量大到排隊撐爆連線池，才把「擋人」搬到 Redis，資料庫當最後一道保險：Redis 說搶到、這行 UPDATE 再擋一次，兩邊都過才算數。

> 💡 面試官：一萬個人扣同一把 key，Redis 那個節點會不會被打爆？

**一句話定義**：熱點（hot key，短時間被集中存取的少數 key）在叢集裡逃不掉「一把 key 只住一個節點」：key 空間切成 16384 個槽，叢集穩定時一個槽只由一個節點服務。[出處](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/) 加節點沒用，要拆 key。

*   **分桶庫存**：一萬份拆成 10 把 key 各 1,000 份，用不同雜湊標籤落到不同的槽（槽再由叢集分配到節點，10 個桶配 3 台主節點一定有桶同住一台，但壓力已經拆開），請求按使用者 ID 取餘數選桶。代價是「某桶先賣完、別桶還有」，要不要換桶重試先定好。
*   **本地快取擋讀**：售罄後在應用程式記憶體記一個旗標，之後的請求連 Redis 都不用去。
*   **靜態化擋更多**：活動頁、倒數全進 CDN，Redis 只接「按下搶購」那一下。

*【下單與付款】*

## 搶到之後：排隊寫入、只扣一次、沒付就還

> 🏠 **生活比喻**
>
> 搶到之後**先拿號碼牌，再排隊慢慢寫進帳本**（訊息佇列），寫入時用冪等確保同一張號碼牌只扣一次。

> 💡 面試官：Redis 說搶到了，訂單怎麼寫？使用者怎麼知道結果？

**一句話定義**：用「以佇列平衡負載」（queue-based load leveling）：請求先進訊息佇列，消費者按資料庫扛得住的速度寫訂單；使用者先拿到「排隊中」，結果用輪詢或推播通知。佇列放在工作與它呼叫的服務之間當緩衝，服務按自己的步調處理訊息。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)

**三個必答的後果：**[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)

*   訊息佇列是單向通訊，所以前端要輪詢或推播。
*   多數佇列是「至少一次」遞送，消費者可能收到同一則訊息不只一次，所以寫訂單必須冪等。
*   生產者比消費者快，佇列就會一直長，所以佇列長度要監控；好在能進佇列的人數已被 Redis 限制在庫存數以內。

〈系統設計：短網址的高併發〉講過「丟進佇列就回成功」的風險，這裡回的是「排隊中」，Redis 的預扣紀錄才是真相。

> 💡 面試官：使用者手抖點兩次、App 逾時自動重送，怎麼只扣一次？

**一句話定義**：冪等（idempotent，同一個操作做一次和做很多次結果一樣）靠兩道：用戶端帶冪等鍵，伺服器端用唯一約束擋重複。

**冪等鍵：**

*   冪等鍵是用戶端產生的唯一值，伺服器用它認出「這是同一個請求的重試」，建議用 UUID。[出處](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html)
*   同一把鍵配不同內容應回 422；原請求還在處理又收到重試，應回 409。[出處](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.html)
*   這份 IETF 草案目前是過期狀態，業界範本是 Stripe：存下第一次請求的狀態碼與回應本體，之後帶同一把鍵的請求回同樣結果，鍵至少保留 24 小時。[出處](https://docs.stripe.com/api/idempotent_requests)

```
SET idem:{冪等鍵} 處理中 NX EX 86400
-- 回 OK：第一次，往下做；回 nil：重複請求，把上次結果回給它
```

`NX` 是 key 不存在才設定，`EX` 是以秒計的過期時間。[出處](https://redis.io/docs/latest/commands/set/) 同一條指令在〈分散式鎖與 Redis〉是用來上鎖，「值要隨機、釋放要比對」那課講得完整。

**資料庫那道**：訂單表對（使用者 ID, 活動 ID）建唯一索引，第二筆插入被擋下；在 MySQL 8.4.11 實跑，同一組 (42, 1001) 插第二次回重複鍵錯誤。發生重複鍵錯誤時，InnoDB 會在重複的索引紀錄上設一個共用鎖，多個交易同時插同一列可能死結[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locks-set.html)，所以唯一索引是保險，Redis 名單先擋掉絕大多數重複。

> 💡 面試官：搶到但十五分鐘沒付款，庫存怎麼還？

**一句話定義**：把「十五分鐘後檢查」變成一則延遲訊息或一個定時掃描；到期沒付就取消訂單、Redis 庫存加回、名單移掉這個人。

**延遲訊息**：RabbitMQ 核心沒有延遲佇列（要靠 rabbitmq_delayed_message_exchange 外掛），不裝外掛的標準做法是「訊息存活時間（TTL）加死信交換器」：

*   發布訊息時設 `expiration` 屬性，替單一訊息指定 TTL。[出處](https://www.rabbitmq.com/docs/ttl)
*   到期的訊息送去死信交換器（dead letter exchange，接收被拒絕、過期或被擠出佇列訊息的地方），單一訊息的 TTL 過期就是觸發條件之一；消費者接死信佇列檢查訂單狀態。[出處](https://www.rabbitmq.com/docs/dlx)

一個坑：過期訊息要排到佇列頭才會真的被丟棄。先放 30 分鐘、後放 5 分鐘的訊息會卡住後者，每種延遲時間各開一條佇列可避開。[出處](https://www.rabbitmq.com/docs/ttl)

**定時任務**：每分鐘掃「待付款且建立超過 15 分鐘」的訂單。簡單，代價是精度一分鐘；多台機器同時掃、付款回呼與取消同時到，都用條件式更新「狀態從待付款改成已取消」決勝負，影響列數 0 就是別人先做了。

*【保命】*

## 下游掛了、黃牛來了，主流程怎麼活

> 🏠 **生活比喻**
>
> - 下游掛了＝**付款櫃台壞了就先保留訂單，晚點補**
> - 黃牛＝**門口驗證身分、限制同一人狂刷**

> 💡 面試官：發紅包要呼叫核心帳務入帳，帳務系統慢了或掛了，搶購要跟著掛嗎？

**一句話定義**：不要。用斷路器（circuit breaker，像家裡的電路保險開關，失敗太多就跳開、不再送請求，面試常叫「熔斷」）隔開下游，再用降級（degradation，關掉不重要的功能保重要的）讓主流程活著。

**三態怎麼講：**[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)

*   關閉（Closed）：請求照送並數失敗，超過門檻就進入開啟並啟動計時器。
*   開啟（Open）：請求立即失敗，回傳例外。
*   半開（Half-Open）：放有限數量的請求通過，成功就切回關閉，任一失敗就退回開啟；用意是防止正在恢復的服務突然被請求淹沒。
*   跟重試的分工：重試是預期最終會成功才重試，斷路器是擋掉很可能失敗的操作。

**降級怎麼講**：分兩層：[出處](https://sre.google/sre-book/addressing-cascading-failures/)

*   卸載負載（load shedding）：伺服器接近過載時丟掉一部分流量。
*   優雅降級（graceful degradation）：更進一步，減少需要完成的工作量。

套到紅包：帳務斷路器跳開時搶購照常，訂單寫成「待入帳」、入帳改佇列慢慢補，使用者看到「已領取，稍後入帳」；「好友排行」這類非必要功能先關或降級，把資源留給必要功能。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

**追問時要補的**：重試是連鎖故障的加速器。

*   排程重試一律用隨機化的指數退避，並考慮設伺服器層級的重試預算。[出處](https://sre.google/sre-book/addressing-cascading-failures/)
*   Google 內部的做法：每個請求最多重試三次，而且重試佔請求的比例低於 10% 才重試。[出處](https://sre.google/sre-book/handling-overload/)

熔斷元件的現行方案見〈後端與雲端面試題庫〉，那邊答工具、這邊答原理。

> 💡 面試官：怎麼防機器人與黃牛？

**一句話定義**：沒有一招能全擋，靠疊加把機器人的成本拉高到不划算。這類攻擊有正式名稱 OAT-005 Scalping（OWASP 自動化威脅清單）：用不公平的方法取得限量或熱門的商品或服務，別名包括搶購機器人、插隊、票券黃牛。[出處](https://owasp.github.io/www-project-automated-threats-to-web-applications/assets/oats/EN/OAT-005_Scalping.html)

*   **限購**：一人一份寫進 Lua 腳本的名單；銀行 App 有實名基礎，一個身分只對應一個帳號。
*   **驗證碼與答題**：開搶前先過一題，把「同一毫秒按下」打散成幾秒；只在活動入口做，顧體驗。
*   **風控**：新註冊帳號、同一 IP 大量帳號、請求間隔規律得像機器，合成風險分數，高分的進慢速隊或二次驗證。
*   **事後稽核**：紅包集中在少數收款帳戶就凍結、追回。「事前擋不完，事後可追」要講出來。

邊緣防護與應用限流要分開、兩層都要：DDoS 防護擋不住一個合法使用者把服務打爆，應用層限流也吸收不了容量型攻擊。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

*【壓測與觀測】*

## 怎麼知道系統扛得住

> 🏠 **生活比喻**
>
> 壓力測試像**開賣前先演習**：找一大群人模擬搶購，看系統哪裡先倒。

> 💡 面試官：上線前怎麼確認能撐每秒 9 萬？上線後怎麼知道撐不住了？

**壓測分種類**：壓測（load testing，用工具模擬大量使用者打系統）依 k6 的分類有六種：[出處](https://grafana.com/docs/k6/latest/testing-guides/test-types/)

| 種類 | 測什麼 |
| --- | --- |
| 冒煙 | 最小負載下腳本能動 |
| 平均負載 | 預期的正常情況 |
| 壓力 | 超過預期的極限 |
| 尖峰 | 突然、短暫、大量的活動增加 |
| 臨界點 | 逐步加負載，找出容量極限 |
| 浸泡 | 長時間的可靠性 |

*   秒殺最像尖峰測試：一秒內從 0 衝到 9 萬，看 Redis、佇列、連線池哪個先撐不住；臨界點測試給的是「每台實際扛多少」。
*   拒絕路徑也要壓測：拒絕若還要完整認證、解析，被拒絕的洪水一樣能壓垮系統。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

**觀測看什麼**：四個黃金訊號：[出處](https://sre.google/sre-book/monitoring-distributed-systems/)

*   延遲：成功與失敗請求的延遲要分開看。
*   流量：系統收到多少需求。
*   錯誤：包含明確的（HTTP 500）與隱含的（回 200 但內容錯）。
*   飽和：服務有多滿，重點看最受限的那個資源。

秒殺的儀表板：搶購 API 的 p99 延遲（99% 的請求都比它快的那個時間）、429 比例、Redis CPU、佇列長度、連線池使用率、斷路器狀態。

觸發限流用 p99 延遲不用平均使用率：平均使用率看起來健康時，p99 可能已經超標。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/throttling)

> 秒殺的答案是一條漏斗：前端與 CDN 擋看熱鬧的、Gateway 擋超量的、Redis 擋沒庫存的、佇列替資料庫排隊；每一層都要快速失敗，每一層的失敗都要便宜

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| 秒殺 | 限量球鞋開賣 |
| 前端限流 | 捷運站就管制 |
| Redis 扣庫存 | 一人顧發號機 |
| 非同步下單 | 先拿號碼牌再排隊 |
| 壓力測試 | 開賣前演習 |

### 重點整理

*   開場五問：商品數、峰值、能不能超賣、能不能少賣、公平性；容量先算每秒請求數與頻寬，再用 Little 定律算同時在線的連線數，最後靠壓測換成每台機器的真數字。
*   流量一層層擋：按鈕與驗證碼 → CDN → Gateway 限流 → 應用層檢查 → Redis 預扣 → 佇列 → 資料庫；越前面拒絕越便宜，回 429 附 Retry-After。
*   限流四演算法：固定視窗有邊界問題、滑動視窗精確但狀態多、漏桶輸出平滑（Nginx limit_req）、令牌桶允許突發（Spring Cloud Gateway 的 replenishRate 與 burstCapacity）；分散式限流把計數器放 Redis，用 Lua 讓 INCR 與 EXPIRE 原子。
*   不超賣靠原子：Redis 一支 Lua 腳本做「查、判斷、扣、記名單」，Redis 保證腳本原子執行；資料庫 UPDATE … WHERE stock > 0 也不超賣，但排他鎖讓一萬個請求排隊。熱點拆成多把 key 分桶，雜湊標籤決定落在哪個槽。
*   搶到之後：佇列平衡負載、結果用輪詢或推播；冪等鍵（用戶端 UUID，Stripe 存 24 小時）加唯一索引擋重複；沒付款用 TTL 加死信交換器或定時掃描退回庫存。
*   保命：斷路器三態隔開下游、降級關非必要功能、重試用隨機指數退避加重試預算；防黃牛靠限購、驗證碼、風控、事後稽核疊加。
*   壓測六種裡秒殺重點是尖峰與臨界點，拒絕路徑也要壓；觀測看延遲、流量、錯誤、飽和四個黃金訊號，用 p99 延遲當觸發限流的主訊號。

## 隨堂測驗

**Q1. 秒殺題開場先問「能不能超賣」和「能不能少賣」，為什麼這兩題會改變設計？**

- (A) 絕不超賣決定扣庫存必須是原子操作；不能少賣決定要做逾時退回庫存
- (B) 兩題只影響活動頁的文案，不影響架構
- (C) 超賣與少賣都由 CDN 的快取時間決定
- (D) 問這兩題是為了決定用哪種資料庫索引

<details><summary>看答案</summary>

**答案：(A)** 紅包多發是真金白銀，所以扣庫存要原子；要保證發完，搶到沒付款的份就得退回，兩個需求各長出一段設計。

</details>

**Q2. 為什麼秒殺系統要「越前面的層越早拒絕」？**

- (A) 拒絕越早成本越低，後面每一層只接自己扛得住的量，資料庫只處理真的要扣庫存的請求
- (B) 因為前端的拒絕會自動同步到資料庫
- (C) 因為 Gateway 拒絕的請求會被 Redis 自動重試
- (D) 因為越後面的層回應越快

<details><summary>看答案</summary>

**答案：(A)** 拒絕一個請求的成本要比它省下的工作低，所以把便宜的檢查放前面、貴的寫入放最後。

</details>

**Q3. Gateway 要吸收開搶瞬間的短暫尖峰，四種限流演算法裡哪一種最合適？為什麼？**

- (A) 令牌桶——閒置時代幣會累積，允許短暫爆量到桶的容量，平均速率仍受控
- (B) 固定視窗——每分鐘一個計數器，邊界瞬間可以放進兩倍
- (C) 漏桶——輸出速率固定，任何突發都會被排隊或丟掉
- (D) 滑動視窗——因為它完全不需要狀態

<details><summary>看答案</summary>

**答案：(A)** Spring Cloud Gateway 的 Redis 限流器就是令牌桶，replenishRate 管補充速率、burstCapacity 管一次能吃掉多少突發。

</details>

**Q4. 分散式限流用 Redis 時，為什麼要把 INCR 與 EXPIRE 包進 Lua 腳本，而不是分兩條指令送？**

- (A) 兩條指令中間可能出事，INCR 做了 EXPIRE 沒做，計數鍵就永遠留著；Lua 腳本由 Redis 保證原子執行
- (B) 因為 Redis 的 EXPIRE 指令只能在 Lua 裡呼叫
- (C) 因為 Lua 腳本可以跨多台 Redis 同時執行
- (D) 因為 INCR 不是原子操作，需要 Lua 補救

<details><summary>看答案</summary>

**答案：(A)** INCR、EXPIRE 分兩條指令送有競態條件，修法就是改成一支 EVAL 送出的 Lua 腳本。

</details>

**Q5. Redis 預扣庫存時，為什麼「先 GET 看剩多少、再 DECR」會超賣？**

- (A) 兩個請求可能同時 GET 到剩 1，然後各自 DECR，庫存變成 -1
- (B) 因為 GET 會把庫存清成 0
- (C) 因為 DECR 遇到負數會自動歸零，所以少賣不是超賣
- (D) 因為 GET 與 DECR 不能在同一個連線裡執行

<details><summary>看答案</summary>

**答案：(A)** 判斷與扣減是兩個指令，中間可以被插隊；把「查、判斷、扣」放進同一支 Lua 腳本才是原子的。

</details>

**Q6. 直接在 MySQL 執行 UPDATE stock = stock - 1 WHERE stock > 0，高併發下慢在哪裡？**

- (A) 同一列的 UPDATE 要拿排他鎖，後面的交易必須等前一個釋放，一萬個請求就是排成一列輪流
- (B) 因為這條語句會超賣，資料庫要花時間修正負數
- (C) 因為 WHERE stock > 0 讓資料庫無法使用索引
- (D) 因為每次 UPDATE 都會重建整張表的索引

<details><summary>看答案</summary>

**答案：(A)** InnoDB 對更新的那一列設排他鎖，別的交易對同一列的鎖請求得等它釋放；正確性沒問題，代價是排隊。

</details>

**Q7. 一萬個人同時扣同一把 Redis key，加節點為什麼沒用？正確做法是什麼？**

- (A) 一把 key 只住在一個雜湊槽、一個節點上；要把庫存拆成多把 key 分桶，用不同的雜湊標籤落到不同的槽、分散壓力
- (B) 加節點會自動把同一把 key 複製到每個節點分攤壓力
- (C) 把 key 改成更長的名字就能分散到多個節點
- (D) 改用資料庫存庫存，Redis 只做快取

<details><summary>看答案</summary>

**答案：(A)** 叢集把 key 空間切成 16384 個槽、一個槽只由一個節點服務；熱點只能拆 key，不能靠加機器。

</details>

**Q8. 使用者手抖點兩次搶購，伺服器怎麼確保只扣一次？**

- (A) 用戶端帶冪等鍵，伺服器用 SET NX 或唯一索引擋下第二次，並回傳第一次的結果
- (B) 把第二次請求的庫存扣掉後再加回去
- (C) 讓前端按鈕變灰就夠了，伺服器不必處理
- (D) 把兩次請求都寫進訂單，事後由客服刪一筆

<details><summary>看答案</summary>

**答案：(A)** 冪等鍵的做法是同一把鍵回同樣的結果，資料庫的唯一索引是最後一道保險。

</details>

**Q9. 帳務系統慢到逾時，斷路器跳到「開啟」狀態後會發生什麼事？之後怎麼恢復？**

- (A) 請求立即失敗不再送往帳務系統；計時器到期進入半開，放少量請求試探，成功就關閉、失敗就退回開啟
- (B) 所有請求繼續送往帳務系統，只是延長逾時時間
- (C) 斷路器會自動重試每個失敗的請求直到成功
- (D) 斷路器永久關閉帳務功能，需要重新部署才能恢復

<details><summary>看答案</summary>

**答案：(A)** 開啟時快速失敗、半開時試探，這樣正在恢復的下游不會一下子被請求淹沒；主流程則靠降級（先記待入帳）活下來。

</details>
