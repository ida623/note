## 三種讀寫模式：誰負責把資料放進快取

> 🏠 **生活比喻**
>
> - Cache-Aside＝**自己去冰箱拿，沒有就去廚房拿並放一份進冰箱**
> - Read/Write-Through＝**請管家處理**
> - Write-Behind＝**先寫便條，晚點再登記帳本**

以下以 Redis 8.x、Spring Framework 7.0（Spring 6 同樣適用）、Caffeine 3.x 為準。

> 💡 面試官：Cache-Aside、Read-Through、Write-Through、Write-Behind 差在哪？

**一句話定義**：差在「誰負責把資料放進快取、寫入時快取跟資料庫誰先誰後」。最常見的兩種：Cache-Aside 在資料被請求之後才更新快取；Write-Through 在主資料庫更新時立刻更新快取。[出處](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/caching-patterns.html)

| 模式 | 誰放資料 | 讀不到時 | 寫入時 | 銀行情境 |
| --- | --- | --- | --- | --- |
| Cache-Aside（旁路快取） | 應用程式自己 | 應用程式查資料庫、回填快取 | 寫資料庫，再把快取那筆刪掉 | 匯率表、商品頁：讀多寫少、可以晚幾秒 |
| Read-Through（讀穿） | 快取元件 | 快取自己去資料庫載入 | 同 Cache-Aside | Spring Cache 的 @Cacheable |
| Write-Through（寫穿） | 快取元件 | 同上 | 同一次寫入更新資料庫與快取，兩邊成功才回應 | 寫完立刻要讀到的資料 |
| Write-Behind（寫回） | 快取元件 | 同上 | 先寫快取就回應，延後批次寫回資料庫 | 瀏覽次數這類丟一點沒關係的計數 |

Cache-Aside 的讀取：先查快取，命中就回傳；未命中就查資料庫，把查到的資料放進快取，再回傳。[出處](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/caching-patterns.html)

```
// Cache-Aside：讀
Rate get(String pair) {
    Rate r = redis.get("rate:" + pair);            // 1. 先查快取
    if (r != null) return r;
    r = db.findRate(pair);                          // 2. 未命中，查資料庫
    if (r != null) {
        int ttl = 300 + random.nextInt(60);         // 3. 回填，TTL 加隨機秒數（雪崩那題講為什麼）
        redis.set("rate:" + pair, r, EX, ttl);
    }
    return r;
}
// Cache-Aside：寫
void update(String pair, Rate r) {
    db.saveRate(pair, r);                           // 1. 先更新資料庫
    redis.del("rate:" + pair);                      // 2. 再刪快取
}
```

**Write-Through 與 Write-Behind 怎麼答：**

*   **Write-Through**：資料成功寫進底層資料來源之前，put 不會回傳，所以完全不會改善寫入效能。
*   **Write-Behind**：修改過的快取項目在設定的延遲之後，非同步寫回資料來源。
*   **Write-Behind 的代價**：快取實際上變成權威紀錄（system-of-record，以它為準的那一份），業務上必須允許資料只存在叢集記憶體。[出處](https://docs.oracle.com/en/middleware/standalone/coherence/14.1.1.0/develop-applications/caching-data-sources.html)

帳戶餘額不能用 Write-Behind，這句一定要講。四種模式各由誰放資料的對照圖，見〈快取放哪裡、怎麼失效〉。

## 先刪快取還是先更新資料庫

> 🏠 **生活比喻**
>
> **先改帳本再撕便條**；延遲雙刪＝**撕掉後過一會再撕一次**，防止中間又被貼回舊的。

> 💡 面試官：更新資料時，先刪快取還是先更新資料庫？

**一句話定義**：先更新資料庫、再刪快取。順序反過來，會有一小段時間某個用戶端在資料庫更新前就來讀，未命中之後把舊資料從資料庫撈回來放進快取，快取裡就留下舊資料。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)

```
先刪快取、再更新資料庫（錯的順序）：
  A：刪快取 rate:USD
  B：讀快取未命中 → 查資料庫得到「舊匯率 31.5」
  A：更新資料庫為 31.7
  B：把 31.5 回填進快取          ← 快取是舊的，直到 TTL 到期

先更新資料庫、再刪快取（對的順序）：
  A：更新資料庫為 31.7
  B：讀快取命中「31.5」          ← 只在 A 兩步之間短暫讀到舊值
  A：刪快取
  下一位：未命中 → 查到 31.7 → 回填
```

這兩條時間線用兩個 Map 模擬、照順序交錯執行的程式與輸出，實跑見〈快取放哪裡、怎麼失效〉。對的順序也只是縮短讀到舊值的時間：Cache-Aside 模式本身不保證資料庫與快取一致。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)

> 💡 面試官：延遲雙刪解決什麼、沒解決什麼？

**一句話定義**：延遲雙刪（先刪快取、更新資料庫、隔幾百毫秒再刪一次快取）是業界慣用的補救。第二次刪是要清掉「第一次刪與更新資料庫之間被別人回填的舊值」；「幾百毫秒」是估一次讀取回填要多久，還要蓋過主從資料庫的複寫延遲。

*   **解決了：**「先刪快取」順序留下的舊值，以及讀寫分離時從庫還沒同步就被讀走回填的舊值。
*   **沒解決**：延遲是猜的，讀取比猜的更慢就漏掉；第二次刪也可能失敗，要進訊息佇列重試；兩次刪之間仍讀得到舊值，它是最終一致，不是強一致。
*   **收尾**：不管哪種順序，快取都要設 TTL 當最後一道保險：TTL 到了 key 就從快取刪掉，之後必須回資料庫拿更新後的資料。[出處](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/cache-validity.html) 讀多的路徑真的要「寫完立刻讀到」，就換成 Write-Through。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside)

> 先更新資料庫、再刪快取，是「舊值只會短暫存在」跟「舊值可能留到 TTL 到期」的差別；TTL 是最後一道保險，不是主要手段

*【三種故障】*

## 雪崩、穿透、擊穿：都是「快取沒接住、資料庫被打到」

> 🏠 **生活比喻**
>
> - 雪崩＝**大量便條同時過期**
> - 穿透＝**一直問不存在的東西**
> - 擊穿＝**最熱門的那張剛好過期**

> 💡 面試官：快取雪崩、穿透、擊穿各是什麼、各怎麼防？

**一句話定義**：三個名字都是業界慣用語，共同點是「請求繞過快取直接打到資料庫」，差在為什麼繞過：一大批 key 同時失效叫雪崩；查根本不存在的資料叫穿透；一把熱門 key 剛好過期叫擊穿。

| 故障 | 怎麼發生 | 怎麼防 |
| --- | --- | --- |
| 雪崩 | 整批匯率同一秒過期，或 Redis 整台掛掉 | TTL 加隨機秒數；Redis 做主從與哨兵（Sentinel）；資料庫端限流、斷路器 |
| 穿透 | 拿不存在的帳號狂查，每次未命中、每次打資料庫 | Bloom Filter 先擋「確定不存在」；查無此人也用短 TTL 快取 |
| 擊穿 | 熱門商品頁那把 key 到期的瞬間，幾千個請求同時去重建 | 互斥重建：只讓一個請求查資料庫；或邏輯過期：先回舊值、背景更新 |

**隨機 TTL 是最佳實務：**

*   TTL ＝ 原本的秒數 ＋ 隨機產生的值（加一點時間抖動，jitter）。所有商品資料同時過期，後端資料庫就得吞下所有商品請求。[出處](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/cache-validity.html)
*   Redis 本身也怕同秒到期：很多 key 在同一刻到期，會成為延遲的來源。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

Redis 8.10.2 實測：`SET rate:usd 31.5 EX 348`（300 加隨機 48），`TTL` 回 348；空結果快取、`BF.RESERVE`、`SET NX` 搶鎖的完整輸出，實跑見〈快取放哪裡、怎麼失效〉。

**Bloom Filter 怎麼答**：原理與名單怎麼建見〈系統設計：短網址的高併發〉。Bloom Filter 能保證某個元素「不在」集合裡，對「在」只能給出估計；Redis 建立時要給預期元素數與誤判率。[出處](https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/)

**互斥重建**：Spring 的快取抽象預設不鎖任何東西，同一個值可能被算好幾次。解法是 `sync` 屬性：鎖住那筆快取項目，只有一條執行緒在算，其他的等到項目更新。[出處](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html) 跨機器的版本是用 `SET 鍵 值 NX EX 秒數` 搶一把短鎖，搶到的查資料庫回填、沒搶到的等一下重讀快取；Redis 8.10.2 實測，第二個搶的回空值。鎖的三個不能省的地方見〈分散式鎖與 Redis〉。

```
@Cacheable(cacheNames = "rates", key = "#pair", sync = true)   // 同一把 key 只讓一條執行緒去查
public Rate findRate(String pair) { return db.findRate(pair); }

@CacheEvict(cacheNames = "rates", key = "#pair")                // 更新後把那筆快取刪掉
public void updateRate(String pair, Rate r) { db.saveRate(pair, r); }
```

**邏輯過期**：快取值不設 TTL，另外記一個業務上的到期時間；到期後先把舊值回給使用者，同時只派一個背景任務去更新。Caffeine 的 `refreshAfterWrite` 就是這個機制：

*   **更新（refresh）**：非同步替 key 載入新值，期間仍回傳舊值。
*   **淘汰**：讀取者要等到新值載入完。[出處](https://github.com/ben-manes/caffeine/wiki/Refresh)

代價是短暫看到舊值，匯率表可以、餘額不行。

## 熱 key 與大 key：一個是太多人讀同一把，一個是一把太重

> 🏠 **生活比喻**
>
> - 熱 key＝**大家搶同一瓶飲料**
> - 大 key＝**一格塞了一整箱東西**

> 💡 面試官：熱 key 怎麼發現、怎麼拆？

**一句話定義**：熱 key（hot key，短時間被集中存取的少數 key）的麻煩在 Redis Cluster 裡一把 key 只住一個槽、一個槽只由一個節點服務[出處](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)，所以加節點不會分攤它的壓力——理由〈系統設計：秒殺與限流〉講過。

*   **怎麼發現：**`redis-cli --hotkeys`，只在 maxmemory-policy 是 \*lfu 時有效[出處](https://redis.io/docs/latest/develop/tools/cli/)，因為它靠 LFU 的存取頻率計數；單把 key 用 `OBJECT FREQ`。工具以外，應用程式端抽樣統計也是常見答法。
*   **拆法一，本地快取擋讀**：熱門商品頁先放進應用程式記憶體（Caffeine），大多數讀取連 Redis 都不用去；〈系統設計：秒殺與限流〉用同一招擋售罄後的讀取。代價是各節點短暫不一致。
*   **拆法二，複製多份**：把 `product:1001` 寫成 `product:1001:0` 到 `:9` 十份，讀時隨機挑一份；十份多半落在不同的槽、分散到不同節點，壓力就拆開了；代價是更新要刪十份。十把 key 用 `CLUSTER KEYSLOT` 算出來落在十個不同的槽，以及 `--hotkeys` 的實際輸出，實跑見〈快取放哪裡、怎麼失效〉。

> 💡 面試官：大 key 為什麼危險？

**一句話定義**：大 key（big key，一把 key 的值很大，例如幾十萬個成員的 Set）危險在 Redis 用單一執行緒處理指令，一個慢指令會讓其他用戶端全部排隊等。`SORT`、`LREM`、`SUNION` 這類多元素指令最容易慢，例如取兩個大集合的交集可能花掉可觀的時間。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

*   **怎麼發現：**`redis-cli --bigkeys` 抽樣找元素很多的 key，`--memkeys` 抽樣找佔記憶體多的 key，`--keystats` 兩者合一。[出處](https://redis.io/docs/latest/develop/tools/cli/) 它們走 `SCAN`；`KEYS` 是生產環境很常見的延遲來源，只准除錯用。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
*   **怎麼刪**：用 `UNLINK` 不用 `DEL`：每把 key O(1) 移除，O(N) 的記憶體回收放到另一條執行緒做。[出處](https://redis.io/docs/latest/commands/unlink/) 在 Redis 8.10.2 實測：20 萬個成員的 Set，`MEMORY USAGE` 回 9,234,711 位元組（約 9 MB），`UNLINK` 立刻回 1；`--bigkeys` 的輸出見〈快取放哪裡、怎麼失效〉。要讓 `DEL` 也走背景，設定檔開 `lazyfree-lazy-user-del yes`（預設 no）。[出處](https://github.com/redis/redis/blob/8.0/redis.conf)
*   **怎麼拆**：大 Hash 按欄位名雜湊拆成 100 個小 Hash；大 List 按時間切段；大 String 多半是整份 JSON 塞進一把 key，改存欄位。

## 資料結構、為什麼快、持久化、淘汰

> 🏠 **生活比喻**
>
> Redis 快的原因像**一位手腳很快的櫃台員**：東西全放手邊（記憶體）、一次專心處理一位（單執行緒）不用切換。持久化＝**定時拍照（RDB）或每步寫日記（AOF）**。

> 💡 面試官：Redis 的資料結構各適合什麼？

**一句話定義**：看「值的形狀」選：一個值 String，有欄位的紀錄 Hash，有順序 List，去重 Set，要排名 Sorted Set，記「有沒有」Bitmap，只要「大約幾個」HyperLogLog。[出處](https://redis.io/docs/latest/develop/data-types/) 每種結構的指令與輸出，實跑見〈快取放哪裡、怎麼失效〉。

| 型別 | 定義 | 銀行情境 |
| --- | --- | --- |
| String | 最基本的型別，一串位元組 | 匯率值、Session、計數器、分散式鎖 |
| Hash | 欄位—值配對的紀錄，像 Java 的 HashMap | 一個帳戶的多個欄位，只改一欄 |
| List | 依插入順序排列的字串串列 | 最近十筆交易、簡單佇列 |
| Set | 無序、不重複的字串集合 | 今天登入過的帳號、黑名單 |
| Sorted Set | 不重複字串，依各自的分數維持順序 | 熱門商品排行、以時間當分數的延遲任務 |
| Bitmap | 不是獨立型別，而是定義在 String 上的位元操作，String 最大 512 MB[出處](https://redis.io/docs/latest/develop/data-types/strings/bitmaps/) | 每個帳號一個位元記今天有沒有登入，一億個帳號約 12 MB |
| HyperLogLog | 估算不重複元素數，最多用 12 KB，標準誤差 0.81%[出處](https://redis.io/docs/latest/develop/data-types/probabilistic/hyperloglogs/) | 活動頁的不重複訪客數 |

> 💡 面試官：Redis 為什麼快？它是單執行緒嗎？

**一句話定義**：快的原因有三：資料在記憶體、指令處理是單執行緒沒有鎖的開銷、用 I/O 多工（multiplexing，一條執行緒同時看管很多條連線，誰有資料就處理誰）不會卡在等網路。

*   Redis 大體上是單執行緒設計：單一行程用多工服務所有用戶端請求，而且設計成不會卡在讀寫 socket 這類系統呼叫上。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)
*   CPU 很少成為 Redis 的瓶頸，瓶頸通常在記憶體或網路。[出處](https://redis.io/docs/latest/develop/get-started/faq/)

**版本界線要答對：**「單執行緒」指執行指令那條線。Redis 6.0 起可以選擇用多條執行緒處理 I/O[出處](https://github.com/redis/redis/blob/6.0/00-RELEASENOTES)，把用戶端 socket 的讀寫放到不同的 I/O 執行緒；預設 `io-threads 1`，也就是照舊只用主執行緒。[出處](https://github.com/redis/redis/blob/8.0/redis.conf)

答法：「指令執行單執行緒，每個指令都是原子的；6.0 起網路讀寫可多執行緒，預設關著」。

> 💡 面試官：RDB 對 AOF，快取要不要開持久化？

**一句話定義：**

*   **RDB**：每隔一段時間，對資料集做某一時刻的快照。
*   **AOF**：記錄每一個寫入操作，啟動時重播、重建資料集。
*   **第三個選項，不持久化**：做快取時有時會這樣用。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

|   | RDB | AOF |
| --- | --- | --- |
| 檔案 | 非常緊湊的單一檔案，適合備份與災難復原 | 一個接一個的操作紀錄，容易看懂、容易匯出，太大時背景重寫 |
| 會丟多少 | 要把停機時的資料遺失降到最低，RDB 不適合；快照通常五分鐘以上一次 | 預設 `appendfsync everysec`：每秒 fsync 一次，最多丟一秒；`always` 最安全但很慢 |
| 代價 | 需要常常 fork()，資料集大時可能讓 Redis 停幾毫秒到一秒 | 視 fsync 策略，可能比 RDB 慢 |

**怎麼選：**

*   要接近 PostgreSQL 的資料安全：兩種都開。
*   能接受丟幾分鐘：只開 RDB 就好。
*   不建議只開 AOF。[出處](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

銀行情境：純快取（匯率、商品頁）可以不開，掛了從資料庫回填、但要防雪崩；當鎖、當預扣庫存這種「丟了會出帳務問題」的用途至少 AOF everysec。不持久化與開 AOF 兩台重開前後的對照，實跑見〈快取放哪裡、怎麼失效〉。

> 💡 面試官：記憶體滿了怎麼辦？maxmemory-policy 怎麼設？

**一句話定義：**`maxmemory` 設上限，`maxmemory-policy` 決定滿了淘汰誰，目前有十種：`noeviction` 不淘汰，寫入回錯誤；`allkeys-` 開頭的四種對全部 key 用 LRU（最近最少用）、LFU（最不常用）、LRM（最近最少被改——只看寫入不看讀取，Redis 8.6 起新增）、隨機；`volatile-` 開頭的五種只淘汰設了 TTL 的 key，多一個 `volatile-ttl` 挑剩餘 TTL 最短的；沒有 key 設 TTL 時，volatile 系列的行為等同 noeviction。[出處](https://redis.io/docs/latest/develop/reference/eviction/)

```
# redis.conf
maxmemory 2mb                    # 上限；0 表示不限制
maxmemory-policy allkeys-lru     # 沒特別理由時，allkeys-lru 是好的預設選項
maxmemory-samples 5              # 抽樣近似，預設抽 5 把，10 更準但多吃 CPU
```

**兩個常考細節**：第一，Redis 開源版的預設是 `noeviction`，快取用途一定要改。[出處](https://github.com/redis/redis/blob/8.0/redis.conf) 第二，LRU 是抽樣少量 key、淘汰其中最久沒用的，不是精確計算。[出處](https://redis.io/docs/latest/develop/reference/eviction/) Redis 8.10.2 實測：`maxmemory 2mb`、`allkeys-lru`，寫進 3,000 把各 1 KB 的 key 後剩 428 把、`evicted_keys` 2,572，兩個數用同一個 `INFO` 指令讀，加起來剛好 3,000；另一台用 `noeviction` 寫同樣 3,000 把，只有 440 把寫進去，其餘回「OOM command not allowed when used memory > 'maxmemory'」。完整輸出見〈快取放哪裡、怎麼失效〉。

*【兩層與分工】*

## Caffeine 加 Redis 怎麼失效，HTTP 快取又是誰的事

> 🏠 **生活比喻**
>
> 兩層快取＝**自己抽屜（Caffeine）＋共用冰箱（Redis）**；冰箱換了東西要**廣播叫大家清抽屜**。

> 💡 面試官：本地快取加分散式快取兩層，資料改了怎麼讓兩層都失效？

**一句話定義**：兩層是「每台應用程式自己的記憶體」加「大家共用的 Redis」：先查本地快取、再查共用快取，最後才查資料庫。代價是要小心設定，避免本地快取比共用快取舊太多。[出處](https://learn.microsoft.com/en-us/azure/architecture/best-practices/caching) 難的是散在幾十台機器記憶體裡的 Caffeine。

*   **做法一，短 TTL 認了**：本地層只留幾秒到幾十秒，過了就不再視為有效。這是最簡單的解法。[出處](https://redis.io/docs/latest/develop/reference/client-side-caching/)
*   **做法二，廣播失效**：更新的那台刪 Redis 之後，用 Pub/Sub 發一則「rate:USD 失效」，每台訂閱到就刪自己的 Caffeine。代價是訊息會送到每一台，包括根本沒快取那筆的。[出處](https://redis.io/docs/latest/develop/reference/client-side-caching/)
*   **做法三，Redis 6 起的用戶端追蹤（client tracking）**：伺服器替你記哪台用戶端讀過哪把 key。key 被修改、因 TTL 到期或因 maxmemory 被淘汰時，所有可能快取著它的用戶端都會收到失效訊息，收到就必須刪掉對應的 key。[出處](https://redis.io/docs/latest/develop/reference/client-side-caching/)

Spring Cache 的 `@Cacheable`、`@CacheEvict`、`sync = true` 與「自己呼叫自己不生效」用 Spring Framework 7.0.9 實際執行的程式與輸出，實跑見〈快取放哪裡、怎麼失效〉。

**Caffeine 為什麼是本地層的標準答案**：高效能的 Java 快取程式庫，命中率接近最佳[出處](https://github.com/ben-manes/caffeine/wiki)；淘汰用 Window TinyLfu，在各種工作負載上都比 LRU 好很多。[出處](https://github.com/ben-manes/caffeine/wiki/Efficiency)

```
LoadingCache<String, Rate> local = Caffeine.newBuilder()
    .maximumSize(10_000)                          // 數量上限，淘汰最近沒用或很少用的
    .expireAfterWrite(Duration.ofSeconds(30))      // 寫入 30 秒後到期：本地層短 TTL
    .refreshAfterWrite(Duration.ofSeconds(10))     // 10 秒後被查到就背景更新，期間回舊值
    .build(pair -> redis.getOrLoad(pair));         // 未命中往下一層拿
```

`expireAfterWrite` 從建立或最近一次替換起算，`expireAfterAccess` 從最近一次讀或寫起算。[出處](https://github.com/ben-manes/caffeine/wiki/Eviction) Spring 裡通常交給快取抽象[出處](https://docs.spring.io/spring-framework/reference/integration/cache.html)：@Cacheable 觸發放入、@CacheEvict 觸發移除、@CachePut 照常執行方法並更新快取。[出處](https://docs.spring.io/spring-framework/reference/integration/cache/annotations.html)

> 💡 面試官：CDN、瀏覽器的 HTTP 快取，跟應用層快取怎麼分工？

**一句話定義**：HTTP 快取存「整個回應」，由瀏覽器與 CDN 依標頭自動處理，適合靜態檔與公開頁面；應用層快取存「查詢結果」，由程式自己管，適合登入後每個人不同的資料。HTTP 快取分兩種：

*   **共用快取（shared cache）**：儲存回應給多個使用者重用，通常部署在中間節點，也就是 CDN。
*   **私有快取（private cache）**：專屬單一使用者，通常是瀏覽器的一部分。[出處](https://www.rfc-editor.org/rfc/rfc9111)

| 資料 | 放哪一層 | 標頭或做法 |
| --- | --- | --- |
| 商品圖、JS、CSS | CDN 與瀏覽器 | `Cache-Control: public, max-age=31536000`，檔名帶版本雜湊 |
| 匿名可看的商品頁 | CDN 幾十秒 ＋ Redis | `s-maxage`：對共用快取蓋過 max-age[出處](https://www.rfc-editor.org/rfc/rfc9111#section-5.2.2.10) |
| 登入後的餘額、明細 | 只在應用層，或不快取 | `Cache-Control: private, no-store`；`private`：共用快取不得儲存[出處](https://www.rfc-editor.org/rfc/rfc9111#section-5.2.2.7) |

新鮮度、`no-cache` 對 `no-store`、ETag 與 304，見〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉。個人資料被 CDN 存起來給別人看，多半是漏了 `private`。

> 快取的每一題都在問：舊值能被看到多久、被誰看到；先講這份資料能容忍多舊，再選模式與 TTL

### 🗺️ 比喻對照表

| 技術名詞 | 生活比喻 |
| --- | --- |
| Cache-Aside | 自己拿，沒有就順便補 |
| 延遲雙刪 | 撕兩次便條 |
| 雪崩 / 穿透 / 擊穿 | 同時過期 / 問不存在 / 熱門過期 |
| Redis 單執行緒 | 專心的快手櫃台員 |

### 重點整理

*   Cache-Aside 應用程式自己回填、寫完刪快取；Write-Through 兩邊同步寫、寫不會變快；Write-Behind 先寫快取、延後寫回資料庫，餘額不能用。
*   先更新資料庫、再刪快取；延遲雙刪補舊值但延遲是猜的、仍是最終一致；TTL 是最後一道保險，要強一致改 Write-Through。
*   雪崩用隨機 TTL；穿透用 Bloom Filter 加快取空結果；擊穿用互斥重建（Spring sync=true、SET NX）或邏輯過期（Caffeine refreshAfterWrite）。
*   熱 key 一把只住一個槽、加節點沒用：--hotkeys（要 LFU）找，本地快取或複製多份拆。大 key 卡住單執行緒：--bigkeys 找，UNLINK 背景回收，拆小。
*   Redis 快在記憶體、單執行緒執行指令加 I/O 多工；6.0 起 io-threads 可多執行緒讀寫網路，預設關。RDB 快照可能丟幾分鐘；AOF 預設每秒 fsync、最多丟一秒；純快取可不開，當鎖或庫存至少 AOF。淘汰策略預設 noeviction、快取要改 allkeys-lru。
*   兩層失效三招：本地短 TTL、Pub/Sub 廣播、Redis 6 起的 client tracking。HTTP 快取存整個回應：靜態檔與匿名頁交給 CDN 用 max-age 與 s-maxage，個人資料加 private。

## 隨堂測驗

**Q1. 匯率表用 Cache-Aside，更新一筆匯率時為什麼要「先更新資料庫、再刪快取」，而不是反過來？**

- (A) 先刪快取的話，空檔裡未命中的讀取會把舊值回填，快取留著舊值直到 TTL 到期
- (B) 先更新資料庫的話，Redis 會自動跟著同步，之後就不需要再另外刪快取
- (C) 先刪快取的話，資料庫那邊的更新會因為鎖衝突而失敗，所以一定要先更新
- (D) 兩種順序的結果完全一樣，只是團隊習慣不同，面試時講哪一種都可以

<details><summary>看答案</summary>

**答案：(A)** 順序很重要：先刪快取會在更新前留下一個視窗，讀取者把過時資料回填進快取。

</details>

**Q2. 延遲雙刪（刪快取、更新資料庫、幾百毫秒後再刪一次）解決了什麼、又沒解決什麼？**

- (A) 清掉中間被回填的舊值，但延遲是猜的、第二次刪可能失敗，仍是最終一致
- (B) 讓快取與資料庫變成強一致，從此任何時刻都不會再讀到舊值，也不必設 TTL
- (C) 取代 TTL，做了延遲雙刪之後，快取裡的 key 就不必再設過期時間了
- (D) 解決快取穿透，因為第二次刪會把不存在的 key 也一起從快取清掉

<details><summary>看答案</summary>

**答案：(A)** 延遲雙刪是縮短舊值存在的時間，不是消除；要寫完立刻讀到，可以考慮改用 Write-Through。

</details>

**Q3. 整批匯率在凌晨同一秒寫進 Redis、TTL 都設 300 秒，五分鐘後資料庫突然被打爆。這是哪種故障、怎麼防？**

- (A) 快取雪崩；TTL 加隨機秒數讓 key 錯開到期
- (B) 快取穿透；用 Bloom Filter 擋掉根本不存在的匯率代碼
- (C) 快取擊穿；把 TTL 拉長到一天，讓它不要那麼常到期
- (D) 大 key 問題；把整張匯率表拆成很多把比較小的 key

<details><summary>看答案</summary>

**答案：(A)** 一大批 key 同時失效就是雪崩；很多 key 同一刻到期，在 Redis 本身也會成為延遲來源。

</details>

**Q4. 熱門商品頁那把 key 到期的瞬間，幾千個請求同時未命中、同時去查資料庫。Spring Cache 裡最直接的防法是？**

- (A) @Cacheable 加 sync = true，同一把 key 只讓一條執行緒去查
- (B) 把 @Cacheable 換成 @CachePut，讓每次呼叫都把結果寫回快取，就不會同時查資料庫
- (C) @CacheEvict 加 allEntries = true，先清空整個快取再讓大家重新載入
- (D) 把 TTL 設成 0，讓那把 key 永遠不會過期

<details><summary>看答案</summary>

**答案：(A)** Spring 的快取抽象預設不鎖任何東西，同一個值可能被算好幾次；sync 屬性就是為這種情境設計的。

</details>

**Q5. 一把 Redis key 每秒被讀幾十萬次，把叢集裡那個節點打爆了。為什麼「再加幾個節點」沒用？**

- (A) 一把 key 只落在一個槽、一個槽只由一個節點服務；要複製多份或用本地快取擋讀
- (B) 加節點會讓所有雜湊槽重新計算，搬移期間那把 key 反而變得更慢、更容易逾時
- (C) Redis Cluster 規定最多只能有三個主節點，再加的節點只能當複本、不能分攤讀取
- (D) 加節點只對寫入有幫助，讀取一律由第一個節點負責，所以讀的壓力不會被分攤

<details><summary>看答案</summary>

**答案：(A)** Redis Cluster 把 key 空間切成 16384 個槽、穩定時一個槽只由一個節點服務；熱 key 只能拆，不能靠加機器。

</details>

**Q6. 要刪一個有 20 萬個成員、約 9 MB 的 Set，為什麼建議用 UNLINK 而不是 DEL？**

- (A) DEL 回收大物件時其他請求都得等；UNLINK 把回收放到另一條執行緒
- (B) DEL 只能刪 String 型別的 key，刪 Set、Hash 這類集合型別的 key 必須改用 UNLINK
- (C) UNLINK 會先把整個 Set 備份到 RDB 檔，刪錯時還可以從備份救回來，比較安全
- (D) DEL 會連帶刪掉同一個雜湊槽裡的其他 key，UNLINK 只刪指定的那一把，不會誤刪

<details><summary>看答案</summary>

**答案：(A)** UNLINK 每把 key O(1) 移除，O(N) 的回收放到另一條執行緒做；大 key 的危險就是卡住單執行緒。

</details>

**Q7. 面試官問「Redis 是單執行緒嗎？」以 Redis 6 以後的版本，最準確的答法是？**

- (A) 指令執行是單執行緒、每個指令是原子的；6.0 起 io-threads 可多執行緒讀寫網路，預設關
- (B) 完全單執行緒，從第一版到現在的任何版本，整個行程都只有一條執行緒在工作
- (C) 6.0 起完全多執行緒，指令會並行執行，所以 INCR 這類指令已經不再是原子的了
- (D) 取決於作業系統，Linux 上是多執行緒，macOS 和 Windows 上才是單執行緒

<details><summary>看答案</summary>

**答案：(A)** Redis 6.0 起可以選擇用多條執行緒處理 I/O；設定檔預設 io-threads 1，就是照舊只用主執行緒。

</details>

**Q8. Redis 拿來當秒殺的預扣庫存，只開 RDB 每五分鐘快照一次，機器斷電會怎樣？該怎麼改？**

- (A) 最多丟掉五分鐘的扣庫存紀錄；至少改開 AOF everysec，最多丟一秒
- (B) RDB 是每次寫入都即時存檔，斷電也不會丟任何一筆扣庫存紀錄，不需要改
- (C) 只要把快照間隔改成每一分鐘一次，斷電時就完全不會丟資料了
- (D) 把 maxmemory-policy 改成 noeviction，資料就不會因為斷電而遺失

<details><summary>看答案</summary>

**答案：(A)** 要把停機時的資料遺失降到最低，RDB 不適合；AOF 預設每秒 fsync 一次，最多丟一秒。

</details>

**Q9. Redis 開源版剛裝好、設了 maxmemory 但沒動 maxmemory-policy，記憶體滿了寫入會發生什麼事？快取用途該改成什麼？**

- (A) 預設 noeviction，寫入回 OOM 錯誤；快取用途改成 allkeys-lru
- (B) 預設是 allkeys-lru，記憶體滿了會自動淘汰最久沒用的 key，所以完全不用改設定
- (C) 預設是 volatile-ttl，會先刪掉剩餘 TTL 最短的 key，沒設 TTL 的 key 永遠保留
- (D) 記憶體滿了 Redis 會自動重新啟動並清空所有資料，重啟後再從資料庫重新載入

<details><summary>看答案</summary>

**答案：(A)** 預設的 maxmemory-policy 是 noeviction；實測時切成 noeviction 再寫入，回的就是 OOM command not allowed。

</details>
