## SOA 的 ESB 跟 API Gateway 差在哪

> 🏠 **生活比喻**
>
> - ESB＝**中央大總機**，所有訊息都經過它轉換和路由，它很聰明但也很重
> - API Gateway＝**只在大門口驗票指路**，邏輯留在各家店

答題公式：先一句話定義，再講差別與取捨，最後補版本或實務註記。以下版本為準：Spring Boot 4.1、Spring Cloud 2025.1、Resilience4j 2.4（官方文件站標示 v2.2.0）、Istio 1.31。

> 💡 面試官：單體、SOA、微服務怎麼演進？ESB 跟現在的 API Gateway 差在哪？

**一句話定義**：三者差在「拆多細」與「聰明放哪裡」。單體（monolith）是一個部署單位；SOA（服務導向架構）拆成服務，但整合邏輯集中在 ESB（Enterprise Service Bus，企業服務匯流排）；微服務拆得更小，整合邏輯留在服務身上。

**ESB 是什麼**：把大量聰明放進通訊機制本身的典型。ESB 產品常內建訊息路由、編排、轉換、套用業務規則這些功能。[出處](https://martinfowler.com/articles/microservices.html)

**API Gateway 是什麼**：給每個用戶端一個統一的介面去存取後面的服務。[出處](https://microservices.io/patterns/index.html)

它管入口：路由、認證、限流、TLS 終結（加密連線在大門解開，後面走內部網路），也會把一個請求分派到多個服務再合併結果、把對外協定轉成內部用的協定。[出處](https://microservices.io/patterns/apigateway.html)

界線在業務規則：規則留在服務裡，也就是「聰明端點、笨管線」（smart endpoints and dumb pipes）。[出處](https://martinfowler.com/articles/microservices.html)

|   | ESB | API Gateway |
| --- | --- | --- |
| 放在哪 | 服務與服務之間的中間層 | 外部流量進來的入口 |
| 管什麼 | 路由、協定轉接、欄位轉換、多系統編排、業務規則 | 路由、認證、限流、TLS 終結、合併多個服務的回應、對外協定轉內部協定 |
| 業務規則 | 大量在匯流排上 | 不放，留在各服務 |

收尾一句：業務規則一旦搬進 Gateway，它就容易長成新的 ESB。

> ESB 是聰明的管線，Gateway 是笨的門：門查證件、數人頭、指路，不替你辦業務

## 服務發現兩種模式，集中設定兩條路

> 🏠 **生活比喻**
>
> - 服務發現＝**商場的店家目錄**：客戶端自己查目錄（客戶端發現），或問服務台帶路（伺服器端發現）
> - 集中設定＝**總部統一發公告**，各店自動更新

> 💡 面試官：服務發現有哪兩種模式？Kubernetes 的 Service 算哪一種？

**一句話定義**：差別在「誰去查名冊」（名冊就是服務註冊表，Service Registry）。

*   **用戶端模式**（client-side discovery）：用戶端自己查服務註冊表，拿到服務實例的位置。[出處](https://microservices.io/patterns/client-side-discovery.html)
*   **伺服器端模式**（server-side discovery）：用戶端把請求發給位置固定的路由器（也就是負載平衡器），路由器查服務註冊表，再轉給可用的實例。[出處](https://microservices.io/patterns/server-side-discovery.html)

**取捨：**

*   **用戶端模式**：零件與網路跳數較少；代價是用戶端跟服務註冊表綁在一起、每種語言各寫一次。[出處](https://microservices.io/patterns/client-side-discovery.html)
*   **伺服器端模式**：用戶端程式碼較簡單；代價是除非雲端環境內建，路由器是另一個要安裝、設定的元件，而且網路跳數比較多。[出處](https://microservices.io/patterns/server-side-discovery.html)

**K8s 的 Service 算哪種**：伺服器端。Kubernetes 這類叢集方案在每台主機跑一個代理，當作伺服器端發現的路由器。[出處](https://microservices.io/patterns/server-side-discovery.html) 例外是 headless Service：平台不做負載平衡或代理，把 Pod 位址交給用戶端自己挑要連哪個 Pod，這時就是用戶端模式。[出處](https://kubernetes.io/docs/concepts/services-networking/service/) 原理見〈Service：找路〉。

**版本註記（Eureka 現況）：**

*   **Eureka 還在**：Spring Cloud Netflix 現行版 5.0.2 只剩服務發現（Eureka）一項[出處](https://docs.spring.io/spring-cloud-netflix/reference/)
*   **其他已移除**：Hystrix、Ribbon、Zuul 在 Spring Cloud 2020.0 移除[出處](https://github.com/spring-cloud/spring-cloud-release/wiki/Spring-Cloud-2020.0-Release-Notes)，Hystrix 的現況見〈後端與雲端面試題庫〉

現在的答案：

*   **用戶端負載平衡**：用 Spring Cloud LoadBalancer[出處](https://docs.spring.io/spring-cloud-commons/reference/spring-cloud-commons/loadbalancer.html)
*   **斷路器**：用 Spring Cloud Circuit Breaker（架在不同斷路器實作上的一層抽象，支援 Resilience4J 與 Spring Retry）[出處](https://spring.io/projects/spring-cloud-circuitbreaker)
*   **版本**：Spring Cloud 2025.1 對應 Spring Boot 4.0，要配 4.1 得用 2025.1.2 起。[出處](https://spring.io/projects/spring-cloud)

> 💡 面試官：集中設定怎麼做？Spring Cloud Config 跟 ConfigMap 怎麼選？

**一句話定義**：Spring Cloud Config 替分散式系統把設定搬到程式外面，分伺服器端與用戶端兩半；儲存後端預設用 git，所以設定天生有版本與標籤。[出處](https://docs.spring.io/spring-cloud-config/reference/) 用戶端設 `spring.config.import=optional:configserver:` 會連預設位置 `http://localhost:8888` 的 Config Server，拿掉 `optional:` 則連不到就啟動失敗。[出處](https://docs.spring.io/spring-cloud-config/reference/client.html)

**ConfigMap 這條路**：ConfigMap 是存非機密資料的 API 物件，內容是鍵值對：

*   **怎麼用**：當環境變數、命令列參數，或 volume 裡的設定檔
*   **不保密**：ConfigMap 不提供保密或加密，機密的改用 Secret。[出處](https://kubernetes.io/docs/concepts/configuration/configmap/) 實作見〈K8s 上手：Minikube 與上雲〉。

**怎麼選**：設定只是各環境不同的幾個值，ConfigMap 加 Secret 可能就夠；要設定有版本紀錄，Config Server 配 git 比較合適。

## 斷路器的參數名、重試的四個配件、隔艙、逾時

> 🏠 **生活比喻**
>
> - 斷路器＝**電源總開關**
> - 重試＝**打電話沒接就隔一下再打**，要加退避和抖動
> - 隔艙＝**船艙分隔**

實跑結果見〈韌性模式：Resilience4j 的斷路器、重試與限流〉。

斷路器（circuit breaker，面試常叫熔斷）的三態、隨機指數退避、重試預算見〈系統設計：秒殺與限流〉，這節補 Resilience4j 的參數，以及隔艙與逾時。

> 💡 面試官：斷路器三個狀態怎麼切換？滑動視窗、失敗率門檻、半開試探在 Resilience4j 裡各是哪個參數？

**一句話定義**：斷路器是有限狀態機，三個正常狀態 CLOSED、OPEN、HALF_OPEN，另有三個特殊狀態；呼叫結果存在滑動視窗裡彙總，視窗可選計數型或時間型。[出處](https://resilience4j.readme.io/docs/circuitbreaker)

| 三態的哪一步 | 參數（預設值） | 行為 |
| --- | --- | --- |
| CLOSED 時記帳 | `slidingWindowType`（COUNT_BASED）、`slidingWindowSize`（100） | 計數型彙總最近 N 次呼叫；時間型彙總最近 N 秒 |
| 還不能判斷 | `minimumNumberOfCalls`（100） | 設 10 而只評估了 9 次，9 次全失敗也不會跳開 |
| CLOSED 到 OPEN | `failureRateThreshold`（50）、`slowCallRateThreshold`（100）、`slowCallDurationThreshold`（60000 毫秒） | 失敗率大於等於門檻就轉 OPEN，開始直接拒絕呼叫、不再送出；慢呼叫比例達門檻同樣跳開 |
| OPEN 時 | `waitDurationInOpenState`（60000 毫秒） | OPEN 時以 `CallNotPermittedException` 拒絕呼叫，等待時間過後轉 HALF_OPEN |
| HALF_OPEN 試探 | `permittedNumberOfCallsInHalfOpenState`（10） | 放行設定數量的呼叫，其餘照樣拒絕；試完失敗率或慢呼叫比例仍達門檻就退回 OPEN，都低於門檻就回 CLOSED。Azure 的模式描述是任一失敗就退回，Resilience4j 看的是比例 |

預設所有例外都算失敗；列進 `ignoreExceptions` 的例外既不算失敗也不算成功。[出處](https://resilience4j.readme.io/docs/circuitbreaker) 餘額不足是正確的業務拒絕，要列進去，否則可能把好端端的下游熔斷掉。

> 💡 面試官：重試要配什麼才安全？

**一句話定義**：失敗不是暫時性的就取消並回報；暫時性的才等一下再試，必要時重複，間隔一次比一次長，直到達到最大次數。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry) 安全的重試要四個配件：

*   **上限：**`maxAttempts`（預設 3，含第一次呼叫）；`retryExceptions` 列要重試的例外，`ignoreExceptions` 列不重試的。[出處](https://resilience4j.readme.io/docs/retry)
*   **退避（backoff，間隔越等越久）：**`waitDuration`（預設 500 毫秒，重試之間的固定等待時間）[出處](https://resilience4j.readme.io/docs/retry)，Spring Boot 設定再加 `enableExponentialBackoff: true` 與 `exponentialBackoffMultiplier`。[出處](https://resilience4j.readme.io/docs/getting-started-3)
*   **抖動（jitter，間隔加隨機量，免得大家同時醒來再撞一次）：**`enableRandomizedWait` 與 `randomizedWaitFactor`，和指數退避可以同時開。[出處](https://github.com/resilience4j/resilience4j/blob/v2.4.0/resilience4j-framework-common/src/main/java/io/github/resilience4j/common/retry/configuration/CommonRetryConfigurationProperties.java)
*   **冪等（idempotent，同一件事做幾次結果都一樣）**：不冪等的操作，重試可能讓它被執行不只一次，例如服務處理成功卻沒能送出回應。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry) 入帳這種寫入要帶冪等鍵讓下游去重，做法見〈系統設計：秒殺與限流〉「App 逾時自動重送，怎麼只扣一次」那題。

追問「不用 Resilience4j 行不行」：Spring Framework 7 起核心內建 `@Retryable` 與 `@ConcurrencyLimit`，在設定類別加 `@EnableResilientMethods` 啟用；但沒有斷路器與逾時，這兩樣仍要 Resilience4j。[出處](https://docs.spring.io/spring-framework/reference/core/resilience.html)

> 💡 面試官：隔艙解決什麼？

**一句話定義**：隔艙（bulkhead）名字來自船體的分艙隔板：船身破了只有受損那一艙進水，船不會沉。做法是把應用的元素隔成多個資源池，一個壞了其他照常運作，例如替每個下游服務各配一個連線池。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/bulkhead)

**Resilience4j 的參數**：兩種實作，`SemaphoreBulkhead` 用 Semaphore，`FixedThreadPoolBulkhead` 用有界佇列加固定執行緒池。Semaphore 版是 `maxConcurrentCalls`（預設 25，允許的最大並行執行數）與 `maxWaitDuration`（預設 0，擠不進去時最多卡多久）[出處](https://resilience4j.readme.io/docs/bulkhead)，就是〈Java 並行快答：執行緒池、鎖與並行集合〉的 `Semaphore` 限量放行。

> 💡 面試官：逾時怎麼設？為什麼說逾時比重試更重要？

**一句話定義**：逾時是其他三件的前提。逾時太長，跑斷路器的執行緒可能被卡很久，斷路器才知道操作失敗。[出處](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) 重試同樣要等上一次結束，隔艙名額也會被卡住的呼叫占著。多長：設短一點，但要夠長，讓操作大多數時候能成功。

**Resilience4j 的做法**：TimeLimiter 設逾時時間（`timeoutDuration`）與要不要取消執行中的 future（代表「之後才拿得到結果」的物件；`cancelRunningFuture`），包的是 `CompletionStage` 或 `Future`。[出處](https://resilience4j.readme.io/docs/timeout)

注意：對 `CompletableFuture`，逾時只是讓呼叫端先拿到失敗；它的 `cancel` 不靠中斷來停止處理，底層呼叫還在跑。[出處](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CompletableFuture.html) 真正把呼叫停下來，要靠 HTTP 用戶端自己的連線逾時與讀取逾時。

註解疊加的預設套用順序是 `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) )`，要改就用各自的 `…AspectOrder` 屬性。[出處](https://resilience4j.readme.io/docs/getting-started-3)

查餘額呼叫核心帳務，四件套在 `application.yml` 設完。

*   **Spring Boot 3**：鍵名同下（模組 `resilience4j-spring-boot3`，要有 actuator 與 aop 兩個 starter）[出處](https://resilience4j.readme.io/docs/getting-started-3)
*   **Spring Boot 4**：要換 2.4.0 起的 `resilience4j-spring-boot4`[出處](https://github.com/resilience4j/resilience4j/releases/tag/v2.4.0)[出處](https://repo1.maven.org/maven2/io/github/resilience4j/resilience4j-spring-boot4/)，aop starter 在 Boot 4 改名為 `spring-boot-starter-aspectj`。[出處](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)

```
resilience4j.circuitbreaker:
  instances:
    coreBanking:
      registerHealthIndicator: true
      slidingWindowType: COUNT_BASED
      slidingWindowSize: 100
      minimumNumberOfCalls: 20
      failureRateThreshold: 50
      slowCallDurationThreshold: 1s          # 要比逾時 2s 短，否則慢呼叫先被逾時切掉
      slowCallRateThreshold: 80
      waitDurationInOpenState: 30s
      permittedNumberOfCallsInHalfOpenState: 5
      ignoreExceptions:
        - com.example.bank.InsufficientBalanceException   # 業務拒絕不算失敗
resilience4j.retry:
  instances:
    coreBanking:
      maxAttempts: 3
      waitDuration: 500ms
      enableExponentialBackoff: true
      exponentialBackoffMultiplier: 2
      enableRandomizedWait: true
      retryExceptions:
        - java.io.IOException
        - java.util.concurrent.TimeoutException
      ignoreExceptions:
        - com.example.bank.InsufficientBalanceException
resilience4j.bulkhead:
  instances:
    coreBanking:
      maxConcurrentCalls: 20
      maxWaitDuration: 0
resilience4j.timelimiter:
  instances:
    coreBanking:
      timeoutDuration: 2s
      cancelRunningFuture: true
```

```
@Bulkhead(name = "coreBanking")
@TimeLimiter(name = "coreBanking")
@CircuitBreaker(name = "coreBanking", fallbackMethod = "balanceFallback")
@Retry(name = "coreBanking")
public CompletableFuture<Balance> balance(String account) {
    return CompletableFuture.supplyAsync(() -> coreBankingClient.balance(account), pool);  // 傳自己的池
}

// 斷路器 OPEN 或半開名額用完時進這裡：回上一次快取的餘額
private CompletableFuture<Balance> balanceFallback(String account, CallNotPermittedException e) {
    return CompletableFuture.completedFuture(balanceCache.lastKnown(account));
}
```

> 逾時給每次呼叫一個終點，斷路器數終點、重試等終點、隔艙守名額：沒有逾時，三個都在等一個可能不來的結果

## 三種訊號、拉取模型、一條 trace 怎麼穿過所有服務

> 🏠 **生活比喻**
>
> - 指標、日誌、追蹤＝**體溫數字、病歷、就醫動線**
> - 拉取模型＝**抄表員定時來抄**
> - trace＝**快遞單號**，一路追蹤每一站

實跑結果見〈可觀測性：Micrometer、Prometheus 與 OpenTelemetry〉。

> 💡 面試官：指標、日誌、追蹤怎麼分工？四個黃金訊號是什麼？

**一句話定義**：可觀測性（observability）的定義見〈後端與雲端面試題庫〉。三種訊號：[出處](https://opentelemetry.io/docs/concepts/signals/)

*   **追蹤**（traces）：請求穿過應用的路徑
*   **指標**（metrics）：執行期擷取的量測值
*   **日誌**（logs）：一件事的紀錄

**分工怎麼答**：指標說「有沒有事」，追蹤說「事在哪一段」，日誌說「那一段發生了什麼」。四個黃金訊號「延遲、流量、錯誤、飽和」見〈系統設計：秒殺與限流〉；面試官再追問時補兩點：只能量四個指標就量這四個（限面向使用者的系統）；飽和看的是最受限的那個資源[出處](https://sre.google/sre-book/monitoring-distributed-systems/)，例如網銀 API 的飽和可能是核心帳務連線池使用率，不是 CPU。

> 💡 面試官：Prometheus 為什麼是拉取？Micrometer 跟 Actuator 怎麼把指標吐出來？

**一句話定義：**[出處](https://prometheus.io/docs/introduction/overview/)

*   **資料模型**：多維，時間序列由指標名稱加鍵值對識別
*   **收集方式**：Prometheus 透過 HTTP 去拉取
*   **推送**：要推的話透過中介的 gateway

Micrometer 是中間那層：與供應商無關的可觀測性門面（facade），可以想成可觀測性版的 SLF4J。[出處](https://docs.micrometer.io/micrometer/reference/)

**Actuator 怎麼接：**[出處](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)

*   **自動設定**：Spring Boot Actuator 替 Micrometer 管好相依版本並自動設定
*   **拉取端點**：Prometheus 會去抓取（輪詢）每個應用實例，專案加了 `micrometer-registry-prometheus` 相依，Spring Boot 就提供 `/actuator/prometheus` 端點
*   **批次工作**：存在時間太短、來不及被抓的短命或批次工作用 Pushgateway（中繼站：工作先把指標推給它，Prometheus 再去拉）。

容易漏掉的一步：預設只有 health 端點透過 HTTP 與 JMX 暴露，其他要用 `management.endpoints.web.exposure.include` 打開；端點可能含敏感資訊，開哪些要挑。[出處](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)

```
# application.properties（Spring Boot 4.1）
# 預設只有 health；# 只在行首才算註解，寫在行尾會變成值的一部分
management.endpoints.web.exposure.include=health,info,prometheus
# 預設 0.1；對帳期間全取樣
management.tracing.sampling.probability=1.0
```

> 💡 面試官：分散式追蹤的 trace ID 怎麼從 A 服務傳到 B 服務？OpenTelemetry 在做什麼？

**一句話定義**：A 服務呼叫 B 服務時，A 把 trace ID 與 span ID（span 是一條追蹤裡的一段工作）放進情境（context）；B 用這些值建立屬於同一條 trace 的新 span，把 A 的 span 當父節點。[出處](https://opentelemetry.io/docs/concepts/context-propagation/)

傳播通常由 instrumentation 函式庫（替你在程式裡自動收集遙測資料的函式庫）處理，預設用 W3C TraceContext 規格定義的標頭。

OpenTelemetry 是產生、收集遙測資料的框架，與廠商和工具無關，本身不是可觀測性後端。[出處](https://opentelemetry.io/docs/what-is-opentelemetry/)

**那個標頭長什麼樣：**`traceparent` 標頭識別追蹤系統中傳進來的請求，有四個欄位：[出處](https://www.w3.org/TR/trace-context/)

*   **trace-id**：整個追蹤森林的 ID，16 位元組
*   **parent-id**：呼叫端所知的這個請求的 ID（有些追蹤系統叫 span-id），8 位元組
*   **全零**：兩者全零都是無效值

範例（取自 W3C 規格）：

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
             │  │                                │                └ trace-flags：01 表示呼叫端可能記錄了這條追蹤
             │  │                                └ parent-id：呼叫端這一段（span）的 ID，8 個位元組
             │  └ trace-id：整條追蹤的 ID，16 個位元組，所有服務帶同一個
             └ version：本規格是 00
```

**Spring Boot 這邊：**

*   **自動設定**：Actuator 替 Micrometer Tracing 管好相依版本並自動設定，可接 OpenTelemetry 用 OTLP（OpenTelemetry 自己的傳輸協定）送出[出處](https://docs.spring.io/spring-boot/reference/actuator/tracing.html)
*   **屬性附錄**：`management.tracing.propagation.produce` 預設 `[W3C]`、`management.tracing.sampling.probability` 預設 0.1。[出處](https://docs.spring.io/spring-boot/appendix/application-properties/index.html)

追問：[出處](https://docs.spring.io/spring-boot/reference/actuator/tracing.html)

*   **日誌怎麼跟 trace 對上**：用了 Micrometer Tracing，預設就把關聯 ID 放進日誌，形如 `[traceId-spanId]`
*   **斷鏈原因**：`RestTemplate`、`RestClient` 或 `WebClient` 不是用自動設定的 builder 建立，自動的追蹤傳播就不會生效。

> 指標說有事、追蹤說在哪、日誌說是什麼；三者靠同一個 trace ID 串起來，trace ID 靠 traceparent 標頭傳下去

> 🏠 **生活比喻**
>

> - Serverless＝**計程車**

> 💡 面試官：Service Mesh 是什麼、解決什麼、代價是什麼？

**一句話定義**：服務網格（Service Mesh）把服務間通訊的事從程式碼搬到平台。Istio 是開源的服務網格，透明地疊在既有的分散式應用之上，服務程式碼只需少量修改或不用改；功能包含 mTLS（雙向 TLS，連線兩端都出示憑證驗明身分）、重試、故障轉移，以及所有流量的指標、日誌、追蹤。[出處](https://istio.io/latest/docs/overview/what-is-istio/)

**兩種模式**：實際轉送流量的那層叫資料平面，下設定給它的叫控制平面。Sidecar 模式每個應用旁邊注入一個 Envoy（開源的代理程式）代理，久經實戰，但有資源成本與維運負擔。Ambient 模式 2022 年推出，Istio 1.22 起單叢集情境可用於生產，流量經過每節點一個、只做第四層（傳輸層，看 IP 與埠）的代理，要第七層（應用層，看 HTTP 內容）功能再加 Envoy；分層見〈網路與 HTTP 面試題：三向交握、TLS、REST 對 gRPC〉。[出處](https://istio.io/latest/docs/overview/dataplane-modes/) 預設：安裝設定檔 `default` 裝的是 sidecar 資料平面，ambient 要另選 `ambient` 設定檔。[出處](https://istio.io/latest/docs/setup/additional-setup/config-profiles/)

**代價與選型**：每個 Pod 多一個代理、每一跳多一次轉發，再加一個要維運的控制平面。服務少、語言單一，函式庫可能就夠；服務多、多語言、要全面 mTLS，網格比較划算。

> 💡 面試官：Serverless 適合什麼、不適合什麼？冷啟動是什麼？

**一句話定義**：Lambda 與 ECS、EKS 的三選一見〈後端與雲端面試題庫〉。面試官接著會問生命週期。Init 階段做三件事：啟動所有擴充、啟動 runtime（語言的執行環境，例如 JVM）、執行函式的靜態程式碼。[出處](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)

**冷啟動**：[出處](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)

*   **定義**：下載程式碼與建立環境這前兩步常被稱為冷啟動（cold start），這段時間會計費，也加在整次呼叫的延遲上
*   **算進延遲**：冷啟動與 Init 的初始化程式碼，都算在新環境第一次呼叫的延遲裡
*   **多常發生**：通常不到 1% 的呼叫會碰到，時間從不到 100 毫秒到超過 1 秒。

JVM 啟動與 Spring 初始化都落在 Init，Java 的冷啟動可能偏長；解法之一是 SnapStart：發布版本時先初始化、存成快照，之後從快取的快照恢復新環境，不必從頭初始化。[出處](https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html)

**適合與不適合**：適合事件驅動、流量一陣一陣、工作短而獨立，例如對帳完發通知。不適合的從生命週期推：長時間執行（一般函式單次最長 15 分鐘[出處](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html)）、要常駐連線或本機狀態（環境會被凍結與回收）、對延遲敏感又流量稀疏（冷啟動比例高）。

> 💡 面試官：十二要素裡的設定、日誌、無狀態行程三條怎麼答？

| 要素 | 主張 |
| --- | --- |
| III 設定 | 設定與程式碼嚴格分離：設定隨部署大幅變動，程式碼不會；設定存在環境變數[出處](https://12factor.net/config) |
| XI 日誌 | 日誌當事件流；應用不管輸出流送去哪、存在哪，不自己寫或管理日誌檔；每個行程把事件流不緩衝地寫到 stdout[出處](https://12factor.net/logs) |
| VI 行程 | 行程無狀態、彼此不共享（share-nothing），要持久的資料存進有狀態的後端服務，通常是資料庫；黏性工作階段（sticky sessions）違反十二要素，永遠不該使用或依賴；工作階段資料適合放 Redis 這類有到期機制的存放區[出處](https://12factor.net/processes) |

追問「登入狀態放哪」：外部存放區或權杖，比較見〈認證與安全面試題：JWT、OAuth 2.0、OIDC 與密碼保存〉。

> 設定放環境、日誌寫 stdout、行程不留狀態：三條都在讓「換一台跑」變成不用想的事

### 重點整理

*   ESB 把轉換、編排、業務規則放在中間層；API Gateway 管入口，也會合併回應、轉協定，但業務規則留在服務：「聰明端點、笨管線」。
*   服務發現差在誰查名冊：用戶端模式跳數少但綁註冊表，伺服器端模式用戶端簡單但多一跳；K8s 的一般 Service 是伺服器端，headless Service 例外。
*   斷路器參數對三態：`slidingWindowSize`／`minimumNumberOfCalls` 記帳，`failureRateThreshold`／`slowCallRateThreshold` 跳 OPEN，`waitDurationInOpenState` 等多久，`permittedNumberOfCallsInHalfOpenState` 試幾個。
*   重試四配件：`maxAttempts`、指數退避、隨機抖動、下游冪等；隔艙用 `maxConcurrentCalls` 分池；逾時是前提，預設順序 Retry 包 CircuitBreaker 包 TimeLimiter 包 Bulkhead。
*   Prometheus 走 HTTP 拉取，短命批次用 Pushgateway；Micrometer 是可觀測性版的 SLF4J；Actuator 預設只暴露 health。
*   trace ID 靠 `traceparent` 傳：version、trace-id（16 位元組）、parent-id（8 位元組）、trace-flags；Spring Boot 4.1 預設送 W3C 格式、取樣 0.1。
*   Istio 的 default 設定檔用 sidecar；Lambda 冷啟動是下載程式碼加建環境；十二要素：設定放環境變數、日誌寫 stdout、行程無狀態。

## 隨堂測驗

**Q1. 團隊在 API Gateway 上陸續加了「VIP 客戶手續費打折」「超過限額改走人工審核」這類規則。從「聰明端點、笨管線」的觀點看，問題在哪？**

- (A) 業務規則進了管線，Gateway 容易變成新的 ESB
- (B) 沒問題，Gateway 本來就該集中所有業務規則
- (C) 這只是效能問題，規則放在 Gateway 或服務裡都不影響架構
- (D) Gateway 技術上無法判斷客戶等級

<details><summary>看答案</summary>

**答案：(A)** Gateway 模式本來就包含路由、合併回應、協定轉換；界線在業務規則，規則該留在服務裡，否則聰明又回到管線上。

</details>

**Q2. Spring Boot 服務在 Kubernetes 上只對 http://core-banking 發請求，由叢集轉到某個 Pod（一般 Service，不是 headless）。這是哪一種服務發現？**

- (A) 伺服器端模式，由叢集的代理查名冊再轉發
- (B) 用戶端模式，因為請求是從用戶端程式發出
- (C) 用戶端模式，叢集把 Pod IP 清單交給應用挑
- (D) 都不是，Kubernetes 沒有服務發現機制

<details><summary>看答案</summary>

**答案：(A)** 差別在誰查名冊；Kubernetes 在每台主機跑代理，當作伺服器端發現的路由器。headless Service 才是把 Pod 位址交給用戶端自己挑。

</details>

**Q3. 斷路器設 slidingWindowSize 100、minimumNumberOfCalls 20、failureRateThreshold 50。服務剛啟動，前 10 次呼叫全部失敗，斷路器現在是什麼狀態？**

- (A) CLOSED，呼叫數還不夠算失敗率
- (B) OPEN，失敗率 100% 已經超過 50% 的門檻
- (C) HALF_OPEN，失敗太多先進入試探階段
- (D) FORCED_OPEN，啟動期間的失敗會強制打開

<details><summary>看答案</summary>

**答案：(A)** 設 10 而只評估了 9 次，即使全失敗也不會跳開；最少呼叫數沒到，失敗率不算數。

</details>

**Q4. 查餘額的斷路器把 InsufficientBalanceException（餘額不足）列進 ignoreExceptions，主要是為了什麼？**

- (A) 業務拒絕不代表下游壞了，不該讓它熔斷
- (B) 讓餘額不足時自動重試，直到帳戶餘額足夠為止
- (C) 讓餘額不足的呼叫改算進慢呼叫比例裡
- (D) 讓例外被吞掉，前端就不會看到錯誤訊息

<details><summary>看答案</summary>

**答案：(A)** 預設所有例外都算失敗，列進忽略清單的既不算失敗也不算成功；例外照樣拋給呼叫端。

</details>

**Q5. 入帳 API 呼叫下游逾時，重試後帳戶多了一筆相同的入帳。最可能的原因與解法是什麼？**

- (A) 第一次已成功只是回應遺失，要用冪等鍵去重
- (B) 重試間隔太短，把 waitDuration 拉長就不會重複
- (C) 斷路器沒打開，打開後就能擋掉重複的入帳
- (D) maxAttempts 太大，改成 2 次就不會重複入帳

<details><summary>看答案</summary>

**答案：(A)** 這正是服務處理成功卻沒能送出回應的情況；間隔與次數只影響多快、多少次，不冪等的寫入重試一次就可能重複。

</details>

**Q6. 下游完全不回應、連線一直掛著，而呼叫端只設了斷路器、重試、隔艙，沒有設任何逾時。會發生什麼事？**

- (A) 呼叫不結束，三件套都等不到結果、名額被占住
- (B) 斷路器會因為沒有回應而立刻跳到 OPEN 狀態
- (C) 重試會在固定間隔後自動送出第二次呼叫
- (D) 隔艙會自動把卡住的呼叫踢掉、釋出名額

<details><summary>看答案</summary>

**答案：(A)** 三件套都要等「呼叫結束」才能動作；逾時太長，跑斷路器的執行緒會被卡很久才知道操作失敗。

</details>

**Q7. 對帳前的檢查批次跑 20 秒就結束，Prometheus 每 1 分鐘來拉一次指標，常常整次執行都沒被抓到。該怎麼做？**

- (A) 改用 Pushgateway，批次結束前把指標推上去
- (B) 把 Prometheus 的拉取間隔改成每 1 秒一次
- (C) 在批次裡寫日誌檔，讓 Prometheus 去讀日誌檔
- (D) 把批次改成永不結束的常駐行程等它來拉

<details><summary>看答案</summary>

**答案：(A)** Prometheus 走 HTTP 拉取；存在時間不夠長、來不及被抓的短命或批次工作，用 Pushgateway 把指標交給 Prometheus。

</details>

**Q8. 服務已加 micrometer-registry-prometheus，但打 /actuator/prometheus 回 404，/actuator/health 正常。最可能的原因是？**

- (A) 預設只暴露 health，要另外設定打開
- (B) Prometheus 端點只能透過 JMX 存取，HTTP 打不到
- (C) 要先把追蹤取樣率設成 1.0 才會產生任何指標
- (D) Micrometer 只支援推送模式，不提供拉取端點

<details><summary>看答案</summary>

**答案：(A)** Actuator 預設只有 health 透過 HTTP 與 JMX 暴露，其他端點要用 management.endpoints.web.exposure.include 打開；取樣率是追蹤的設定，與指標端點無關。

</details>

**Q9. A 服務收到帶 traceparent 的請求，處理時再呼叫 C 服務。A 送給 C 的 traceparent 裡，哪個欄位維持不變、哪個要換？**

- (A) trace-id 不變，parent-id 換成 A 這段的
- (B) trace-id 每一跳換新的，parent-id 原封不動轉送
- (C) 兩個欄位都維持不變，整個標頭原樣轉送
- (D) 兩個欄位都換新，每一跳都算一條新追蹤

<details><summary>看答案</summary>

**答案：(A)** trace-id 是整條追蹤的 ID，所有服務帶同一個；parent-id 是呼叫端所知的這個請求的 ID，下游建立新 span、把上游的 span 當父節點。

</details>

**Q10. 網銀服務把登入後的使用者資料放在行程記憶體，靠負載平衡的黏性工作階段把同一使用者導回同一台。依十二要素第 VI 條，問題在哪？**

- (A) 行程該無狀態，工作階段應放外部存放區
- (B) 沒問題，負載平衡器支援黏性工作階段就符合
- (C) 問題在設定：工作階段逾時應該放環境變數裡
- (D) 問題在日誌：工作階段內容應該寫到 stdout

<details><summary>看答案</summary>

**答案：(A)** 十二要素：行程無狀態且不共享，黏性工作階段永遠不該使用或依賴，工作階段資料適合放 Redis 這類有到期機制的存放區。

</details>
