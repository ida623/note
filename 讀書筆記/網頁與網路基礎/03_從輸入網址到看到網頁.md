# 03. 從輸入網址到看到網頁

**沿著一次瀏覽流程，串起 URL、DNS、連線、HTTP、伺服器處理與瀏覽器渲染。**

### 讀完這課你會

*   依序說出從輸入 URL 到畫面出現的主要階段
*   理解 DNS、傳輸連線與 TLS 各自解決的問題

*【先看全程】*

## 一個 Enter 鍵，啟動一條供應鏈

```
輸入 URL
  → 解析 URL 與檢查快取
  → DNS 解析
  → 建立傳輸與安全連線
  → 傳送 HTTP 請求
  → 伺服器處理
  → 接收 HTTP 回應
  → 解析資源、版面配置、繪製
  → 持續載入與互動
```

實際流程會因快取、Service Worker（瀏覽器裡替網頁攔截請求、離線也能回應的背景程式）、代理伺服器、CDN、HTTP 版本與既有連線而縮短或改道。

*【第一站】*

## 瀏覽器解析 URL

以 `https://www.example.com:443/products?q=book#reviews` 為例：

| 名稱 | 內容 | 是否傳給伺服器 |
| --- | --- | --- |
| Scheme | https | 看版本：直接連伺服器時 HTTP/1.1 不會出現在請求行，瀏覽器只用它決定連線方式與是否加密；HTTP/2 與 HTTP/3 則以 `:scheme` 偽標頭（pseudo-header，以冒號開頭、協定自己用的標頭欄位）送出[RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.1)[RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.3.1) |
| Host | www.example.com | 會 |
| Port | 443 | 否（用於建立連線；非預設埠會跟著出現在 Host 標頭，HTTP/2 與 HTTP/3 則出現在 `:authority` 偽標頭） |
| Path | /products | 會 |
| Query | q=book | 會 |
| Fragment | reviews | 不會隨請求送出，由瀏覽器端使用 |

瀏覽器也可能先檢查 HSTS（HTTP Strict Transport Security，讓瀏覽器記住「這個網站以後一律走 HTTPS」的機制）、安全政策、HTTP 快取及 Service Worker，判斷是否升級為 HTTPS、直接使用快取，或由本機程式攔截處理。

*【找到目的地】*

## DNS 解析與快取

若尚無可用的解析結果，瀏覽器會透過作業系統向設定的 DNS 解析器查詢。瀏覽器、作業系統與遞迴解析器都可能已有快取；若沒有，遞迴解析器再向根、TLD 與權威名稱伺服器取得答案。

DNS 可能回傳多個 IPv4 或 IPv6 位址，瀏覽器會依網路狀況嘗試連線。大型網站的 DNS 也可能依地點與服務狀態，把使用者導向不同 CDN 或資料中心。

*【建立通道】*

## TCP、QUIC 與 TLS 不一定照同一套劇本

使用 HTTP/1.1 或 HTTP/2 時，瀏覽器通常先以 TCP 三向交握建立連線：

```
用戶端 → 伺服器：SYN
伺服器 → 用戶端：SYN + ACK
用戶端 → 伺服器：ACK
```

若是 HTTPS，接著進行 TLS 交握，協商加密參數、驗證憑證並建立工作階段金鑰。「先 TCP 三向交握、再 TLS 交握」是 HTTP/1.1 與 HTTP/2 的劇本；HTTP/3 透過 QUIC 建立連線，傳輸與 TLS 1.3 的安全性合在同一套交握裡，不會先做獨立的 TCP 三向交握[出處](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Evolution_of_HTTP)[RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html)。TLS 與 HTTP/3 的細節以〈HTTP 與 HTTPS〉為主。

> 📝 查證更正：原筆記寫「（HTTPS）TCP 三次握手完成後，會進行 TLS 握手」，查證後補充：這是 HTTP/1.1 與 HTTP/2 的流程；HTTP/3 走 QUIC，連線建立與 TLS 1.3 整合在一起，沒有獨立的 TCP 交握。QUIC 與 TLS 1.3 的關係見 RFC 9001：「This document describes how QUIC [QUIC-TRANSPORT] is secured using TLS [TLS13].」「QUIC carries TLS handshake data in CRYPTO frames」

*【提出要求】*

## 送出 HTTP Request

```
GET /products?q=book HTTP/1.1
Host: www.example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session=...
```

方法與路徑表達要取得的資源，標頭帶上可接受格式、壓縮方式、語言、快取條件及登入資訊等。敏感資料不應因為有 HTTPS 就任意放進 URL，因為 URL 仍可能出現在瀏覽歷史、日誌或分析系統中。

*【網站後場】*

## 伺服器如何處理請求？

請求可能先抵達 CDN、負載平衡器或反向代理，再由 Web 伺服器處理。靜態檔案可直接回傳；動態內容則可能交給應用程式進行路由、權限檢查、商業邏輯、快取及資料庫存取。

```
瀏覽器
  → CDN／負載平衡器
  → Nginx 等反向代理
  → 應用程式
  → 快取／資料庫／其他服務
```

這些元件不是每個網站都必備。小型靜態網站可能由 CDN 直接回應，大型系統則可能經過多層服務。

*【收到包裹】*

## HTTP Response 告訴瀏覽器怎麼處理

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: max-age=300

<!doctype html>...
```

狀態碼說明結果，`Content-Type` 指出內容格式，快取標頭決定日後能否重用。回應也可能是 301/302 重新導向、304 使用快取，或 4xx、5xx 錯誤。

*【從文字變畫面】*

## 瀏覽器渲染不是「收到整頁才開始」

1.  逐步解析 HTML，建立文件物件模型（DOM）。
2.  發現 CSS、JavaScript、字型與圖片後，排程額外請求。
3.  解析 CSS，建立 CSS 物件模型（CSSOM）。
4.  結合可見內容與樣式，形成渲染所需結構。
5.  進行版面配置（Layout），計算尺寸與位置。
6.  繪製（Paint）並合成（Composite）畫面圖層。

JavaScript 可能修改 DOM 或樣式，也可能延後解析；CSS、字型與圖片的載入狀態也會影響首次顯示與版面穩定。瀏覽器通常能邊接收、邊解析、邊載入，而非等待所有資料到齊。

單頁應用程式（SPA）只在第一次載入走完這整條流程；之後切換頁面由前端路由只換內容、不重新載入整頁，見〈Ajax、SPA 與路由〉。

*【第一次之後】*

## 快取、連線重用與 CDN 讓後續更快

*   **HTTP 快取**：直接使用尚未過期的資源，或用 ETag 等條件向伺服器確認。
*   **連線重用**：在同一連線上處理後續請求，減少重建連線成本。
*   **CDN**：從離使用者較近的節點提供可快取內容。
*   **壓縮**：降低 HTML、CSS、JavaScript 等文字資源的傳輸量。

`Connection: keep-alive` 是 HTTP/1.x 常見概念；HTTP/2 與 HTTP/3 的連線管理方式不同，不應只靠這個標頭理解所有版本。

### 重點整理

*   URL 解析、DNS 與連線分別回答「要什麼、去哪裡、怎麼安全抵達」。
*   請求可能穿過 CDN、反向代理與應用程式，再以 HTTP 回應回傳。
*   瀏覽器收到 HTML 後仍要取得相依資源、建立 DOM/CSSOM、配置並繪製。

- (C) 處理 HTTP 回應

**Q3. 使用 HTTP/2 over HTTPS 時，常見的連線順序是什麼？**

- (A) TCP 交握、TLS 交握、HTTP 請求
- (B) DNS 回應、畫面繪製、TCP 交握
- (C) HTTP 請求、TCP 交握、TLS 交握
- (D) TLS 交握、DNS 查詢、解析 URL

<details><summary>看答案</summary>

**答案：(A)** 取得位址後，HTTP/2 常先建立 TCP，再完成 TLS，才傳送受保護的 HTTP 訊息。

</details>

**Q4. HTTP/3 為何不需要先做 TCP 三向交握？**

- (A) 它使用以 UDP 為基礎的 QUIC，連線建立與 TLS 1.3 合在同一套交握
- (B) 它沿用 HTTP/1.1 的 keep-alive 連線
- (C) 它把 TLS 交握提前到 DNS 查詢時完成
- (D) 它只在既有的 TCP 連線上多工

<details><summary>看答案</summary>

**答案：(A)** QUIC 以 UDP 為底層並整合 TLS 1.3，不需要獨立的 TCP 交握；其餘選項是別的機制。

</details>

**Q5. 動態頁面請求抵達伺服器端後，哪項工作最可能發生？**

- (A) 應用程式執行路由、權限檢查與資料查詢
- (B) CDN 節點重新產生 TLS 憑證
- (C) 負載平衡器直接改寫回應的 HTML 內容
- (D) 反向代理替資料庫建立索引

<details><summary>看答案</summary>

**答案：(A)** 動態內容通常由應用程式依請求執行邏輯並組成回應；CDN、負載平衡器與代理不負責這些工作。

</details>

**Q6. Content-Type 回應標頭有什麼作用？**

- (A) 告訴接收端內容的媒體類型
- (B) 告訴接收端內容的壓縮方式
- (C) 指定回應可以被快取多久
- (D) 宣告伺服器支援的 HTTP 版本

<details><summary>看答案</summary>

**答案：(A)** 媒體類型是 Content-Type；壓縮方式是 Content-Encoding，快取時間是 Cache-Control。

</details>

**Q7. 瀏覽器的 Layout 階段主要做什麼？**

- (A) 計算元素的尺寸與位置
- (B) 把 HTML 解析成 DOM 樹
- (C) 把樣式表解析成 CSSOM
- (D) 把圖層合成最終畫面

<details><summary>看答案</summary>

**答案：(A)** DOM 與 CSSOM 準備好之後，Layout 決定幾何配置；合成是更後面的階段。

</details>

**Q8. CDN 通常如何改善載入速度？**

- (A) 從離使用者較近的節點提供可快取內容
- (B) 把所有動態請求改成靜態檔案
- (C) 讓瀏覽器跳過 DNS 查詢
- (D) 把 TCP 連線升級成 QUIC

<details><summary>看答案</summary>

**答案：(A)** CDN 將內容分布到多個節點，縮短傳輸距離並分擔來源站負載；它不會改變請求本身的性質。

</details>
