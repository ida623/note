# 10. GCP 網路位址與子網路

> 來源：[筆記平台 · 雲端 AWS 與 GCP](https://hhtim.github.io/notes-platform/cloud/#/lesson/gcp-networking)　第 10 課 / 共 18 課 · 約 9 分鐘

**從 CIDR 與子網路遮罩的通用讀法出發，理解最長前綴比對、Google Cloud 的保留位址與子網路大小限制，以及 Cloud NAT。**

### 讀完這課你會

*   看懂 10.0.0.0/24 這種寫法
*   算出子網路能用幾個位址
*   說出路由表多條對得上時哪條贏
*   知道沒有對外位址的 VM 怎麼連外

*【先看懂那條斜線】*

## 一個位址加一個斜線數字，就圈出一整段範圍

一個 IPv4 位址是 32 個位元（bit，電腦裡最小的資料單位，只有 0 和 1 兩種值），習慣上切成四段、每段用十進位寫出來，例如 `10.0.0.7`。

但規劃網路時要講的往往不是「某一個位址」，而是「某一段連續的位址」。這時候就用 CIDR 寫法：位址後面加一條斜線和一個數字，例如 `10.0.0.0/24`。（CIDR＝Classless Inter-Domain Routing，無類別跨網域路由。名字聽起來很大，實際上就是這個斜線寫法。網路課口語講的「網段」、AWS 文件寫的「CIDR 區塊」，都是指這樣一段位址。）

> 斜線後面的數字＝前面幾個位元是固定的「網路」部分；剩下的位元才可以變，用來編號裡面的機器。

所以 `10.0.0.0/24` 的意思是：32 個位元裡，前 24 個固定，剩下 8 個可以自由變化。8 個位元能排出 2 的 8 次方＝256 種組合，也就是 `10.0.0.0` 到 `10.0.0.255` 這 256 個位址。

同一件事還有另一種老寫法叫**子網路遮罩**（subnet mask）：把「前 24 個位元固定」畫成 `255.255.255.0`。兩種寫法講的是同一件事，`/24` 只是比較短。

| 寫法 | 固定的位元數 | 可變的位元數 | 位址總數 | 等效的子網路遮罩 |
| --- | --- | --- | --- | --- |
| `/8` | 8 | 24 | 16,777,216 | 255.0.0.0 |
| `/16` | 16 | 16 | 65,536 | 255.255.0.0 |
| `/24` | 24 | 8 | 256 | 255.255.255.0 |
| `/28` | 28 | 4 | 16 | 255.255.255.240 |
| `/29` | 29 | 3 | 8 | 255.255.255.248 |
| `/32` | 32 | 0 | 1 | 255.255.255.255 |

> 💡 最容易記反的一點：**斜線數字越大，範圍越小**。因為固定的位元越多，能自由變化的就越少。`/8` 是一千六百多萬個位址，`/32` 只剩一個。想成綁繩子——綁得越緊，能動的空間越少。

*【兩條路都對得上】*

## 最長前綴比對：誰比較精確，就聽誰的

路由表是一張「要去哪裡、下一站走哪條路」的對照表。麻煩的是同一個目的地常常會同時符合好幾條規則。假設表上有這兩條：

```
目的地 0.0.0.0/0       → 走對外閘道     （任何位址都符合）
目的地 10.0.5.0/24     → 走內部通道     （只有這 256 個位址符合）
```

現在要送一個封包到 `10.0.5.7`。兩條都對得上——第一條因為它涵蓋全部位址，第二條因為 `10.0.5.7` 正好落在那 256 個裡面。該走哪條？

> 規則叫**最長前綴比對**（Longest Prefix Match）：挑斜線數字最大、也就是講得最精確的那一條。這裡 `/24` 比 `/0` 精確，所以走內部通道。

「前綴」（prefix）就是前面那段固定不變的位元；比得越長，代表這條規則指名得越具體。這是網路設備共通的作法，不是哪一家雲端獨有的。

Google Cloud 把這件事叫「最具體的目的地」（most specific destination），不叫「最長前綴比對」，兩種講法指的是同一個規則：在適用的靜態或動態路由裡，挑涵蓋封包目的位址、而且最具體的那一條[出處](https://docs.cloud.google.com/vpc/docs/routes)。

*   例外是「政策型路由」（Policy-based routes）：它不使用最長前綴比對[出處](https://docs.cloud.google.com/vpc/docs/policy-based-routes)

如果兩條路由一樣精確呢？那就再比優先順序值（priority）：從 `0`（最高優先）到 `65535`（最低優先）[出處](https://docs.cloud.google.com/vpc/docs/using-routes)——數字小的贏，跟一般「第一名是 1」的直覺一樣。

*【不是全部都歸你】*

## Google Cloud 每個子網路先拿走四個位址

切好一個子網路之後，裡面的位址並不是全部都能配給機器。Google Cloud 在每個子網路的主要 IPv4 範圍裡固定保留四個，以 `10.1.2.0/24` 為例：

| 位置 | 這個範圍裡是哪一個 | 用途 |
| --- | --- | --- |
| 第一個 | `10.1.2.0` | 網路位址，代表整個網段本身 |
| 第二個 | `10.1.2.1` | 預設閘道（default gateway，機器要出這個網段時的出口） |
| 倒數第二個 | `10.1.2.254` | Google 保留，供日後使用 |
| 最後一個 | `10.1.2.255` | 廣播位址（broadcast，一次送給網段內全部機器用的位址） |

所以一個 `/24` 雖然有 256 個位址，實際能配出去的是 252 個[出處](https://docs.cloud.google.com/vpc/docs/subnets)。

這個數字每家雲端不一樣，換平台時不能沿用。AWS 保留的是**五個**：「每個子網路 CIDR 區塊中的前四個 IP 位址與最後一個 IP 位址無法供你使用」，多出來的那一個是保留給 VPC 的 DNS 伺服器[出處](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)。同樣一個 `/24`，在 Google Cloud 能配 252 個，在 AWS 只能配 251 個。

*【切太小會被擋】*

## 子網路的上下限：最小 /29

知道要保留四個之後，就看得懂為什麼有最小值。Google Cloud 的規定是：「最小的主要或次要範圍大小是八個 IPv4 位址。換句話說，你能使用的最長子網路遮罩是 `/29`。」[出處](https://docs.cloud.google.com/vpc/docs/subnets)

`/29` 是 8 個位址，扣掉保留的四個，只剩 4 個能配給機器。再往下切一級是 `/30`、只有 4 個位址，四個保留位址就把它佔滿了，一台機器都配不到——所以下限停在 `/29` 是有道理的。

另一端的上限有但書：

*   能用的最短子網路遮罩是 `/4`，但大多數 `/4` 的位址範圍會被額外的驗證擋下，建不出這麼大的子網路
*   為了少挑到無效的子網路範圍，建議子網路最大只到 `/8`

所以實務上可以把 `/8` 當成上限來規劃，`/4` 是理論值[出處](https://docs.cloud.google.com/vpc/docs/subnets)。

> 💡 規劃時的順序建議反過來想：先估這個子網路以後最多會放幾台機器，加上保留的四個，再往上找最接近的那個斜線數字。子網路建好之後要改範圍比一開始留寬一點麻煩得多。

*【沒有對外位址也要連得出去】*

## Cloud NAT 讓私有的 VM 單向連外

為了安全，很多 VM 刻意不給它外部 IP 位址，外面就完全找不到它。但這種機器還是需要主動連出去——抓系統更新、呼叫外部的 API 都要。Cloud NAT 就是補這一段的代管服務。

Cloud NAT 分成兩種：對外連網際網路的叫 **Public NAT**；另一種 Private NAT 是做私有網路之間的位址轉換，不走網際網路。Public NAT 讓沒有外部 IPv4 位址的 Google Cloud 資源，能夠與網際網路上的 IPv4 目的地通訊。Cloud NAT 的做法是替前往網際網路、虛擬私有雲（VPC）網路、地端網路與其他雲端供應商網路的**對外**流量做網路位址轉換[出處](https://docs.cloud.google.com/nat/docs/overview)。（網路位址轉換＝NAT，出去的時候把來源的私有位址換成一個對外位址，回來的時候再換回去，〈VPC 網路架構〉講 AWS 時已經出現過。）

兩個特性值得記住，因為都跟直覺不太一樣：

*   **它不是一台你要自己顧的機器。**：Cloud NAT 是分散式、軟體定義的代管服務，不是靠一台代理虛擬機或設備在做。你不會看到一台「NAT 主機」跑在那裡，也不需要替它擴充規格或做高可用，那些是 Google 在底層處理的。
*   **它只放行回程，不放行主動連入。**：Cloud NAT 只替已建立連線的入站回應封包做位址轉換，不允許未經請求的入站連線。所以裝了 Cloud NAT 不等於把 VM 對外開了一個門，外面仍然連不進來。

對照〈VPC 網路架構〉的 AWS：兩邊解決的是同一個問題，做法的分工不同。AWS 的 NAT Gateway 是你自己在某個公開子網路裡建出來的一個資源（見〈VPC 網路架構〉）；Cloud NAT 則沒有對應的實體或虛擬機可以指著看，它不是靠代理虛擬機或設備在做。共同點是兩者都只讓內部主動往外，不讓外面主動連進來。

### 重點整理

*   CIDR 的斜線數字代表前面幾個位元固定；數字越大、範圍越小，`/24` 是 256 個位址。
*   子網路遮罩（`255.255.255.0`）與 CIDR（`/24`）是同一件事的兩種寫法。
*   路由表有多條都符合時，挑最精確的那條（最長前綴比對）；一樣精確才比優先順序值，數字小的贏。
*   Google Cloud 每個子網路保留四個位址：網路位址、預設閘道、倒數第二個、廣播位址；AWS 保留五個。
*   子網路最小 `/29`（8 個位址、只剩 4 個可配），上限實務上抓 `/8`。
*   Cloud NAT 讓沒有外部位址的 VM 主動連外，是分散式的代管服務，而且不允許外面主動連進來。

## 隨堂測驗

**Q1. 10.0.0.0/24 這個寫法涵蓋多少個 IPv4 位址？**

- (A) 256 個，從 10.0.0.0 到 10.0.0.255
- (B) 24 個，斜線後面的數字就是位址數量
- (C) 16,777,216 個，因為斜線後面的 24 個位元可以自由變化
- (D) 1 個，斜線後面的數字是這台機器的編號

<details><summary>看答案</summary>

**答案：(A)** 斜線數字是「固定的位元數」不是可變的：32 減 24 剩 8 個位元可變，2 的 8 次方就是 256。

</details>

**Q2. /16 和 /28 相比，哪一個涵蓋的位址範圍比較大？**

- (A) /16，斜線數字越小，固定的位元越少、可變的就越多
- (B) /28，斜線數字越大代表範圍越大
- (C) 一樣大，斜線數字只影響寫法，不影響實際範圍
- (D) 要看斜線前面的位址是什麼才判斷得出來

<details><summary>看答案</summary>

**答案：(A)** 固定的位元越多，能自由變化的就越少：/16 有 16 個可變位元，/28 只剩 4 個。

</details>

**Q3. 子網路遮罩 255.255.255.0 等於下列哪一個 CIDR 寫法？**

- (A) /24
- (B) /8
- (C) /32
- (D) /255

<details><summary>看答案</summary>

**答案：(A)** 255.255.255.0 代表前面三段共 24 個位元固定，就是 /24；兩種寫法講的是同一件事。

</details>

**Q4. 路由表裡同時有 0.0.0.0/0 與 10.0.5.0/24 兩條，要送封包到 10.0.5.7 時會走哪一條？**

- (A) 走 10.0.5.0/24，兩條都符合時挑最精確、前綴最長的那一條
- (B) 走 0.0.0.0/0，因為涵蓋範圍越大的規則優先權越高
- (C) 走 0.0.0.0/0，因為它是預設路由，一定最先被比對
- (D) 兩條都走，封包會被複製成兩份分別送出去

<details><summary>看答案</summary>

**答案：(A)** 最長前綴比對的規則是「誰講得最具體就聽誰的」，不是誰涵蓋得廣誰贏。

</details>

**Q5. 兩條路由的目的地一樣精確時，Google Cloud 靠什麼決定走哪一條？**

- (A) 比優先順序值，0 是最高優先、65535 是最低
- (B) 比優先順序值，數字越大越優先
- (C) 比建立時間，先建立的那一條優先
- (D) 隨機挑一條，所以應該避免讓這種情況出現

<details><summary>看答案</summary>

**答案：(A)** 一樣精確才輪到優先順序值，而且數字小的贏——0 最高、65535 最低。

</details>

**Q6. 在 Google Cloud 建一個 /29 的子網路，實際上能配給機器的位址有幾個？**

- (A) 4 個，8 個位址裡有 4 個被保留走了
- (B) 6 個，跟一般網路一樣只扣掉網路位址與廣播位址
- (C) 8 個，整段都能配出去
- (D) 2 個，只有中間那兩個能用

<details><summary>看答案</summary>

**答案：(A)** Google Cloud 每個子網路固定保留四個：網路位址、預設閘道、倒數第二個與廣播位址。

</details>

**Q7. 同樣切一個 /24，Google Cloud 能配出 252 個位址、AWS 只能配 251 個，差別在哪？**

- (A) AWS 保留五個、Google Cloud 保留四個，AWS 多留一個給 VPC 的 DNS 伺服器
- (B) AWS 的 /24 只有 255 個位址，本來就比 Google Cloud 少一個
- (C) Google Cloud 不保留廣播位址，AWS 有保留
- (D) AWS 會把最後一個位址留給 NAT Gateway 使用

<details><summary>看答案</summary>

**答案：(A)** 兩邊都保留網路位址、閘道、一個供日後使用的位址與廣播位址；AWS 另外多留一個給 VPC 的 DNS 伺服器（範圍起點加二），所以可用數少一個。

</details>

**Q8. 替一台沒有外部 IP 位址的 VM 設定 Cloud NAT 之後，下列哪個敘述正確？**

- (A) 它可以主動連到網際網路，但網際網路仍然無法主動連進來
- (B) 它會因此取得一個外部 IP 位址，外面可以直接連進來
- (C) 進出都通了，等於把它搬進公開子網路
- (D) 它只連得到同一個 VPC 裡的其他資源，還是連不到網際網路

<details><summary>看答案</summary>

**答案：(A)** Cloud NAT 只替已建立連線的回應封包做轉換，不允許未經請求的入站連線。

</details>
