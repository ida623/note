## B+ 樹、叢集索引與二級索引

答題公式：先一句話定義，再講差別與取捨，最後補一句版本或實務註記。

> 💡 面試官：索引是什麼？為什麼用 B+ 樹，不用雜湊或二元樹？

**一句話定義**：索引是資料表旁邊另外維護的一份排序好的目錄，讓資料庫不用逐列掃描就能找到目標資料列。MySQL 的主鍵、唯一鍵、一般索引都存成 B-tree（多路平衡樹，MySQL 統稱 B-tree；面試常說的 B+ 樹是它把資料放在葉節點的變形）[出處](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html)。

**為什麼不是二元樹**：B-tree 的一個節點可以有很多個子節點，不像二元樹每個節點只能有兩個[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_b_tree)。InnoDB 一個索引頁預設 16KB[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)，一頁能放很多個鍵，每往下一層容量就乘上一頁的鍵數，所以樹很矮——從根到葉只要讀少少幾頁。頁（page）正是 InnoDB 在硬碟與記憶體之間一次搬動的資料單位[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_page)，讀幾頁就是幾次 I/O，這是「適合磁碟」的意思。

**為什麼不是雜湊**：雜湊索引只能做等號比對，不能做範圍查詢、不能幫 ORDER BY 排序、也只能拿整把鍵去查[出處](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)；B-tree 隨時保持排序，等號與範圍（大於、小於、BETWEEN）都能用[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_b_tree)。

> 💡 面試官：InnoDB 的叢集索引與二級索引差在哪？回表是什麼？

**一句話定義**：每張 InnoDB 資料表都有一個叫叢集索引（clustered index；這裡的「叢集」是資料列聚在索引裡的意思，跟 Redis 叢集那種多台機器無關）的特殊索引，資料列本身就存在它的葉節點裡；有主鍵就拿主鍵當叢集索引，沒有主鍵就拿第一個所有欄位皆 NOT NULL 的唯一索引，兩者都沒有時 InnoDB 自己生一個隱藏的 `GEN_CLUST_INDEX`[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。

**差別**：叢集索引之外的索引都叫二級索引（secondary index），它的每一筆記錄除了被索引的欄位，還帶著那一列的主鍵值；InnoDB 拿這個主鍵值再到叢集索引裡找出整列[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)——這第二趟就是「回表」。所以走二級索引查一列要找兩棵樹，走主鍵只要一棵。

> 主鍵越長，每一個二級索引都要跟著變胖——所以主鍵要短

> 💡 面試官：主鍵為什麼建議用自動遞增整數，不用 UUID？

三個理由：

*   **沒有天然主鍵**：沒有天然的唯一非空欄位時，建議加一個自動遞增欄位當主鍵[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)。
*   **主鍵會複製進二級索引**：主鍵值會被複製進每一個二級索引，主鍵長就整體變大[出處](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-queries.html)。
*   **插入順序與頁分裂**：依序插入時索引頁大約填到 15/16，隨機插入則只有 1/2 到 15/16[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)——UUID 的值是亂跳的，會到處插頁、造成頁分裂（一頁塞滿要拆成兩頁）與空洞。

真的要用 UUID，MySQL 提供 `UUID_TO_BIN(uuid, 1)` 把變動快的時間部分換到後面，這樣存進索引欄位可以改善索引效率[出處](https://dev.mysql.com/doc/refman/8.4/en/miscellaneous-functions.html#function_uuid-to-bin)。

## 最左前綴、覆蓋索引與五種失效寫法

> 💡 面試官：複合索引的最左前綴原則是什麼？`(a, b, c)` 哪些查詢用得到？

**一句話定義**：複合索引可以想成把多個欄位的值串起來排序的一份清單，查詢條件必須從最左邊那欄開始、連續往右，最佳化器（資料庫裡決定一條查詢要怎麼執行的元件）才能用它定位[出處](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)。

| WHERE 條件 | 用得到 `(a, b, c)` 嗎 | 原因 |
| --- | --- | --- |
| `a = 1` | 用得到 | 只用第一欄，是最左前綴 |
| `a = 1 AND b = 2`、`a = 1 AND b = 2 AND c = 3` | 用得到 | 連續的前綴 |
| `a = 1 AND c = 3` | 只用到 a 那一欄 | 中間跳過 b，c 不能拿來定位——這種寫法會被當成只有 `a = 1` 來最佳化[出處](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)；EXPLAIN 的 key_len 只會算到 a |
| `b = 2`、`b = 2 AND c = 3` | 用不到 | 不是最左前綴，不會用索引查找 |
| `a = 1 OR b = 2` | 用不到 | OR 的兩邊沒有共同的索引前綴 |

再一個例子：`INDEX name (last_name, first_name)`：`WHERE first_name = 'John'` 與 `WHERE last_name = 'Jones' OR first_name = 'John'` 都用不到這個索引[出處](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)。

> 💡 面試官：覆蓋索引是什麼？怎麼從 EXPLAIN 看出來？

**一句話定義**：覆蓋索引（covering index）是「查詢要的欄位全部都在索引裡」的情況：不用拿索引值當指標回表，直接從索引結構回傳結果，省掉磁碟 I/O[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_covering_index)。因為 InnoDB 的二級索引本來就帶著主鍵欄位，`SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID'` 只要有 `(customer_id, status, created_at)` 這個索引就能覆蓋。

EXPLAIN 的 Extra 欄出現 `Using index`，意思就是只靠索引樹取得欄位資料、不必再去讀實際資料列[出處](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html#explain-extra-information)。有個邊角要知道：同一筆交易改過的資料表，在交易結束前 InnoDB 不會對它套用覆蓋索引[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_covering_index)。

> 💡 面試官：哪些寫法會讓索引用不上？

*   **對欄位套函式**：`WHERE YEAR(created_at) = 2026`——索引存的是 created_at 原值，不是算過的結果。改寫成範圍條件 `created_at >= '2026-01-01' AND created_at < '2027-01-01'`，或建函式索引（functional key part，直接對表達式建索引）[出處](https://dev.mysql.com/doc/refman/8.4/en/create-index.html#create-index-functional-key-parts)。
*   **隱含型別轉換**：字串欄位拿來跟數字比，例如 `WHERE phone = 900000123`，MySQL 沒辦法用該欄位的索引快速查找——因為 `'1'`、`' 1'`、`'1a'` 很多不同字串都會轉成同一個數字[出處](https://dev.mysql.com/doc/refman/8.4/en/type-conversion.html)。寫成 `'0900000123'` 就好了。
*   **前置萬用字元**：`LIKE '%0123'` 用不到索引；`LIKE '0900%'` 這種常數字串開頭、不以萬用字元起頭的才能用[出處](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)。
*   **OR 混到沒索引的欄位**：`WHERE customer_id = 42 OR amount > 29000`——WHERE 的兩邊沒有都用到索引，就不會用索引[出處](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)。兩邊各自有索引時，最佳化器可能改走 Index Merge（把兩個索引各掃一次再合併結果）[出處](https://dev.mysql.com/doc/refman/8.4/en/index-merge-optimization.html)。
*   **條件挑不掉多少列**：否定條件（`!=`、`NOT IN`）常落在這裡：最佳化器估計走索引仍要碰到資料表的一大部分時，會放棄索引改掃全表，因為順序讀比反覆跳頁快[出處](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)。這不算失效，是最佳化器的成本判斷。

## EXPLAIN 與慢查詢日誌

EXPLAIN 在 MySQL 8.4 的實跑見〈索引是怎麼運作的〉。

> 💡 面試官：EXPLAIN 要看哪幾欄？

**一句話定義**：EXPLAIN 印出最佳化器打算怎麼執行這條查詢；四欄最重要——`type`（存取方式）、`key`（實際選用的索引）、`rows`（估計要檢查的列數）、`Extra`（額外資訊）[出處](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)。

| `type` 由好到差 | 意思 |
| --- | --- |
| const | 主鍵或唯一索引全部欄位比對常數，最多一列，只讀一次 |
| eq_ref | JOIN 時對每組前面的列只讀一列，用的是主鍵或 UNIQUE NOT NULL 索引 |
| ref | 用索引的最左前綴或非唯一索引查找，符合值的列都讀出來 |
| range | 用索引取一段範圍：`>`、`BETWEEN`、`IN()`、`LIKE 'x%'` 這些 |
| index | 掃整棵索引樹；搭配 `Using index` 時是掃覆蓋索引，比掃表小 |
| ALL | 全表掃描；不是第一張表時通常非常糟，加索引可以避掉 |

出處：[EXPLAIN Join Types](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html#explain-join-types)

`rows` 對 InnoDB 是估計值，不見得準[出處](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)。

Extra 欄除了 `Using index`，要認得 `Using index condition`（先用索引裡的欄位過濾、再決定要不要回表）、`Using filesort`（要多做一趟排序）、`Using temporary`（要建暫存資料表）——想讓查詢快，就盯後兩個[出處](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html#explain-extra-information)。

```
EXPLAIN SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID';
-- type=ref  key=idx_cust_status_created  key_len=86  rows=14  Extra=Using index
EXPLAIN SELECT * FROM orders WHERE status = 'PAID';
-- type=ALL  key=NULL  rows=19615  Extra=Using where   ← 跳過最左欄，全表掃描
EXPLAIN FORMAT=TREE SELECT id, status FROM orders WHERE customer_id = 42 AND status = 'PAID';
-- -> Covering index lookup on orders using idx_cust_status_created (customer_id=42, status='PAID')
```

MySQL 8.4 的 `EXPLAIN` 預設輸出格式由 `explain_format` 變數決定；TREE 格式描述得更精確，也是 `EXPLAIN ANALYZE`（真的執行一次、附上實際耗時與列數）固定使用的格式[出處](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。

> 💡 面試官：慢查詢怎麼找？

開慢查詢日誌（slow query log）：執行時間超過 `long_query_time` 秒、且檢查的列數達到 `min_examined_row_limit` 的 SQL 會被記下來；`long_query_time` 最小 0、預設 10 秒，可以到微秒；日誌預設是關的[出處](https://dev.mysql.com/doc/refman/8.4/en/slow-query-log.html)。

沒用到索引的查詢預設不記，要另外開 `log_queries_not_using_indexes`；日誌太長就用 `mysqldumpslow` 彙整[出處](https://dev.mysql.com/doc/refman/8.4/en/slow-query-log.html#slow-query-log-parameters)。

找出來之後就是上一題：拿 EXPLAIN 看它為什麼慢。

## 四個等級、三種讀異常與 MVCC

讀異常與鎖的實跑見〈交易隔離層級與鎖〉；ACID 見〈SQL 三種子語言：DDL、DML、DQL〉。

> 💡 面試官：四個隔離層級各允許哪些讀異常？MySQL 預設哪個？PostgreSQL 預設哪個？

**一句話定義**：隔離層級（isolation level）是「多筆交易同時跑時，彼此看得到對方多少中間狀態」的設定，換的是效能與一致性之間的平衡。SQL 標準定義了三種讀異常[出處](https://www.postgresql.org/docs/current/transaction-iso.html)：

*   **髒讀（dirty read）**：讀到另一筆交易還沒提交的資料——對方一旦還原（rollback，取消整筆交易），你讀到的就是從沒存在過的值。
*   **不可重複讀（nonrepeatable read）**：同一筆交易裡重讀同一列，發現被別的交易改掉並提交了。
*   **幻讀（phantom read）**：同一筆交易裡重跑同一個條件查詢，符合條件的「列的集合」變了——別人插了或刪了列。

| 隔離層級 | 髒讀 | 不可重複讀 | 幻讀 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 不會 | 可能 | 可能 |
| REPEATABLE READ | 不會 | 不會 | 標準允許；PostgreSQL 實作上擋掉；InnoDB 靠快照與 Next-Key 鎖擋住一般情況，但交易內自己 UPDATE 到別人剛提交的列後，那些列會變成看得到[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)（見下） |
| SERIALIZABLE | 不會 | 不會 | 不會 |

InnoDB 提供 SQL:1992 標準的全部四級，**預設 REPEATABLE READ**[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)；**PostgreSQL 預設 READ COMMITTED**，而且內部只實作三級——它的 READ UNCOMMITTED 行為等同 READ COMMITTED；PostgreSQL 的 REPEATABLE READ 實作也不允許幻讀[出處](https://www.postgresql.org/docs/current/transaction-iso.html)。

InnoDB 在 REPEATABLE READ 下，一般 SELECT 讀的是交易第一次讀取時建立的快照；READ COMMITTED 則每次讀都拿新快照，而且一般搜尋與索引掃描不加間隙鎖（只剩外鍵檢查與重複鍵檢查會用），所以會出現幻讀[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

SERIALIZABLE 是在 REPEATABLE READ 之上，把所有一般 SELECT 隱含改成 `SELECT ... FOR SHARE`（autocommit 關閉時）[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

```
SELECT @@transaction_isolation;                          -- REPEATABLE-READ
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 只改這條連線
```

> 💡 面試官：MVCC 是什麼？InnoDB 怎麼用 undo log（記錄「修改前長什麼樣」的日誌）讀到舊版本？

**一句話定義**：MVCC（多版本並行控制）是讓讀取不用等寫入的鎖：InnoDB 保留被改過的資料列的舊版本，查詢看到的是某個時間點的快照——那個時間點之前提交的變更看得到，之後的或未提交的看不到[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。這種讀法叫一致性讀（consistent read），它不對資料表加任何鎖，所以其他連線可以同時改[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

**怎麼做到**：舊版本存在 undo 表空間（tablespace，資料庫在硬碟上的一組檔案）裡一個叫還原區段（rollback segment）的結構；InnoDB 替每一列多藏三個欄位，其中 `DB_TRX_ID` 記最後改它的交易編號，`DB_ROLL_PTR` 指向 undo log 記錄——那筆記錄裡有把這列還原成修改前內容所需的資訊[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)。讀到一列時比對交易編號，若它是在自己的快照之後才改的，就沿著指標回溯出舊版本。

實務代價：只要還有交易的快照可能用到某段 undo log，它就不能被清掉；所以連只做讀取的交易也要定期提交，否則還原區段會越長越大、塞滿 undo 表空間[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)。長交易在 PostgreSQL 造成的是另一種問題，本課最後一題「MySQL 與 PostgreSQL 差在哪」會提。

## 悲觀對樂觀、記錄鎖、間隙鎖與 Next-Key 鎖

> 💡 面試官：悲觀鎖對樂觀鎖，各適合什麼？

**一句話定義**：悲觀鎖是「先鎖再改」——假設會有人跟你搶；樂觀鎖是「先改再驗」——假設多半沒人搶，提交時才檢查資料有沒有被動過。取捨：悲觀策略犧牲效能或並行度換安全，適合失敗比例高或失敗代價大的情況；樂觀策略則假設多數請求會成功，先做再處理少數失敗[出處](https://dev.mysql.com/doc/refman/8.4/en/glossary.html#glos_pessimistic)。

**悲觀鎖：`SELECT ... FOR UPDATE`**

對搜尋碰到的索引記錄加排他鎖（exclusive lock，同一時間只能一筆交易持有），效果跟對那些列下 UPDATE 一樣；其他交易不能改、不能 `FOR SHARE`，鎖在提交或還原時才放[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

只擋寫不擋讀的用 `FOR SHARE`。要注意鎖定讀只在 autocommit（每條語句自動當成一筆交易立刻提交）關閉、或已 `START TRANSACTION` 時才有意義[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

不想排隊等鎖可以加 `NOWAIT`（有鎖就立刻報錯）或 `SKIP LOCKED`（跳過被鎖的列，適合佇列型資料表）[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html#innodb-locking-reads-nowait-skip-locked)。

**樂觀鎖：版本欄位**

資料表多一個 `version` 欄位，更新時把讀到的版本帶進 WHERE：

```
UPDATE accounts
   SET balance = balance - 100, version = version + 1
 WHERE id = 1 AND version = 7;
-- 影響列數 = 1 成功；= 0 表示有人先改過，重讀再試
```

資料庫本身不用長時間持鎖，衝突由應用程式重試處理；適合讀多寫少、衝突機率低的場景。衝突高時重試會一直失敗，這時候悲觀鎖反而省。

> 💡 面試官：記錄鎖、間隙鎖、Next-Key 鎖是什麼？為什麼可以擋幻讀？

*   **記錄鎖（record lock）**：鎖一筆索引記錄。`SELECT c1 FROM t WHERE c1 = 10 FOR UPDATE` 讓其他交易不能插入、更新或刪除 c1 = 10 的列。沒有索引的資料表也是鎖隱藏叢集索引的記錄[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-record-locks)。
*   **間隙鎖（gap lock）**：鎖兩筆索引記錄之間的「空隙」，或第一筆之前、最後一筆之後的空隙。`WHERE c1 BETWEEN 10 AND 20 FOR UPDATE` 讓別人插不進 15——不管原本有沒有 15 這個值[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-gap-locks)。間隙鎖純粹是「禁止插入」，不同交易可以同時持有同一段間隙的間隙鎖，它們彼此不衝突[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-gap-locks)。
*   **Next-Key 鎖**：記錄鎖加上「該記錄前面那段間隙」的間隙鎖。索引裡有 10、11、13、20 時，可能的 Next-Key 鎖區間是 (負無限, 10]、(10, 11]、(11, 13]、(13, 20]、(20, 正無限)[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-next-key-locks)。

**為什麼擋得住幻讀**：幻讀是重跑同一個查詢多出一列；InnoDB 預設的 REPEATABLE READ 對搜尋與索引掃描用 Next-Key 鎖，把「已有的記錄」和「記錄之間可以插入的位置」一起鎖住，別人就插不進你掃過的範圍[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-next-key-locks)。用唯一索引做等號查找、且條件涵蓋索引全部欄位時，只鎖那一筆記錄、不鎖前面的間隙；非唯一索引或範圍條件才會鎖間隙[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html#innodb-gap-locks)。

```
-- 連線 A（REPEATABLE READ，customer_id 有非唯一索引）
START TRANSACTION;
SELECT id FROM orders WHERE customer_id = 42 FOR UPDATE;
-- 連線 B：插入 customer_id = 42 的新列 → 被 Next-Key 鎖擋住，等到 A 提交
INSERT INTO orders (customer_id, status, created_at, amount, phone)
VALUES (42, 'NEW', NOW(), 1, '0999999999');
-- 同一組操作改成 READ COMMITTED：B 立刻成功——因為這個等級不加間隙鎖
```

分散式環境下這些鎖只管得到同一台資料庫；多台機器搶同一把鎖的問題見〈分散式鎖與 Redis〉。

## 死結排查、Online DDL 與 PostgreSQL 對照

> 💡 面試官：死結怎麼發生、InnoDB 怎麼處理、怎麼看 SHOW ENGINE INNODB STATUS？

**一句話定義**：死結（deadlock）是多筆交易各持有一把對方需要的鎖，全部卡住等待、誰也不放[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)。典型情境是兩筆交易以相反順序鎖同一批列：

```
-- 交易 A                                  -- 交易 B
UPDATE accounts SET ... WHERE id = 1;      UPDATE accounts SET ... WHERE id = 2;
UPDATE accounts SET ... WHERE id = 2;  ←等  UPDATE accounts SET ... WHERE id = 1;  ←等
-- 其中一方收到：ERROR 1213 (40001) Deadlock found when trying to get lock; try restarting transaction
```

**InnoDB 怎麼處理**：死結偵測預設開啟，偵測到就還原其中一筆交易（受害者）來解開，挑的是「較小」的那筆——大小以插入、更新、刪除的列數計[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlock-detection.html)。

若用 `innodb_deadlock_detect` 關掉偵測，就靠 `innodb_lock_wait_timeout`（預設 50 秒）逾時，錯誤碼 1205。要注意逾時預設**只還原當下那一條語句、不是整筆交易**（要整筆還原得開 `innodb_rollback_on_timeout`）；應用程式若以為交易已整筆還原就直接開新交易，前面的語句其實還在原交易裡、鎖也還握著[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html#sysvar_innodb_lock_wait_timeout)。

所以就算應用程式邏輯正確，也要處理「交易必須重試」的情況[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)。

**怎麼排查：**`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 區段列出最近一次死結牽涉的交易、各自正在執行的語句、持有與等待的鎖，以及 InnoDB 決定還原哪一筆[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-standard-monitor.html)。它只留最近一次；死結頻繁時開 `innodb_print_all_deadlocks`，把每一次都寫進錯誤日誌[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)。

**怎麼減少：**[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)

*   交易小而短，做完一組相關變更就提交
*   不同交易對多張表或大範圍列用同樣的順序操作
*   替 `FOR UPDATE` 與 `UPDATE ... WHERE` 用到的欄位建好索引，掃得少就鎖得少
*   能接受舊快照的 SELECT 就別加 `FOR UPDATE`
*   鎖定讀若能接受，改用 READ COMMITTED 這類較低的隔離層級

> 死結不危險，重試就好；面試答到重試機制才算完整

> 💡 面試官：大表加欄位或加索引會鎖表嗎？

**一句話定義**：Online DDL 讓 `ALTER TABLE` 用即時（instant）或就地（in-place）方式改結構，改的同時允許其他連線讀寫（叫並行 DML，DML 就是 INSERT／UPDATE／DELETE）；預設不用特別設定，MySQL 會在允許的範圍內選最少鎖的做法[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl.html)。

*   **加欄位**：通常可以 INSTANT（COMPRESSED 列格式、帶全文索引的表等例外除外），只改中繼資料（描述資料表結構的那份資料）、不重建表；INSTANT 是 MySQL 8.4 的預設演算法[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html#online-ddl-column-operations)。
*   **加二級索引**：不能 INSTANT，但可以 in-place、不重建表、允許並行 DML；建索引期間資料表照常可讀可寫，語句會等到所有正在存取這張表的交易結束才完成[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html#online-ddl-index-operations)。
*   **改欄位型別**：既不能 INSTANT 也不能 in-place，要重建表，且不允許並行 DML[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html#online-ddl-column-operations)——這才是正式環境會鎖住的那種。

```
ALTER TABLE orders ADD COLUMN note VARCHAR(100) NULL, ALGORITHM=INSTANT;
ALTER TABLE orders ADD INDEX idx_created (created_at), ALGORITHM=INPLACE, LOCK=NONE;
-- 明寫 ALGORITHM／LOCK 的好處：做不到就立刻報錯，不會默默退回鎖表的複製法
```

明寫 `LOCK=NONE`（允許讀寫）或 `LOCK=SHARED`（只允許讀），要求的並行度做不到時語句會立刻停止，建議用這個做法避免不小心把表鎖住[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl.html)。

> 💡 面試官：MySQL 與 PostgreSQL 主要差在哪？

| 面向 | MySQL（InnoDB） | PostgreSQL |
| --- | --- | --- |
| 預設隔離層級 | REPEATABLE READ[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) | READ COMMITTED；只實作三級，REPEATABLE READ 不會幻讀[出處](https://www.postgresql.org/docs/current/transaction-iso.html) |
| MVCC 舊版本放哪 | undo log（還原區段），另外保存[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html) | 留在資料表裡；UPDATE／DELETE 不會馬上移除舊版本，要靠 VACUUM 回收空間[出處](https://www.postgresql.org/docs/current/routine-vacuuming.html) |
| 索引類型 | InnoDB 的索引都是 B-tree（空間索引用 R-tree、全文索引用倒排表）[出處](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html) | 索引類型多：B-tree、Hash、GiST、SP-GiST、GIN、BRIN 與擴充套件 bloom，預設 B-tree[出處](https://www.postgresql.org/docs/current/indexes-types.html) |
| 讀寫互擋 | 一致性讀不加鎖[出處](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html) | 讀永不擋寫、寫永不擋讀，連 SERIALIZABLE 也靠可序列化快照隔離（SSI，靠偵測交易之間的相依關係、必要時中止其中一筆，而不是靠鎖）維持[出處](https://www.postgresql.org/docs/current/mvcc-intro.html) |

面試時抓兩個對比最有效：預設隔離層級不同（所以同一段程式搬家後幻讀行為會變），以及舊版本的存放位置不同（所以 PostgreSQL 有 VACUUM、MySQL 有 undo 表空間膨脹）。Spring 端 `@Transactional` 的傳播行為見面試集〈Spring 面試快答：IoC、Bean、AOP 與交易〉；隔離層級怎麼對應見〈Spring AOP 與交易控制〉。

### 重點整理

*   InnoDB 索引是 B-tree：節點多路、一頁 16KB、樹很矮，等號與範圍都能用；雜湊只能等號。資料列住在叢集索引的葉節點，二級索引帶主鍵值、要回表。
*   複合索引照最左前綴用；對欄位套函式、字串欄位比數字、`LIKE '%x'`、OR 混到沒索引的欄位，索引都用不上。查詢欄位全在索引裡就是覆蓋索引，EXPLAIN 顯示 `Using index`。
*   EXPLAIN 盯 `type`、`key`、`rows`、`Extra`；`ALL`、`Using filesort`、`Using temporary` 是警訊。慢查詢靠 slow query log 抓，預設關、門檻 10 秒。
*   InnoDB 預設 REPEATABLE READ、PostgreSQL 預設 READ COMMITTED。MVCC 用 undo log 重建舊版本，一致性讀不加鎖；長交易會讓 undo 無法清除。
*   Next-Key 鎖＝記錄鎖＋前一段間隙鎖，InnoDB 靠它在 REPEATABLE READ 擋幻讀；READ COMMITTED 一般搜尋不加間隙鎖。悲觀鎖用 `FOR UPDATE`，樂觀鎖用版本欄位加重試。
*   死結由 InnoDB 自動偵測並還原較小的交易，應用程式要重試；`SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK。加欄位 INSTANT、加索引 in-place 不鎖表，改型別才重建。

## 隨堂測驗

**Q1. InnoDB 的索引為什麼用 B-tree（B+ 樹）而不是雜湊索引？**

- (A) B-tree 隨時保持排序，等號與範圍查詢都能用，也能配合 ORDER BY；雜湊只能做等號比對
- (B) 雜湊索引在 InnoDB 裡佔的空間比 B-tree 大很多
- (C) B-tree 的等號查找比雜湊快
- (D) 雜湊索引不支援 NOT NULL 欄位

<details><summary>看答案</summary>

**答案：(A)** 雜湊索引的限制：只能等號、不能範圍、不能幫 ORDER BY、只能拿整把鍵查；B-tree 的優勢正好是範圍與排序，等號查找雜湊反而更快。

</details>

**Q2. 「回表」指的是什麼？**

- (A) 走二級索引找到主鍵值後，再到叢集索引裡把整列資料找出來的第二趟查找
- (B) 資料表太大時把資料搬回主鍵順序重排
- (C) 交易還原時把資料改回修改前的樣子
- (D) 查詢結果從快取回寫到資料表

<details><summary>看答案</summary>

**答案：(A)** InnoDB 的二級索引記錄帶著主鍵值，查非索引欄位就得拿主鍵再去叢集索引找一次；覆蓋索引就是為了省掉這一趟。

</details>

**Q3. 資料表有複合索引 (a, b, c)，下列哪個 WHERE 條件完全用不到這個索引來查找？**

- (A) WHERE b = 2 AND c = 3
- (B) WHERE a = 1
- (C) WHERE a = 1 AND b = 2 AND c = 3
- (D) WHERE a = 1 AND c = 3

<details><summary>看答案</summary>

**答案：(A)** 最左前綴原則：條件要從 a 開始才能用索引定位。(b, c) 不是最左前綴，不會用索引查找；a = 1 AND c = 3 至少還能用到 a。

</details>

**Q4. EXPLAIN 的 Extra 欄出現「Using index」代表什麼？**

- (A) 查詢需要的欄位全部從索引樹取得，不必再讀實際資料列（覆蓋索引）
- (B) 這條查詢一定用了主鍵索引
- (C) 最佳化器建議你替這條查詢加索引
- (D) 查詢正在建立暫存索引

<details><summary>看答案</summary>

**答案：(A)** Using index 是只靠索引樹裡的資訊取得欄位、不用額外去讀資料列——這正是覆蓋索引生效的訊號。

</details>

**Q5. phone 是有索引的 VARCHAR 欄位，為什麼 WHERE phone = 900000123 用不到索引？**

- (A) 字串欄位跟數字比較時要對每一列做型別轉換，很多不同字串都會轉成同一個數字，索引無法用來快速查找
- (B) 數字比字串長度短，索引的鍵長度不符
- (C) VARCHAR 欄位本來就不能建索引
- (D) MySQL 禁止在 WHERE 裡使用數字常數

<details><summary>看答案</summary>

**答案：(A)** 字串欄位與數字比較時 MySQL 無法用該欄位的索引快速查找，因為 '1'、' 1'、'1a' 都會轉成 1。改寫成字串常數 '0900000123' 就能走索引。

</details>

**Q6. InnoDB 預設的隔離層級是哪一個？PostgreSQL 預設呢？**

- (A) InnoDB 是 REPEATABLE READ，PostgreSQL 是 READ COMMITTED
- (B) 兩者都是 READ COMMITTED
- (C) InnoDB 是 READ COMMITTED，PostgreSQL 是 REPEATABLE READ
- (D) 兩者都是 SERIALIZABLE

<details><summary>看答案</summary>

**答案：(A)** InnoDB 預設 REPEATABLE READ，PostgreSQL 預設 Read Committed。這題常被拿來測有沒有實際用過兩種資料庫。

</details>

**Q7. InnoDB 的一致性讀（一般 SELECT）為什麼不用等其他交易的寫入鎖？**

- (A) 它讀的是某個時間點的快照，被改過的列會透過 undo log 重建出舊版本，整個過程不加鎖
- (B) InnoDB 會在讀取時把寫入交易暫停
- (C) 一般 SELECT 會自動加共享鎖，寫入交易要等它讀完
- (D) 因為 InnoDB 預設關閉所有鎖

<details><summary>看答案</summary>

**答案：(A)** 這就是 MVCC：每列藏著交易編號與指向 undo log 的指標，讀到比自己快照新的版本就沿指標回溯舊版本；一致性讀不對資料表加任何鎖。

</details>

**Q8. 為什麼 InnoDB 在 REPEATABLE READ 下能擋住幻讀？**

- (A) 搜尋與索引掃描用 Next-Key 鎖，把掃過的記錄和記錄之間的間隙一起鎖住，別的交易插不進那個範圍
- (B) REPEATABLE READ 會把整張資料表鎖起來
- (C) InnoDB 在這個等級下把所有 SELECT 改成 FOR UPDATE
- (D) 因為每次 SELECT 都重新拿一份新快照

<details><summary>看答案</summary>

**答案：(A)** 幻讀是重跑查詢多出新列；Next-Key 鎖＝記錄鎖＋前一段間隙鎖，鎖住了「可以插入的位置」。每次拿新快照是 READ COMMITTED 的行為，反而會出現幻讀。

</details>

**Q9. 樂觀鎖用版本欄位的做法，UPDATE 影響列數為 0 代表什麼？該怎麼處理？**

- (A) 讀到資料之後有人先改過（版本已變），應重讀最新資料再重試
- (B) 資料庫發生死結，InnoDB 已還原這筆交易
- (C) 該列被 FOR UPDATE 鎖住，要等鎖釋放
- (D) 版本欄位型別不對，UPDATE 被靜默忽略

<details><summary>看答案</summary>

**答案：(A)** WHERE version = 讀到的版本 沒命中，就表示這一列在你讀取之後被改過並提交；樂觀鎖把衝突留給應用程式重試，資料庫端不長時間持鎖。

</details>

**Q10. 發生死結時 InnoDB 預設會怎麼做？排查時要看哪裡？**

- (A) 自動偵測並還原其中一筆較小的交易，應用程式要重試；用 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 區段看牽涉的語句與鎖
- (B) 兩筆交易都會被還原，資料庫重新啟動後才能繼續
- (C) 一直等到 innodb_lock_wait_timeout 逾時，沒有其他機制
- (D) 把資料表切換成唯讀，要 DBA 手動解鎖

<details><summary>看答案</summary>

**答案：(A)** 死結偵測預設開啟，InnoDB 挑插入／更新／刪除列數較少的交易還原，應用程式要準備好重試；逾時機制只在關掉偵測時才是主要手段。

</details>
