## 解耦、緩衝尖峰、非同步，以及要付的代價

答題公式：一句話定義，再講取捨，最後補版本。以下以 Apache Kafka 4.3、RabbitMQ 4.3、Spring for Apache Kafka 4.1、Spring AMQP 4.1 為準。名詞：訊息佇列（message queue）是幫程式「留言」的中間站；送的叫生產者（producer）、收的叫消費者（consumer）、中間那台伺服器叫 broker（訊息代理）。

> 💡 面試官：什麼時候該引進訊息佇列？代價是什麼？

**一句話定義**：呼叫方不需要馬上拿到結果、兩邊又不該互相拖累時，才值得放 broker；理由是解耦、非同步，以及用佇列緩衝尖峰流量（面試集〈系統設計：秒殺與限流〉叫「以佇列平衡負載」）。

**理由與代價：**

*   **理由**：broker 提供時間上的解耦（temporal decoupling）：生產者與消費者不必同時執行。
*   **代價**：生產者可能不小心把同一則訊息送兩次，消費者的處理邏輯要冪等，否則會重複下單或重複收費。[出處](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/messaging)

引進佇列等於簽三份帳單：一致性從「馬上」變「稍後」、每個消費者都要冪等、多一套要監控。需要同步結果、或本來就在同一筆資料庫交易裡，直接呼叫就好。

> 💡 面試官：Kafka 與 RabbitMQ 差在哪？

**一句話定義**：Kafka 是可重讀的分區日誌，RabbitMQ 是讀完即刪的佇列加路由；差在資料模型，不在誰快。

|   | Kafka | RabbitMQ |
| --- | --- | --- |
| 訊息存放 | 日誌（log）：訊息被消費後不會刪除，保留多久由主題（topic）設定[出處](https://kafka.apache.org/43/getting-started/introduction/#main-concepts-and-terminology) | 佇列：消費者確認（ack）後，broker 就可以把那次投遞標記為待刪除[出處](https://www.rabbitmq.com/docs/reliability) |
| 拉還是推 | 拉（pull）：推的話消費者容易被壓垮，拉的話消費者只是落後，之後再追上[出處](https://kafka.apache.org/43/design/design/#push-vs-pull) | 推（push）：消費者訂閱之後，RabbitMQ 把佇列裡的訊息推給它；靠 prefetch（一次最多欠幾則未確認的訊息）防壓垮[出處](https://www.rabbitmq.com/docs/consumers) |
| 怎麼分工 | 消費者群組（consumer group）：主題切成多個分區（partition），每個分區在任一時刻只被群組裡的一個消費者消費[出處](https://kafka.apache.org/43/design/design/#consumer-position) | 交換器（exchange）依綁定規則把訊息路由到佇列；同一條佇列的多個消費者輪流收到訊息[出處](https://www.rabbitmq.com/docs/consumers) |

**取捨**：事件流、多個下游各自重讀、量大選 Kafka；工作佇列、複雜路由、讀完即刪選 RabbitMQ。版本要補的兩句：Apache Kafka 4.0 起只支援 KRaft、ZooKeeper 模式已移除[出處](https://kafka.apache.org/43/getting-started/upgrade/)；RabbitMQ 4.0 起移除鏡像佇列，複製佇列改用仲裁佇列（quorum queue）[出處](https://www.rabbitmq.com/docs/quorum-queues)。

## 三種語意，最後一種靠佇列自己做不到

> 💡 面試官：至多一次、至少一次、剛好一次——哪個做得到、代價是什麼？

**一句話定義：**

*   **至多一次**：可能丟失，但絕不重送。
*   **至少一次**：絕不丟失，但可能重送。
*   **剛好一次**：只被處理一次。很多系統宣稱做到剛好一次，要細讀但書。[出處](https://kafka.apache.org/43/design/design/#message-delivery-semantics)

| 語意 | 生產端 | 消費端 | 代價 |
| --- | --- | --- | --- |
| 至多一次 | 不等確認、失敗不重試 | 先提交位移（offset，記錄讀到哪裡的數字）再處理 | 會丟；只給丟了沒關係的資料 |
| 至少一次 | 等 broker 確認，沒收到就重送 | 先處理再提交位移；當機在兩步之間就重做 | 會重複，消費端必須冪等。Kafka 預設保證至少一次送達[出處](https://kafka.apache.org/43/design/design/#message-delivery-semantics)；RabbitMQ 用確認機制可保證至少一次[出處](https://www.rabbitmq.com/docs/reliability) |
| 剛好一次 | 只在「Kafka 讀、Kafka 寫」內成立：交易式生產者把輸出與位移寫進同一筆交易，消費者用 read_committed 只讀已提交的訊息 | 對其他目的地系統要做到剛好一次，通常需要那些系統配合[出處](https://kafka.apache.org/43/design/design/#message-delivery-semantics)，寫進資料庫那步還是靠冪等 |   |

**生產端細節：**`acks` 決定等幾個複本：

*   `acks=0`：完全不等伺服器確認。
*   `acks=1`：領導者寫進本地日誌就回應；它在追隨者複製完之前掛掉，那筆紀錄就會丟失。
*   `acks=all`：只要至少一個同步複本存活，紀錄就不會丟失。
*   重送造成的重複由 `enable.idempotence` 處理：生產者確保每則訊息在串流裡只寫入一份；沒有衝突設定時預設開啟。[出處](https://kafka.apache.org/43/configuration/producer-configs/)

> 💡 面試官：消費者怎麼做到冪等？

**一句話定義**：冪等（idempotent，做一次和做很多次結果一樣）靠三招：去重表、業務唯一鍵、版本號；前提是每則訊息帶全域唯一的編號。

*   **去重表**：追蹤已經處理過的訊息編號[出處](https://microservices.io/patterns/data/transactional-outbox.html)：一張以「訊息編號＋消費者名稱」為主鍵的表，寫這一列與業務更新放**同一筆交易**，重複訊息撞主鍵、整筆回復。
*   **業務唯一鍵**：直接拿訂單編號、轉帳序號當唯一索引。很多情況下訊息本身有主鍵，更新因此是冪等的。[出處](https://kafka.apache.org/43/design/design/#message-delivery-semantics)
*   **版本號**：更新加條件 `WHERE version = 舊版本`，影響列數 0 代表已處理或已過期；順序亂了也不會把舊狀態蓋回去。

```
CREATE TABLE processed_message (
  message_id   VARCHAR(64) NOT NULL,  -- 生產端給的全域唯一編號
  consumer     VARCHAR(64) NOT NULL,  -- 哪個服務處理的
  processed_at TIMESTAMP   NOT NULL,
  PRIMARY KEY (message_id, consumer)
);

BEGIN;   -- 兩步同一筆交易
INSERT INTO processed_message VALUES (:message_id, 'ledger-service', NOW());  -- 重複會撞主鍵
UPDATE account SET balance = balance - :amount WHERE account_id = :from_id;
COMMIT;
```

*【順序、丟失、堆積、死信】*

## 四個營運題

> 💡 面試官：訊息順序怎麼保證？

**一句話定義**：Kafka 只保證同一分區內有序，所以用帳戶編號當訊息的 key：同一個 key 的事件會寫進同一個分區，讀出順序與寫入時相同。[出處](https://kafka.apache.org/43/getting-started/introduction/#main-concepts-and-terminology) 全域有序等於只開一個分區，就沒有平行度。RabbitMQ 一條佇列先進先出，但多個消費者輪流取、有人失敗後訊息重新排入佇列（requeue），順序就變。

> 💡 面試官：訊息丟了怎麼辦？

**一句話定義**：三個地方會丟——生產者送出但 broker 沒收到、broker 沒寫進足夠複本、消費者收到但處理前當機。

*   **生產者確認**：Kafka 用 `acks=all` 加 `min.insync.replicas`（最少同步複本數）：同步複本數低於這個最小值，分區就不接受寫入。[出處](https://kafka.apache.org/43/design/design/#replication) RabbitMQ 是發布者確認（publisher confirm）：持久化訊息寫進磁碟之後，才送出 basic.ack。[出處](https://www.rabbitmq.com/docs/confirms)
*   **複本**：Kafka 只要任一時刻至少有一個同步複本存活，已提交的訊息就不會丟失[出處](https://kafka.apache.org/43/design/design/#replication)。RabbitMQ 的重要資料要用耐久佇列，並以持久化方式發布訊息[出處](https://www.rabbitmq.com/docs/reliability)——耐久（durable）是佇列撐得過重啟，持久（persistent）是訊息寫進磁碟，兩個都要。
*   **手動確認**：RabbitMQ 的自動確認是訊息一送出就視為成功送達，不安全[出處](https://www.rabbitmq.com/docs/confirms)；手動模式在做完該做的事之前不要確認。[出處](https://www.rabbitmq.com/docs/reliability) Kafka 對應的是關掉 `enable.auto.commit`（預設 true，每 5 秒在背景定期提交），處理完再提交。[出處](https://kafka.apache.org/43/configuration/consumer-configs/) Amazon SQS 沒有 ack，用可見性逾時（visibility timeout，取走後一段時間別人看不到，沒刪除就重新可見）代替。[出處](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)

> 💡 面試官：訊息堆積怎麼處理？

**一句話定義**：堆積（backlog，生產快過消費）先加消費者，再批次，最後問它會不會自己消。加消費者的上限是分區數（第一節 Kafka 對 RabbitMQ 那張表：一個分區同時只給一個消費者），多的閒著，所以分區數要先估好。批次是一批只做一次資料庫往返，一次 `poll()` 最多回 `max.poll.records` 則（預設 500）。[出處](https://kafka.apache.org/43/configuration/consumer-configs/) 拉模式下尖峰過了會自己消；持續堆積是容量不夠，不是調參數。RabbitMQ 要設 prefetch，否則消費者可能被壓垮、在記憶體累積訊息、耗盡 heap（程式的記憶體堆）。[出處](https://www.rabbitmq.com/docs/confirms)

> 💡 面試官：死信佇列是什麼、什麼時候用？

**一句話定義**：死信佇列（dead letter queue）收容處理不了的訊息。RabbitMQ 四種情況會變成死信，收容處叫死信交換器（dead letter exchange）：

*   消費者負面確認、且不重新排入
*   訊息因 TTL 過期
*   佇列超過長度上限而被丟棄
*   仲裁佇列（quorum queue，RabbitMQ 4.0 起的預設複製佇列）的訊息被退回超過 delivery-limit 次[出處](https://www.rabbitmq.com/docs/dlx)

最後那種叫毒訊息（poison message，每次都失敗、永遠確認不了的訊息），仲裁佇列用 `x-delivery-count` 標頭記次數。[出處](https://www.rabbitmq.com/docs/quorum-queues) 死信不是丟掉，是留證據：數量大於 0 要告警，修好後要能重放。Kafka 沒這概念，靠用戶端框架做（最後一節）。

## 先寫資料庫再發訊息，為什麼會不一致

> 💡 面試官：為什麼「先寫資料庫再發訊息」會不一致？Outbox 怎麼解？

**一句話定義**：資料庫交易與發訊息是對兩個系統各寫一次，叫雙重寫入問題：

*   資料庫更新成功、事件通知失敗：下游不會知道這個變更。
*   更新失敗、事件卻送出了：資料可能被弄壞。[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
*   不用兩階段提交（2PC，大家都說能做才一起做）：資料庫或 broker 可能不支援，而且把服務同時綁在兩者身上通常不是好事。[出處](https://microservices.io/patterns/data/transactional-outbox.html)

面試集〈系統設計：短網址的高併發〉「丟進佇列就回成功」的錯誤，正解在這裡。

**解法**：交易式 Outbox（transactional outbox）先把訊息當作更新業務資料那筆交易的一部分存進資料庫，再由另一個程序送到 broker。存訊息的表叫寄件匣（outbox），另一個程序叫訊息轉送器（message relay）。好處是訊息保證在交易提交時、而且只在提交時被送出。[出處](https://microservices.io/patterns/data/transactional-outbox.html)

```
CREATE TABLE outbox (
  id             BIGINT      PRIMARY KEY,  -- 遞增序號，輪詢照它排序；序號小的交易可能較晚提交，所以難保序
  aggregate_type VARCHAR(64) NOT NULL,     -- 'transfer'
  aggregate_id   VARCHAR(64) NOT NULL,     -- 轉帳序號，當 Kafka 的 key 保順序
  event_type     VARCHAR(64) NOT NULL,     -- 'TransferDebited'
  payload        JSON        NOT NULL,
  created_at     TIMESTAMP   NOT NULL,
  published_at   TIMESTAMP   NULL          -- 轉送成功後填上
);

BEGIN;   -- 業務寫入與寄件匣同一筆交易
UPDATE account SET balance = balance - 1000 WHERE account_id = 'A';
INSERT INTO outbox (...) VALUES (...);
COMMIT;
```

**轉送器兩種做法：**

*   **輪詢發布者**（polling publisher）定期查 outbox 表，缺點是難以按順序發布[出處](https://microservices.io/patterns/data/polling-publisher.html)。
*   **交易日誌尾隨**（transaction log tailing）改讀資料庫的變更日誌，缺點是每種資料庫要用它專屬的方案[出處](https://microservices.io/patterns/data/transaction-log-tailing.html)。

不建 outbox 表的做法：用 DynamoDB Streams（把每筆資料變更依序吐出來的串流）這種變更資料擷取（CDC）直接把變更當事件送出。[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

> Outbox 把「發訊息」變成至少一次：轉送器可能在發布之後、記錄之前當機，重啟就再發一次，消費端還是要冪等[出處](https://microservices.io/patterns/data/transactional-outbox.html)

> 💡 面試官：Saga 的兩種協調方式？補償怎麼設計？

**一句話定義**：Saga 是一連串本地交易，每筆更新資料庫並發布事件觸發下一筆；某筆因違反業務規則失敗，就執行一連串補償交易（compensating transaction）倒回前面的變更。[出處](https://microservices.io/patterns/data/saga.html)

**兩種協調方式：**

*   **協同式**（choreography；〈後端與雲端面試題庫〉稱事件協作式）：每筆本地交易發布領域事件，觸發其他服務的本地交易[出處](https://microservices.io/patterns/data/saga.html)，適合參與者少，代價是參與者變多就難以追蹤彼此的相依[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-choreography.html)。
*   **編排式**（orchestration；同課稱中央協調式）：由一個編排器（orchestrator）告訴參與者要執行哪些本地交易[出處](https://microservices.io/patterns/data/saga.html)，AWS 上可用 Step Functions（AWS 的流程編排服務）實作，代價是編排器可能成為單點故障[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)。

```
編排式 Saga 的狀態機（跨行轉帳）

  STARTED ──扣款成功──▶ DEBITED ──對方入帳成功──▶ COMPLETED
     │                    │
   扣款失敗           入帳失敗（帳戶不存在、逾時到上限）
     ▼                    ▼
  FAILED           COMPENSATING ──退回扣款成功──▶ FAILED（錢已回到原帳戶）
                          │
                     退回也失敗 ──▶ 死信 + 人工介入
```

**補償三條規則：**

*   **第一，補償是反向動作不是刪除**——退回同金額、留下兩筆紀錄。Saga 沒有自動回復，倒回變更的補償交易要自己設計。[出處](https://microservices.io/patterns/data/saga.html)
*   **第二，每步與每個補償都冪等**，才能在當機或編排器故障後重複執行。[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)
*   **第三，缺少隔離性**：Saga 沒有 ACID 裡的隔離性，多個 Saga 同時執行可能造成資料異常[出處](https://microservices.io/patterns/data/saga.html)。扣款後入帳前，別人看到的餘額已經少了；對策是語意鎖（semantic lock）[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)，實務上就是把那筆錢標成「轉出中」凍結。

*【最終一致與銀行帳務】*

## 「暫時看不到」可以，「錢不見了」不行

> 💡 面試官：最終一致對強一致，業務上怎麼解釋「暫時看不到」？

**一句話定義**：強一致是寫完下一秒任何人都讀到新值；最終一致是複本會在一段時間內趨於一致，期間有人可能讀到舊值。

> 💡 面試官：銀行轉帳可以用最終一致嗎？

**一句話定義：**「對方何時看到錢」可以，「錢的總額」不行。同一系統內的轉帳放同一筆 ACID 交易就好；跨系統（跨行、外部支付機構）沒有共同的交易，才用 Saga 加冪等加對帳，每步守住「錢不能少、帳要對得上」。

*   **帳務分錄**：複式簿記（double-entry bookkeeping）：每一筆交易都記成金額相等、方向相反的兩筆分錄（借與貸）。[出處](https://en.wikipedia.org/wiki/Double-entry_bookkeeping) 套進 Saga：扣款不是「餘額減 1000」而是「客戶帳戶借 1000、轉出中間帳戶貸 1000」（客戶存款是銀行的負債，扣款記借方），錢沒消失，只是換了位置；入帳成功後中間帳戶才結掉，補償則反向再記兩筆。分錄只增不改。
*   **冪等**：每筆轉帳一個交易序號，扣款、入帳、補償都拿它當唯一鍵；重送、重跑撞到唯一鍵就是「已經做過」，避開重複收費。[出處](https://learn.microsoft.com/en-us/azure/architecture/guide/technology-choices/messaging)
*   **對帳**：日終把兩邊分錄逐筆比對：己方每筆「轉出中」，對方是否都有入帳，差異進人工處理。對帳是承認「至少一次」與「補償也可能失敗」會發生；死信佇列裡的東西最後都要在對帳表上有交代。

**跟業務怎麼講**：別說「最終一致」四個字，說「送出成功」跟「對方看到」是兩個時間點，畫面顯示「處理中」而不是假裝完成；承諾處理中看得到、多久內一定有結果、失敗一定退回原狀。一致性模型的預期，事先要跟業務團隊講清楚。[出處](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

## @KafkaListener 與 @RabbitListener 各一眼

重送、去重表、死信與 Outbox 的實跑見〈訊息佇列：Spring 接 Kafka 與 RabbitMQ〉。

> 💡 面試官：訊息佇列在 Spring 怎麼接？

**Spring for Apache Kafka（4.1）：**@KafkaListener 把一個 Bean 的方法指定為監聽器容器的監聽器，需要 @EnableKafka 與名為 `kafkaListenerContainerFactory` 的工廠 Bean（Spring Boot 自動組態會給）。[出處](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/listener-annotation.html)

```
public class Listener {

    @KafkaListener(id = "foo", topics = "myTopic", clientIdPrefix = "myClientId")
    public void listen(String data) {
        ...
    }
}
```

*   **位移何時提交由 AckMode 決定**：從 2.3 版起，框架把 enable.auto.commit 設成 false；預設 BATCH 是一次 poll() 的紀錄全部處理完才提交，MANUAL 則自己呼叫 `acknowledge()`。[出處](https://docs.spring.io/spring-kafka/reference/kafka/receiving-messages/message-listener-container.html)
*   **丟例外時**：預設的 DefaultErrorHandler 共試 10 次，用完交給 DeadLetterPublishingRecoverer，預設送到名為 `原主題-dlt` 的主題。Kafka 的死信主題由此而來。[出處](https://docs.spring.io/spring-kafka/reference/kafka/annotation-error-handling.html)

**Spring AMQP（4.1）**：下面這段只要 myQueue 有訊息，processOrder 就會被呼叫。佇列必須已存在並綁定到某個交換器，或由 RabbitAdmin 自動宣告。[出處](https://docs.spring.io/spring-amqp/reference/amqp/receiving-messages/async-annotation-driven.html)

```
@Component
public class MyService {

    @RabbitListener(queues = "myQueue")
    public void processOrder(String data) {
        ...
    }
}
```

*   **預設 acknowledgeMode 是 AUTO**：容器自動確認，除非監聽器丟出例外。[出處](https://docs.spring.io/spring-amqp/reference/amqp/containerAttributes.html)
*   **丟例外的預設行為**：訊息被拒絕、由 broker 重新排入佇列，所以下游暫時故障這類例外會一再重送。
*   **不想重送：**`defaultRequeueRejected` 設 false，讓訊息被丟棄（或路由到死信交換器）；或丟 AmqpRejectAndDontRequeueException，針對單一訊息不重新排入。
*   **例外中的例外**：轉換失敗這類不可能成功的錯誤，預設的錯誤處理器 ConditionalRejectingErrorHandler 會直接拒絕、不重新排入。[出處](https://docs.spring.io/spring-amqp/reference/amqp/exception-handling.html)

**追問時要補的：**@Transactional 包在監聽器方法上，預設情況下只管資料庫那筆交易，管不到位移提交或訊息確認，「資料庫提交了、位移沒提交」的空窗還在——消費端要冪等的另一個理由。@Transactional 本身見〈Spring AOP 與交易控制〉。

### 重點整理

*   引進佇列為了解耦、緩衝尖峰、非同步；代價是一致性變「稍後」、消費者要冪等、多一套要監控。
*   Kafka 是可重讀的分區日誌、消費者拉、群組分工；RabbitMQ 是讀完即刪的佇列、broker 推、交換器路由。
*   佇列最多給至少一次；剛好一次只在 Kafka 內成立，寫進資料庫靠去重表、業務唯一鍵或版本號。
*   順序只在同一分區內；不丟靠 acks=all、耐久佇列加持久訊息、處理完再確認（Spring Kafka 預設 BATCH、Spring AMQP 預設 AUTO 且例外會重新排入）；堆積先加消費者再批次；壞訊息進死信佇列。
*   先寫資料庫再發訊息是雙重寫入；交易式 Outbox 把訊息寫進同一筆交易的寄件匣表再送出，代價是至少一次。
*   Saga 是一連串本地交易加補償；補償是反向動作、每步冪等、缺隔離性用凍結狀態補。
*   銀行轉帳同一系統用 ACID 交易；跨系統用 Saga，分錄借貸相等、每步冪等、日終對帳——「暫時看不到」可以，「錢不見了」不行。

## 隨堂測驗

**Q1. 一支 API 要在回應前拿到下游服務的計算結果，流量不高，兩個服務共用同一個資料庫。面試官問要不要在中間放訊息佇列，最合理的回答是？**

- (A) 不要——呼叫方需要同步結果、兩邊又在同一筆資料庫交易裡，放佇列只會多出一致性延遲、冪等與監控三份成本
- (B) 要——訊息佇列永遠比直接呼叫可靠
- (C) 要——這樣就能自動拿到剛好一次的保證
- (D) 不要——因為 Kafka 只能處理大流量

<details><summary>看答案</summary>

**答案：(A)** 佇列的價值在解耦、緩衝尖峰、非同步；呼叫方要同步結果時這三個好處都用不到，代價卻一樣要付。

</details>

**Q2. 同一個 Kafka 主題有 6 個分區，某個消費者群組開了 8 個消費者實例，會發生什麼？**

- (A) 只有 6 個在工作，另外 2 個閒著——一個分區同時只給群組裡的一個消費者
- (B) 8 個平均分攤，吞吐量比 6 個時高
- (C) Kafka 自動把主題擴成 8 個分區
- (D) 多出來的 2 個會收到重複的訊息

<details><summary>看答案</summary>

**答案：(A)** 每個分區在任一時刻只被同一個群組裡的一個消費者消費，所以消費者群組的平行度上限就是分區數。

</details>

**Q3. 消費者先處理訊息、再提交位移，處理完但還沒提交時當機了。重啟後會怎樣？這對應哪種送達語意？**

- (A) 那則訊息會被重新處理一次——這是至少一次，所以消費端必須冪等
- (B) 那則訊息永久丟失——這是至多一次
- (C) Kafka 會偵測到並跳過它——這是剛好一次
- (D) 位移會自動補上，不會重做也不會丟

<details><summary>看答案</summary>

**答案：(A)** 位移沒提交，Kafka 認為還沒消費，重啟後從舊位移重讀；先處理再提交換到的是不丟訊息，代價就是可能重複。

</details>

**Q4. 消費者處理轉帳訊息時，把「寫入去重表」和「更新帳戶餘額」放在同一筆資料庫交易裡，重複收到同一則訊息時會發生什麼？**

- (A) 寫去重表撞到主鍵、整筆交易回復，餘額不會被扣第二次
- (B) 餘額會被扣兩次，去重表只是留紀錄
- (C) 去重表阻擋第二次，但餘額那步已經先執行了
- (D) 需要另外加分散式鎖才擋得住

<details><summary>看答案</summary>

**答案：(A)** 去重表能擋重複的關鍵是「跟業務更新在同一筆交易」——主鍵衝突讓整筆交易回復，業務更新一起消失；拆成兩筆交易就會出現先扣款後才發現重複的空窗。

</details>

**Q5. Kafka 生產者設定 acks=1，領導者複本剛回覆成功就當機，追隨者還沒複製到那筆紀錄。結果是？**

- (A) 那筆紀錄丟失——要避免就設 acks=all 並配合 min.insync.replicas
- (B) 追隨者會自動向生產者要回那筆紀錄
- (C) 生產者會收到錯誤並自動重送到新領導者
- (D) 不會丟，因為 Kafka 預設所有寫入都同步到全部複本

<details><summary>看答案</summary>

**答案：(A)** acks=1 時，領導者在追隨者複製完之前掛掉，那筆紀錄就會丟失；acks=all 才會等同步複本確認。

</details>

**Q6. 服務先在資料庫交易裡更新訂單，交易提交後再呼叫 broker 發訊息。發訊息那一步因網路問題失敗了，會怎樣？交易式 Outbox 怎麼避免？**

- (A) 資料庫已更新但下游永遠收不到通知，兩邊不一致；Outbox 把訊息寫進同一筆交易的寄件匣表，再由轉送器另外送出，交易提交就一定有訊息
- (B) 資料庫交易會自動回復，所以沒有不一致；Outbox 只是加速發送
- (C) broker 會主動來資料庫抓漏掉的訊息；Outbox 是那張抓取用的表
- (D) 不會有問題，因為 Spring 的 @Transactional 會把發訊息也納入交易

<details><summary>看答案</summary>

**答案：(A)** 這就是雙重寫入問題；Outbox 讓「訊息存不存在」跟「交易有沒有提交」變成同一件事，代價是轉送器可能重送，消費端仍要冪等。

</details>

**Q7. 跨行轉帳的 Saga 走到「己方已扣款、對方入帳失敗」，正確的補償做法是？**

- (A) 執行一筆反向的退款本地交易，並留下扣款與退款兩筆分錄；補償本身也要用同一個交易序號做到冪等
- (B) 直接刪掉扣款那筆紀錄，讓帳戶回到原狀
- (C) 依賴資料庫自動回復，把扣款那筆交易 rollback
- (D) 什麼都不做，等日終對帳時再補

<details><summary>看答案</summary>

**答案：(A)** Saga 沒有自動回復，補償是開發者設計的反向動作；分錄只增不改，重跑時靠交易序號當唯一鍵避免退兩次。

</details>

**Q8. 面試官問「銀行轉帳可以用最終一致嗎？」哪個回答最站得住？**

- (A) 同一系統內用一筆 ACID 交易就好；跨系統才用 Saga，而且「對方何時看到錢」可以最終一致，但每一步分錄借貸相等、每步冪等、日終對帳都不能省
- (B) 可以，所有轉帳都改成發訊息，讓系統更有彈性
- (C) 不行，銀行任何操作都必須用兩階段提交
- (D) 可以，只要在畫面上寫「處理中」就不需要對帳

<details><summary>看答案</summary>

**答案：(A)** 「暫時看不到」可以接受，「錢不見了」不行；最終一致要靠分錄、冪等、對帳三件事撐住總額守恆。

</details>

**Q9. Spring AMQP 的 @RabbitListener 用預設的 AUTO 確認模式，監聽器方法處理時丟出一般的 RuntimeException（例如下游資料庫暫時連不上），且沒設 defaultRequeueRejected。會發生什麼？**

- (A) 訊息被拒絕並重新排入佇列，然後一再被重送——要設 defaultRequeueRejected 為 false 或丟 AmqpRejectAndDontRequeueException 讓它進死信交換器
- (B) 容器自動確認並丟棄那則訊息
- (C) 訊息被移到 Kafka 風格的 -dlt 主題
- (D) 容器停止整個監聽器，等人工介入

<details><summary>看答案</summary>

**答案：(A)** Spring AMQP 的預設行為是訊息被拒絕、由 broker 重新排入佇列，這類可能恢復的錯誤因此會一再重送；轉換失敗那類不可能成功的錯誤則由預設的錯誤處理器直接拒絕、不重新排入。

</details>
