*【雲端架構】*

## 部署、高可用、安全與成本

答題公式：先一句話定義，再講差別與取捨。

> 💡 面試官：要把系統搬上 AWS，ECS、EKS、Lambda 怎麼選？

**一句話定義**：三者分別是 AWS 代管的容器服務（ECS）、AWS 代管的 Kubernetes 服務（EKS），和無伺服器運算（Lambda——程式由事件觸發才執行，主機完全不用自己管）。容器、託管容器服務與自架 Kubernetes 怎麼選，見〈要不要用 K8s〉。

| 方案 | 適合情境 | 主要取捨 |
| --- | --- | --- |
| ECS | 想用較低的維運成本跑容器化服務 | 與 AWS 整合最直接，但綁定 AWS、生態不如 Kubernetes 完整 |
| EKS | 服務規模大、需要 Kubernetes 生態或搬家彈性 | 彈性最高，但叢集的治理、升級與成本管理都更複雜 |
| Lambda | 事件驅動、流量一陣一陣、工作能在平台限制內做完 | 完全不管主機，但要考量冷啟動（久沒被叫醒的第一次執行特別慢）與執行時間上限 |

選擇不能只看流量：團隊技能、部署頻率、工作負載型態、可攜性與總持有成本都要進來。完整的答案還會補上容器映像檔的 CI/CD（自動建置與部署管線）、VPC（雲上的虛擬私有網路）與 Security Group（跟著網卡（ENI）走的虛擬防火牆規則，見〈VPC 網路架構〉）的網路分區，以及集中式日誌與追蹤。

> 💡 面試官：如何設計跨可用區的高可用架構？

**一句話定義**：可用區（Availability Zone，同一地理區域內供電與網路彼此獨立的機房群）是 AWS 的故障隔離單位；跨可用區架構就是把服務與資料副本分散在不同故障域，一個機房出事仍能繼續服務。

*   入口用負載平衡器跨至少兩個可用區分流，健康檢查要能真的反映服務可不可用。
*   應用服務保持無狀態（任何一台都能接手任何請求），搭配 Auto Scaling 自動增減台數；擴縮的依據可以是 CPU、記憶體、請求量、延遲或佇列長度。
*   關聯式資料庫用 RDS Multi-AZ 做自動容錯移轉；注意它是高可用方案，備援那台平常不服務讀取（這裡講的是單台備援的「Multi-AZ 執行個體部署」；另一種「Multi-AZ 叢集部署」有兩台備援、可以接讀取），讀取擴充要另外用讀取副本，備份與還原演練也不能省。[出處](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.html) Multi-AZ 與讀取副本各解決什麼問題，見〈RDS 資料庫資源〉。
*   快取、訊息系統、NAT 這些依賴元件同樣要消除單點，並驗證連線池撐不撐得過切換瞬間。

> Auto Scaling 解決容量問題，跨可用區解決故障域問題——目的不同，通常要同時做

> 💡 面試官：如何設計雲端中台與資料共享？

**一句話定義**：中台（多個業務系統共用的核心服務層）靠穩定的領域能力與治理規範，讓同一套服務被重複使用。

服務照業務能力與資料所有權拆，不是照資料表或技術層切。跨服務要資料時走同步 API、事件發布或專用查詢模型；直接共用資料庫起步最快，但部署與資料表結構會從此綁死。多租戶（一套系統服務多個客戶）還要明確選擇共用資料表、分 schema（同一個資料庫裡替各租戶劃出獨立的資料表區）還是分資料庫，租戶識別、授權、稽核與資料生命週期都要進設計。

> 💡 面試官：金融級或敏感資料系統怎麼做安全設計？

**一句話定義**：縱深防禦——把身分、網路、資料、稽核設計成一層破了還有下一層的多層防線。

*   **網路**：公有、私有子網路分區，只開必要路徑，內部服務之間的流量也要控管。
*   **身分**：最小權限、職責分離，高權限帳號強制多重要素驗證（MFA）。
*   **資料**：傳輸用現行安全版本的 TLS；靜態資料用 KMS（AWS 的金鑰管理服務）或硬體安全模組管金鑰，並規劃金鑰輪替。
*   **稽核**：CloudTrail 這類操作紀錄要集中保存並開啟完整性驗證——它保證的是紀錄檔被修改、刪除或偽造時「會被發現」，不是檔案本身動不了[出處](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html)；再配上告警、調查與演練流程。

加密不等於合規：資料分類、遮罩、保存期限、資料放在哪個國家、權限定期複核與證據留存，一樣會被追問。

> 💡 面試官：如何控制雲端成本？

穩定的基礎負載用承諾型折扣：Reserved Instances（預先承諾用 1 或 3 年換折扣），相對隨需價格最多可省 72%——折扣隨服務、區域、年限與付款方式而變，不是固定的 60〜75%[出處](https://aws.amazon.com/ec2/pricing/reserved-instances/)。

> 📝 查證更正：原筆記此處寫「Reserved Instances：1-3年預留實例，節省成本60-75%」，查證後更正

可中斷、可重試的批次工作適合 Spot Instances（AWS 拿閒置容量出售，不用出價競標、價格由 AWS 決定，最多比隨需價便宜九成[出處](https://aws.amazon.com/ec2/spot/)；代價是 AWS 要收回時只提前兩分鐘通知[中斷通知](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/spot-instance-termination-notices.html)）。

這兩招都不能取代基本功：照實際用量調整機器規格、自動擴縮、清閒置資源、儲存分層、成本標籤。

*【微服務】*

## 邊界、治理、一致性與監控

> 💡 面試官：微服務的邊界怎麼決定？

**一句話定義**：邊界要圍著「能獨立演進的業務能力與資料所有權」畫，不是追求服務數量。

先用領域驅動設計（DDD——照業務領域而不是技術層切系統）找出各領域的核心規則與交易邊界，再檢查團隊能不能獨立開發、測試、部署（康威定律：系統結構會長得像組織的溝通結構）。每個服務原則上擁有自己的資料，跨服務需求靠契約或事件整合。拆太粗失去獨立性；拆太細則換來網路延遲、分散式交易與維運成本。需求還沒穩定時，模組化的單體通常是更合理的起點。

> 💡 面試官：服務發現、負載平衡、設定與熔斷怎麼搭？

*   **服務發現**：服務的機器會動態增減，要有人維護「現在誰活著、在哪」——Eureka、Consul 或 AWS Cloud Map。
*   **負載平衡**：ALB 適合當入口分流；Spring Cloud LoadBalancer 讓呼叫端自己挑一台。
*   **熔斷與韌性**：熔斷像電路的保險絲：下游一直失敗就先斷開呼叫、直接降級，避免整排執行緒卡在等逾時。Resilience4j 可做逾時、有限重試、熔斷與降級；重試要搭配退避（間隔越等越久）。
*   **設定管理**：Spring Cloud Config 或 Parameter Store 集中管設定；密碼金鑰要再用專門的祕密管理服務並定期輪替。

Netflix 已宣告 Hystrix 停止開發、進入維護模式，並建議新專案改用 Resilience4j 這類仍在維護的方案——面試再答 Hystrix 就是舊答案了[出處](https://github.com/Netflix/Hystrix)。

> 💡 面試官：訂單、庫存、支付跨三個服務，分散式交易怎麼處理？

**一句話定義**：Saga 是把一筆跨服務的交易拆成多筆本地交易，哪一步失敗就用「補償動作」把前面做過的倒回去。

兩種做法：**中央協調式**（orchestration，〈系統設計：訊息佇列與最終一致性〉稱編排式）由一個協調者按劇本叫每個服務做事，流程清楚但協調者較集中；**事件協作式**（choreography，同課稱協同式）沒有指揮，各服務聽到上一步的事件就接著做，耦合鬆但流程散在各處、難追蹤。

實作重點：冪等性（同一件事重做幾次結果都一樣——重試才不會重複扣款）、狀態機、逾時與重試上限、補償也失敗時的死信佇列與人工介入。如果業務真的要求一筆強一致的交易，先考慮把資料留在同一個交易邊界，不要硬拆成多個服務。

> 💡 面試官：微服務能保證傳統 ACID 嗎？

ACID（交易的原子性、一致性、隔離性、持久性）通常只有單一資料庫的交易能直接保證。跨服務要嘛用 2PC（兩階段提交：先問大家能不能做、都說能才一起做）換原子性、賠上可用性與延遲；要嘛接受最終一致——Saga、交易式 Outbox（要發的訊息先跟業務資料寫進同一筆交易，再另行送出；面試集〈系統設計：訊息佇列與最終一致性〉會講）這些模式。金融帳務這種不能掉的資料，靠的是不可變的分錄、唯一鍵、對帳與可重播的事件，不是宣稱採用了某個模式就算數。ACID 四個特性的定義見〈SQL 三種子語言：DDL、DML、DQL〉。

> 💡 面試官：怎麼做端到端的監控？

**一句話定義**：可觀測性是用指標、日誌、分散式追蹤三種訊號，從外部輸出推斷系統內部發生什麼事。

每個請求帶著同一個 trace ID（追蹤編號）穿過所有服務，事後才拼得回完整路徑；延遲、錯誤率、流量、飽和度要能對回服務與業務指標。Spring Cloud Sleuth 只支援到 Spring Boot 2.x，專案已停止維護、核心移交給 Micrometer Tracing——Spring Boot 3 之後的追蹤整合要答 Micrometer Tracing，Zipkin 仍可當接收追蹤資料的後端[出處](https://github.com/spring-cloud/spring-cloud-sleuth)。日誌要結構化，而且不能把敏感內容寫進去。

*【API GATEWAY】*

## 統一入口，不等於集中所有邏輯

> 💡 面試官：API Gateway 應該負責哪些工作？

**一句話定義**：API Gateway 是外部流量進後端的統一大門，共通的政策在門口一次做完。

適合集中做的：路由、TLS 終結（加密連線在大門解開，後面走內部網路）、身分驗證、粗粒度授權、限流（限制一段時間內接受的請求量，細節見下方）、CORS（瀏覽器的跨網域存取規則）、觀測與版本轉送。業務規則與資料所有權留在各領域服務——把邏輯都塞進 Gateway，它就變成一個難以部署的新單體。

> 💡 面試官：JWT、OAuth 2.0 與服務之間的 mTLS 怎麼分工？

**一句話定義**：OAuth 2.0 定義「怎麼授權」的流程；JWT 是把身分與權限聲明裝進一段字串的 Token 格式，實務上幾乎都會簽章（規格也允許加密、或不簽章的變形）；mTLS 是雙向 TLS——連線雙方都出示憑證互相驗明正身。

Gateway 驗外部 Token 的簽章、簽發者、受眾與期限；內部服務收到請求仍要照資源重新授權——不能因為進了大門就信任內網的一切。JWT 簽出去就難以即時作廢，所以要用短效存取 Token、受控的更新流程、金鑰輪替與異常使用偵測；Token 放在瀏覽器哪裡，則要同時評估 XSS（把惡意程式碼塞進網頁執行）與 CSRF（誘使瀏覽器帶著使用者身分發出偽造請求）兩種攻擊——取捨見〈網站安全三題：CORS、CSRF、密碼學〉。

> 💡 面試官：Gateway 的限流與高可用怎麼設計？

**一句話定義**：限流是在系統被打爆之前，按身分、租戶或 API 配額限制一段時間內接受的請求量。

常見演算法有令牌桶、漏桶、滑動視窗（〈系統設計：短網址的高併發〉有對照表）。分散式限流要先想好：各節點的計數狀態要多一致、限流元件故障時是放行還是拒絕、超額時回 429 與重試提示。Gateway 本身要跨故障域部署、可水平擴充，配健康檢查與容量壓測，才不會自己變成新的單點。

*【前後端整合】*

## Angular、Spring Boot 與 API 契約

> 💡 面試官：前後端分離和傳統由後端產生頁面（例如 JSP）差在哪？

**一句話定義**：前後端分離讓瀏覽器應用與後端 API 各自建置、各自部署；傳統做法是後端直接把畫面組好送出。

分離的好處：多端共用同一套 API、前後端獨立擴充、靜態檔可以放 CDN。代價：多了 API 契約、認證、CORS、狀態同步這些整合成本。傳統做法首頁與權限流程集中、結構直接，但前後端難以獨立演進。SEO（搜尋引擎最佳化）或首屏速度重要時，可評估伺服器端算繪（SSR）、預先產生頁面、懶載入與分包——用量測結果決定，不是一律引入。

> 💡 面試官：Angular 與 Spring Boot 之間的 API 契約怎麼設計？

**一句話定義**：API 契約是前後端共同遵守的請求、回應、錯誤與相容性規格。

*   照資源與 HTTP 語意建模；分頁、排序、日期、金額、空值這些細節要明講。
*   錯誤回應帶穩定的錯誤碼與可追蹤的識別碼，訊息不洩漏堆疊或內部資料。
*   版本放 URL 或 Header 都行；重點是相容期限、棄用公告與契約測試。
*   用機器可讀的規格（如 OpenAPI）產文件與型別，在 CI 裡自動擋下破壞相容性的變更。

> 💡 面試官：大型前端的元件與狀態怎麼規劃？

照功能領域切畫面、狀態與資料存取責任：展示元件專心呈現，容器或功能服務負責流程與呼叫 API。只有跨頁面、共享生命週期的狀態才需要集中管理；伺服器來的資料重點在快取失效與重新查詢，短暫的表單或畫面狀態留在元件附近就好——不是所有資料都該進全域 Store。

*【通用問題】*

## 部署、協作與技術決策

> 💡 面試官：藍綠部署、滾動更新、金絲雀發布怎麼選？

**一句話定義**：三種都是降低換版風險的部署策略，差在流量切換的粒度與要多養多少機器。

| 策略 | 做法與優點 | 代價與條件 |
| --- | --- | --- |
| 藍綠 | 新舊兩套環境整組切換，切換與退回舊版都快 | 要同時養兩套容量；資料庫變更仍須新舊相容 |
| 滾動更新 | 一批一批換，額外容量最少 | 新舊版本會短暫共存，協定要相容 |
| 金絲雀 | 先放一小撮真實流量到新版驗證，沒事再逐步放大 | 需要精細的路由、指標門檻與自動退回機制 |

零停機不是換容器就好：readiness 檢查（服務回報「我準備好了」才開始接流量）、連線排空、相容性的資料庫遷移、依賴更新順序、可驗證的退回程序，缺一項都可能中斷。

> 💡 面試官：跨團隊怎麼確保需求被正確實作？

先把業務目標轉成使用情境、非功能需求與驗收條件，再共同確認 API、事件、資料責任和錯誤情境。取捨用架構決策紀錄留底，契約測試與端到端測試提早抓整合問題，每個服務與事件都指定負責人。

> 💡 面試官：怎麼評估 Angular＋Spring Boot＋AWS 這個組合？

技術選型比的是「問題、團隊能力、生命週期成本」，不是技術名氣。這個組合有型別化前端、成熟後端生態與豐富的雲端代管能力；代價是框架升級、分散式系統治理、平台綁定與人才成本。答題時給做法：先用小型驗證量測延遲、部署與故障復原，並預先定義退出或替換路徑。

### 重點整理

*   選雲端服務先講需求與故障模型，再談 ECS／EKS／Lambda；Auto Scaling 管容量、跨可用區管故障域，兩個都要。
*   微服務邊界照業務能力與資料所有權畫；跨服務交易用 Saga＋冪等＋補償，不硬凹 ACID。
*   舊答案要更新：熔斷答 Resilience4j（Hystrix 已停止開發）、追蹤答 Micrometer Tracing（Sleuth 不支援 Spring Boot 3）。
*   Gateway 管共通政策（驗證、限流、路由），業務規則留在領域服務；JWT 過了大門，服務內仍要重新授權。
*   部署三策略記口訣：藍綠換整套、滾動一批批、金絲雀先試一小撮。

## 隨堂測驗

**Q1. 選擇 ECS、EKS 或 Lambda 時，最完整的判斷方式是什麼？**

- (A) 同時評估工作負載型態、團隊能力、維運需求、平台限制與總持有成本
- (B) 一律選 EKS，因為功能最多
- (C) 一律選 Lambda，因為不用管理伺服器
- (D) 只比較單次請求的價格

<details><summary>看答案</summary>

**答案：(A)** 功能最多或單價最低，不代表整個生命週期的成本最低——面試要答出多面向的取捨。

</details>

**Q2. RDS Multi-AZ（單台備援的執行個體部署）主要解決什麼問題？**

- (A) 跨可用區的自動容錯移轉（高可用）
- (B) 自動增加所有查詢的吞吐量
- (C) 取代備份與還原演練
- (D) 消除應用端的連線管理

<details><summary>看答案</summary>

**答案：(A)** 這種部署的備援機平常不服務讀取——讀取擴充要用讀取副本或 Multi-AZ 叢集部署，備份也要另外做。

</details>

**Q3. 判斷微服務邊界時，最重要的依據是什麼？**

- (A) 業務能力、交易邊界與資料所有權
- (B) 每個資料表都建立一個服務
- (C) 讓每個服務的程式碼行數相同
- (D) 照控制器數量平均拆分

<details><summary>看答案</summary>

**答案：(A)** 邊界要支撐業務與團隊獨立演進，不是照技術結構機械切割。

</details>

**Q4. Saga 交易要能安全重試，最不可缺少的是什麼？**

- (A) 冪等性、狀態追蹤與補償失敗的處理
- (B) 所有服務共用同一張資料表
- (C) 無限次立即重試
- (D) 停用逾時機制

<details><summary>看答案</summary>

**答案：(A)** 重試可能重複執行同一步，必須靠冪等與明確狀態避免重複扣款或重複扣庫存。

</details>

**Q5. 現在面試被問「微服務的熔斷機制」，該答哪一個？**

- (A) Resilience4j——Hystrix 已停止開發、進入維護模式
- (B) Hystrix——Netflix 最主流的熔斷器

- (D) 熔斷只能靠硬體防火牆做

<details><summary>看答案</summary>

**答案：(A)** Netflix 已宣告 Hystrix 進維護模式，並建議新專案改用 Resilience4j 這類仍在維護的方案。

</details>

**Q6. Spring Boot 3 之後要做分散式追蹤，該答哪一套？**

- (A) Micrometer Tracing（Sleuth 的核心已移交給它）
- (B) Spring Cloud Sleuth——它支援所有 Spring Boot 版本
- (C) 只看 CPU 使用率就夠
- (D) 把所有請求印進同一個文字檔

<details><summary>看答案</summary>

**答案：(A)** Sleuth 只支援到 Spring Boot 2.x 且已停止維護；新版追蹤整合走 Micrometer Tracing，Zipkin 仍可當後端。

</details>

**Q7. API Gateway 最適合承擔哪一組責任？**

- (A) 路由、身分驗證、限流與統一觀測
- (B) 保存所有服務的業務資料
- (C) 集中實作全部領域規則
- (D) 取代每個服務自己的資源授權

<details><summary>看答案</summary>

**答案：(A)** Gateway 做共通政策；細粒度的業務授權仍由各領域服務負責，否則它會變成新單體。

</details>

**Q8. JWT 已經在 Gateway 驗過了，後端服務還應該做什麼？**

- (A) 照資源與操作重新執行授權判斷
- (B) 完全信任所有內部請求

- (D) 忽略簽發者與受眾欄位

<details><summary>看答案</summary>

**答案：(A)** 驗明身分不等於擁有所有資源的權限——進了大門，各房間仍要各自管鑰匙。

</details>

**Q9. 藍綠部署能快速退回舊版，但仍要特別處理什麼？**

- (A) 資料庫結構變更的新舊相容性
- (B) 把兩套環境跑在同一顆程序裡
- (C) 停用健康檢查
- (D) 讓所有請求同時執行兩次

<details><summary>看答案</summary>

**答案：(A)** 應用退回舊版很快，但不可逆或不相容的資料庫變更會讓退回失效。

</details>

**Q10. 前後端 API 要降低整合風險，最有效的做法是什麼？**

- (A) 定義機器可讀的契約，並在 CI 自動驗證相容性
- (B) 只在上線後做人工測試

</details>
